## 1. 分布式 ID 的需求与方案

### 1.1 分布式 ID 的要求

```
① 全局唯一：所有节点生成的 ID 不重复
② 趋势递增：数据库索引友好（B+ 树顺序插入）
③ 高性能：生成速度要快（不能成为瓶颈）
④ 高可用：不能因为 ID 服务挂掉影响业务
```

### 1.2 常见方案对比

| 方案 | 唯一 | 递增 | 性能 | 问题 |
|---|---|---|---|---|
| UUID | ✅ | ❌ 无序 | 高 | **36 位字符串，索引性能差** |
| 数据库自增 | ✅ | ✅ | 低 | 单点瓶颈、暴露业务量 |
| Redis INCR | ✅ | ✅ | 高 | 依赖 Redis 可用性 |
| **雪花算法** | ✅ | ✅ 趋势递增 | 极高 | 依赖机器时钟 |
| **号段模式** | ✅ | ✅ | 高 | 依赖 DB，但预取号段 |

### 1.3 为什么不用 UUID（⭐ 必考）

```java
// UUID 的问题：
// ① 长度：36 位字符串（32 位 hex + 4 个连字符）→ 存储空间大
// ② 无序：随机生成 → B+ 树索引频繁分裂 → 插入性能差
// ③ 对比：自增 ID 插入时"顺序追加"，UUID 插入时"随机插入"
//    → 大数据量下表插入性能差距可达 10 倍以上

// UUID 适用场景：
//   ✅ 需要"不可猜测"的 ID（对外暴露）
//   ✅ 无状态合并（离线生成）
//   ❌ 数据库主键（索引性能差）
```

## 2. 雪花算法（Snowflake）⭐

### 2.1 64 位结构（⭐ 必画）

```
Snowflake 生成的 ID 是一个 long（64 位）：

┌───┬─────────────────────┬────────────┬──────────────┬───────────┐
│ 0 │ 41 位时间戳          │ 10 位机器 ID │ 12 位序列号   │           │
│ 1 │ (毫秒级，自定义纪元)  │ (5 位机房+5位机器) │ (每毫秒 4096) │           │
└───┴─────────────────────┴────────────┴──────────────┴───────────┘
bit63    bit62~22               bit21~12      bit11~0

各段位含义：
  ① 符号位（1 位）：恒为 0 → ID 永远是正数
  ② 时间戳（41 位）：毫秒级，可表示 2^41 ms ≈ 69 年
  ③ 机器 ID（10 位）：可表示 1024 台机器（5 位机房 + 5 位机器）
  ④ 序列号（12 位）：同一毫秒内最多 4096 个 ID

同一毫秒、同一机器的 ID 构成：
  ID = 时间戳 << 22 | 机器ID << 12 | 序列号
```

### 2.2 为什么时间戳 41 位 ≈ 69 年

```
2^41 毫秒 = 2,199,023,255,552 ms ≈ 69.7 年

69.7 年从"自定义纪元"开始算：
  纪元 = 2020-01-01 → 可用到 2089 年
  纪元 = 2010-01-01 → 可用到 2079 年

→ 实际使用中自己定纪元，够用一辈子
→ 面试常问：41 位为什么是 69 年？2^41 ms / (365*24*3600*1000) ≈ 69
```

### 2.3 各段位的运算

```java
// 位运算核心（理解这 4 行就理解了雪花算法）

// ① 时间戳左移 22 位（让出机器 ID 和序列号的位置）
long timestampPart = (timestamp - EPOCH) << TIMESTAMP_SHIFT;  // << 22

// ② 机器 ID 左移 12 位（让出序列号的位置）
long machinePart = machineId << MACHINE_SHIFT;                // << 12

// ③ 序列号直接放（低 12 位）
long seqPart = sequence;

// ④ 组装
long id = timestampPart | machinePart | seqPart;
```

### 2.4 完整实现（手写版）⭐

```java
public class SnowflakeIdGenerator {
    // 位段定义
    private static final long EPOCH = 1704067200000L;        // 2024-01-01 00:00:00
    private static final long TIMESTAMP_BITS = 41L;
    private static final long MACHINE_BITS = 10L;
    private static final long SEQUENCE_BITS = 12L;

    // 位移量
    private static final long MACHINE_SHIFT = SEQUENCE_BITS;                    // 12
    private static final long TIMESTAMP_SHIFT = SEQUENCE_BITS + MACHINE_BITS;   // 22

    // 掩码
    private static final long SEQUENCE_MASK = ~(-1L << SEQUENCE_BITS);          // 4095
    private static final long MAX_MACHINE_ID = ~(-1L << MACHINE_BITS);          // 1023

    private final long machineId;         // 机器 ID（0~1023）
    private long lastTimestamp = -1L;     // 上次生成的时间戳
    private long sequence = 0L;           // 当前毫秒内的序列号

    public SnowflakeIdGenerator(long machineId) {
        if (machineId < 0 || machineId > MAX_MACHINE_ID) {
            throw new IllegalArgumentException("machineId 必须在 0~1023");
        }
        this.machineId = machineId;
    }

    public synchronized long nextId() {
        long timestamp = System.currentTimeMillis();

        // ① 时钟回拨：当前时间 < 上次时间 → 异常或等待
        if (timestamp < lastTimestamp) {
            throw new RuntimeException("时钟回拨，拒绝生成 ID");
        }

        // ② 同一毫秒：序列号 +1（并处理溢出）
        if (timestamp == lastTimestamp) {
            sequence = (sequence + 1) & SEQUENCE_MASK;
            if (sequence == 0) {
                // 序列号用完了 → 等待下一毫秒
                timestamp = waitNextMillis(lastTimestamp);
            }
        } else {
            // ③ 新的一毫秒：序列号归零
            sequence = 0;
        }

        lastTimestamp = timestamp;

        // ④ 组装 ID
        return ((timestamp - EPOCH) << TIMESTAMP_SHIFT)
                | (machineId << MACHINE_SHIFT)
                | sequence;
    }

    private long waitNextMillis(long lastTimestamp) {
        long timestamp = System.currentTimeMillis();
        while (timestamp <= lastTimestamp) {
            timestamp = System.currentTimeMillis();
        }
        return timestamp;
    }
}
```

### 2.5 为什么用 synchronized

```
synchronized 保护三个共享状态：
  lastTimestamp（上次时间戳）
  sequence（序列号）
  
多线程并发调用 nextId()：
  → 同一毫秒内两个线程可能生成相同序列号 → ID 冲突！
  → synchronized 保证同一时刻只有一个线程生成 ID
  → 单机每秒能生成 4096 × 1000 = 400 万+ 个 ID，synchronized 开销可忽略
```

## 3. 时钟回拨问题（⭐ 必考）

### 3.1 什么是时钟回拨

```
雪花算法依赖系统时钟：
  ID 的时间部分 = 当前毫秒 - 纪元

时钟回拨（NTP 校时 / 手动改时间 / 虚拟化时钟漂移）：
  系统时间突然"往回跳"（如从 14:00:05 跳到 13:59:55）

后果：
  ① 生成的 ID 时间部分变小 → ID 不再递增
  ② 严重时：新 ID 的时间戳 < 之前已生成 ID 的时间戳 → 重复/乱序
  ③ 极端：回拨后与历史 ID 的时间戳+序列号完全重合 → 重复 ID！
```

### 3.2 三种解决方案

```
方案 1：抛异常（直接拒绝）—— 简单粗暴

  if (timestamp < lastTimestamp) {
      throw new RuntimeException("时钟回拨");
  }
  ✅ 简单；❌ 回拨期间服务不可用（ID 生成失败）

方案 2：等待追平（阻塞等待）—— 常用

  if (timestamp < lastTimestamp) {
      // 等到系统时间追上 lastTimestamp 再继续
      timestamp = waitUntil(lastTimestamp);
  }
  ✅ 回拨期间也能用；❌ 回拨超过阈值时等待太久

方案 3：备用 ID（兜底）—— 美团 Leaf 方案

  回拨时：
  ① 先尝试等待追平（回拨 < 阈值，如 5ms）
  ② 等待超时 → 用"备用时间"（上次时间戳 + 1 偏移）继续生成
  ③ 备用时间也用完 → 抛异常
  ✅ 容错最强；❌ 实现复杂

生产实践（美团 Leaf）：
  回拨 < 5ms → 等待追平
  回拨 >= 5ms → 抛异常（服务降级，让监控介入）
```

### 3.3 回拨处理的代码骨架

```java
public synchronized long nextId() {
    long timestamp = System.currentTimeMillis();

    // 时钟回拨处理
    if (timestamp < lastTimestamp) {
        long offset = lastTimestamp - timestamp;

        if (offset <= MAX_BACKWARD_MS) {          // ① 小回拨 → 等待追平
            timestamp = waitUntil(lastTimestamp);
        } else {                                   // ② 大回拨 → 抛异常
            throw new IllegalStateException(
                    "时钟回拨 " + offset + "ms，拒绝生成 ID");
        }
    }
    // ... 正常生成流程
}
```

## 4. 号段模式（美团 Leaf-segment）◈◈

### 4.1 原理

```
问题：数据库自增 ID 每次都要访问 DB → 性能瓶颈

号段模式：一次取一批 ID，内存中用，用完再取

  DB 表：leaf_alloc(biz_tag, max_id, step)
  ┌─────────┬────────┬──────┐
  │ biz_tag │ max_id │ step │
  ├─────────┼────────┼──────┤
  │ order   │ 1000   │ 1000 │  ← 当前已发到 1000，下次取 1000 个
  │ user    │ 2000   │ 1000 │
  └─────────┴────────┴──────┘

取号段流程：
  ① UPDATE leaf_alloc SET max_id = max_id + step WHERE biz_tag = 'order'
  ② SELECT max_id FROM leaf_alloc WHERE biz_tag = 'order'   （拿到新 max_id）
  ③ 内存中可用号段 = (旧max_id, 新max_id]，如 (1000, 2000]
  ④ 业务取 ID 时从内存号段分配 → 不访问 DB！

  号段用完 → 再执行 ①②③ 取下一批
```

### 4.2 双 Buffer 优化

```
问题：号段用完的瞬间要访问 DB → 有短暂的"取号延迟"

双 Buffer 优化：
  Buffer1：当前使用的号段
  Buffer2：预加载的号段（后台提前取）

  使用 Buffer1 时，后台检查 Buffer1 剩余量：
    剩余 < 阈值（如 20%）→ 立即预加载 Buffer2
  Buffer1 用完 → 无缝切换到 Buffer2 → 无感知

  → 把"取号"的等待提前消化 → 业务零等待
```

### 4.3 号段 vs 雪花对比

| 维度 | 号段模式 | 雪花算法 |
|---|---|---|
| 依赖 | 数据库（可用性） | 机器时钟（准确性） |
| 递增性 | 严格递增 | 趋势递增 |
| 性能 | 高（预取号段） | 极高（纯内存位运算） |
| 可用性 | DB 挂 → 号段用完就断 | 时钟回拨 → 需处理 |
| 实现 | 中（双 Buffer 较复杂） | 简单（几十行） |
| 适用 | 需要严格递增 | 高吞吐、趋势递增即可 |

## 5. 生产注意事项 & 常见坑点

### 🕳️ 坑 1：机器 ID 分配冲突

```java
// ❌ 两台机器配置了相同 machineId → 同一毫秒可能生成相同 ID！
// ✅ 机器 ID 要有明确的分配机制：
//    - 配置中心统一分配（Apollo/Nacos）
//    - 按 IP 计算（如 IP 最后一段 % 1024）
//    - 部署脚本写入环境变量
```

### 🕳️ 坑 2：忽略时钟回拨

```java
// ❌ 不处理回拨 → 回拨瞬间可能生成重复 ID → 数据主键冲突！
// ✅ 至少做"抛异常"兜底（见 §3.2）
```

### 🕳️ 坑 3：时间戳左移溢出

```java
// ⚠️ (timestamp - EPOCH) << 22 可能溢出 long？
// 41 位时间戳 << 22 = 63 位 → 加上符号位刚好 64 位
// 时间戳超过 2^41 ms（69 年）→ 溢出 → ID 变负数！
// → 保证纪元选择合理（当前纪元 + 69 年足够）
```

### 🕳️ 坑 4：测试时手动改系统时间

```java
// 测试环境手动改时间 → 时钟回拨 → ID 生成异常
// ✅ 测试时用"可注入时钟"的设计（Clock 接口），方便 mock
```

### 🕳️ 坑 5：ID 里的时间戳不可靠

```java
// ⚠️ 可以从雪花 ID 中提取时间戳，但：
//    - 是"生成时刻"，不是"业务发生时刻"
//    - 时钟回拨时时间戳可能不准
// ✅ 业务需要准确时间 → 单独存时间字段
```

## 6. 面试高频考点

1. **雪花算法的 64 位结构？**
   → 1 位符号 + 41 位时间戳（69 年）+ 10 位机器 ID（1024 台）+ 12 位序列号（4096/毫秒）。

2. **为什么 41 位时间戳能表示 69 年？**
   → 2^41 ms ≈ 69.7 年，从自定义纪元开始算。

3. **时钟回拨怎么处理？**
   → 三种：抛异常（简单）、等待追平（常用）、备用 ID（美团 Leaf 容错最强）。实践：小回拨等待、大回拨抛异常。

4. **为什么不用 UUID 做主键？**
   → 36 位字符串无序，B+ 树索引频繁分裂，插入性能差。

5. **号段模式怎么实现？双 Buffer 解决什么？**
   → DB 维护 max_id，一次取 step 个到内存用。双 Buffer 预加载，避免号段切换瞬间的 DB 延迟。

## 7. 实战练习

### 练习 1：手写雪花算法（60 分钟）★必做

```java
package com.sw.yang.concurrent.distributed;

import org.junit.jupiter.api.Test;

import java.util.HashSet;
import java.util.Set;
import java.util.concurrent.CountDownLatch;

/**
 * 练习 1：手写雪花算法 + 并发唯一性验证
 *
 * 目标：
 * 1. 理解 64 位位运算（时间戳<<22 | 机器ID<<12 | 序列号）
 * 2. 验证：多线程并发生成 10 万个 ID 无重复
 * 3. 验证：ID 趋势递增
 */
public class SnowflakeTest {

    static class SnowflakeIdGenerator {
        private static final long EPOCH = 1704067200000L;       // 2024-01-01
        private static final long MACHINE_BITS = 10L;
        private static final long SEQUENCE_BITS = 12L;
        private static final long MACHINE_SHIFT = SEQUENCE_BITS;                 // 12
        private static final long TIMESTAMP_SHIFT = SEQUENCE_BITS + MACHINE_BITS; // 22
        private static final long SEQUENCE_MASK = ~(-1L << SEQUENCE_BITS);        // 4095
        private static final long MAX_MACHINE_ID = ~(-1L << MACHINE_BITS);        // 1023

        private final long machineId;
        private long lastTimestamp = -1L;
        private long sequence = 0L;

        public SnowflakeIdGenerator(long machineId) {
            if (machineId < 0 || machineId > MAX_MACHINE_ID) {
                throw new IllegalArgumentException("machineId 必须在 0~1023");
            }
            this.machineId = machineId;
        }

        public synchronized long nextId() {
            long timestamp = System.currentTimeMillis();

            // ① 时钟回拨检测
            if (timestamp < lastTimestamp) {
                throw new RuntimeException("时钟回拨，拒绝生成 ID");
            }

            // ② 同一毫秒：序列号 +1
            if (timestamp == lastTimestamp) {
                sequence = (sequence + 1) & SEQUENCE_MASK;
                if (sequence == 0) {
                    timestamp = waitNextMillis(lastTimestamp);  // 序列号用完 → 等下毫秒
                }
            } else {
                sequence = 0;   // 新毫秒：序列号归零
            }

            lastTimestamp = timestamp;

            // ③ 组装（位运算核心）
            return ((timestamp - EPOCH) << TIMESTAMP_SHIFT)
                    | (machineId << MACHINE_SHIFT)
                    | sequence;
        }

        private long waitNextMillis(long lastTimestamp) {
            long timestamp = System.currentTimeMillis();
            while (timestamp <= lastTimestamp) {
                timestamp = System.currentTimeMillis();
            }
            return timestamp;
        }
    }

    @Test
    public void testUniqueness() throws InterruptedException {
        SnowflakeIdGenerator generator = new SnowflakeIdGenerator(1);
        final int threads = 8;
        final int perThread = 20000;   // 8 × 20000 = 16 万个 ID
        Set<Long> ids = java.util.Collections.synchronizedSet(new HashSet<>());
        CountDownLatch start = new CountDownLatch(1);
        CountDownLatch done = new CountDownLatch(threads);

        for (int i = 0; i < threads; i++) {
            new Thread(() -> {
                try {
                    start.await();
                    for (int j = 0; j < perThread; j++) {
                        ids.add(generator.nextId());
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } finally {
                    done.countDown();
                }
            }).start();
        }
        start.countDown();
        done.await();

        int expected = threads * perThread;
        System.out.println("生成 ID 总数: " + expected);
        System.out.println("去重后数量: " + ids.size());
        System.out.println(ids.size() == expected
                ? "✅ 并发生成 16 万个 ID 无重复"
                : "❌ 出现重复 ID！重复了 " + (expected - ids.size()) + " 个");
    }

    @Test
    public void testIncrementing() {
        SnowflakeIdGenerator generator = new SnowflakeIdGenerator(2);
        long prev = generator.nextId();
        boolean increasing = true;
        for (int i = 0; i < 10000; i++) {
            long next = generator.nextId();
            if (next <= prev) {
                increasing = false;
                System.out.println("❌ 不递增: " + prev + " → " + next);
                break;
            }
            prev = next;
        }
        System.out.println(increasing
                ? "✅ 连续生成 1 万个 ID 严格递增"
                : "❌ ID 不递增");
    }
}
```

```java
import org.junit.jupiter.api.Test;

import java.time.Instant;
import java.time.ZoneId;
import java.time.format.DateTimeFormatter;

/**
 * 练习 2：从雪花 ID 反推生成时间（理解位段布局）
 *
 * 原理：ID >> 22 + EPOCH = 生成毫秒时间戳

public class SnowflakeDecodeTest {

    private static final long EPOCH = 1704067200000L;   // 2024-01-01

    @Test
    public void testDecode() {
        // 复用练习 1 的生成器
        SnowflakeTest.SnowflakeIdGenerator generator =
                new SnowflakeTest.SnowflakeIdGenerator(5);

        long id = generator.nextId();
        System.out.println("ID: " + id);

        // 反推时间戳：ID 右移 22 位 = 相对纪元的毫秒数
        long timestamp = (id >> 22) + EPOCH;
        System.out.println("生成时间戳: " + timestamp);

        // 反推机器 ID：ID 右移 12 位 & 1023
        long machineId = (id >> 12) & 1023;
        System.out.println("机器 ID: " + machineId);

        // 反推序列号：ID & 4095
        long sequence = id & 4095;
        System.out.println("序列号: " + sequence);

        // 格式化时间
        String time = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss.SSS")
                .withZone(ZoneId.systemDefault())
                .format(Instant.ofEpochMilli(timestamp));
        System.out.println("生成时间: " + time);
        System.out.println("✅ 位段提取验证成功（>> 22 / >> 12 / & 4095）");
    }
}
```

### 练习 3：时钟回拨处理（45 分钟）

```java
package com.sw.yang.concurrent.distributed;

import org.junit.jupiter.api.Test;

/**
 * 练习 3：时钟回拨的三种处理策略
 *
 * 模拟：手工构造"时钟回拨"场景（把 lastTimestamp 设为未来时间）
 */
public class ClockBackwardTest {

    /**
     * 策略 1：抛异常（简单粗暴）
     */
    static class ThrowGenerator {
        private long lastTimestamp = -1;

        public synchronized long nextId() {
            long timestamp = System.currentTimeMillis();
            if (timestamp < lastTimestamp) {
                throw new IllegalStateException(
                        "时钟回拨 " + (lastTimestamp - timestamp) + "ms");
            }
            lastTimestamp = timestamp;
            return timestamp;   // 简化演示
        }

        /** 模拟回拨：把 lastTimestamp 设为未来（测试用） */
        void simulateClockBackward(long ms) {
            lastTimestamp = System.currentTimeMillis() + ms;
        }
    }

    /**
     * 策略 2：等待追平（小回拨）
     */
    static class WaitGenerator {
        private static final long MAX_BACKWARD_MS = 5;   // 阈值：5ms
        private long lastTimestamp = -1;

        public synchronized long nextId() {
            long timestamp = System.currentTimeMillis();
            if (timestamp < lastTimestamp) {
                long offset = lastTimestamp - timestamp;
                if (offset <= MAX_BACKWARD_MS) {
                    // 小回拨 → 等待追平
                    while (System.currentTimeMillis() < lastTimestamp) {
                        // 自旋等待
                    }
                } else {
                    throw new IllegalStateException(
                            "回拨 " + offset + "ms 超过阈值 " + MAX_BACKWARD_MS + "ms");
                }
            }
            lastTimestamp = System.currentTimeMillis();
            return lastTimestamp;
        }

        /** 模拟回拨：把 lastTimestamp 设为未来（测试用） */
        void simulateClockBackward(long ms) {
            lastTimestamp = System.currentTimeMillis() + ms;
        }
    }

    @Test
    public void testThrowStrategy() {
        ThrowGenerator generator = new ThrowGenerator();
        System.out.println("正常生成: " + generator.nextId());

        // 模拟时钟回拨 100ms（把 lastTimestamp 设为未来）
        generator.simulateClockBackward(100);

        try {
            generator.nextId();
            System.out.println("❌ 回拨后仍生成了 ID（策略失效）");
        } catch (IllegalStateException e) {
            System.out.println("✅ 抛异常策略生效: " + e.getMessage());
        }
    }

    @Test
    public void testWaitStrategy() {
        WaitGenerator generator = new WaitGenerator();
        System.out.println("正常生成: " + generator.nextId());

        // 小回拨 3ms（<= 阈值 5ms）→ 等待追平后正常生成
        generator.simulateClockBackward(3);
        long start = System.currentTimeMillis();
        long id = generator.nextId();
        System.out.println("小回拨 3ms → 等待追平后生成: " + id +
                "（等待 " + (System.currentTimeMillis() - start) + "ms）");

        // 大回拨 100ms（> 阈值 5ms）→ 抛异常
        generator.simulateClockBackward(100);
        try {
            generator.nextId();
            System.out.println("❌ 大回拨仍生成了 ID（策略失效）");
        } catch (IllegalStateException e) {
            System.out.println("✅ 大回拨抛异常: " + e.getMessage());
        }
    }
}
```

## 8. 自测题

1. **雪花算法的 64 位结构？各段位的容量？**
   <details><summary>答案</summary>

   1 位符号 + 41 位时间戳（2^41ms ≈ 69 年）+ 10 位机器 ID（1024 台）+ 12 位序列号（每毫秒 4096 个）。ID = 时间戳<<22 | 机器ID<<12 | 序列号。
   </details>

2. **同一毫秒序列号用完怎么办？**
   <details><summary>答案</summary>

   序列号 (sequence+1) & 4095 溢出为 0 → 自旋等待下一毫秒（waitNextMillis），下一毫秒序列号归零重新开始。
   </details>

3. **时钟回拨的三种方案？生产实践怎么选？**
   <details><summary>答案</summary>

   抛异常（简单）、等待追平（常用）、备用 ID（容错最强）。美团实践：回拨 < 5ms 等待追平，>= 5ms 抛异常（降级让监控介入）。
   </details>

4. **为什么 UUID 不适合做主键？**
   <details><summary>答案</summary>

   36 位字符串占用大 + 完全无序 → B+ 树索引随机插入 → 频繁页分裂 → 插入性能差。
   </details>

5. **号段模式的双 Buffer 解决什么问题？**
   <details><summary>答案</summary>

   号段用完瞬间要访问 DB 取新号段 → 有取号延迟。双 Buffer 后台预加载，使用中 Buffer 剩余量低于阈值时提前加载另一个 Buffer，切换无感知。
   </details>
