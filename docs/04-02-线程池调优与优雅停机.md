## 1. 四种拒绝策略（🛠️ 必背）

### 1.1 触发时机

```
拒绝策略触发的两个条件（同时满足）：
  ① 工作队列已满
  ② 线程数已达 maximumPoolSize

→ 提交的任务"无处安放" → 交给 RejectedExecutionHandler 处理
```

### 1.2 四种内置策略对比

| 策略 | 行为 | 源码核心 | 适用场景 |
|---|---|---|---|
| **AbortPolicy**（默认） | 抛 `RejectedExecutionException` | 直接 throw | 必须感知拒绝、可降级 |
| **CallerRunsPolicy** | 提交线程自己执行任务 | `task.run()` | 流量削峰、不能丢任务 |
| **DiscardPolicy** | 静默丢弃 | 什么都不做 | 允许丢任务、不关心结果 |
| **DiscardOldestPolicy** | 丢弃队首最老任务，再提交 | `poll() + execute()` | 宁可丢旧任务，执行新任务 |

```java
// 源码实现（都在 ThreadPoolExecutor 内部）

// ① AbortPolicy —— 默认，抛异常
public static class AbortPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        throw new RejectedExecutionException("Task " + r.toString() +
                                             " rejected from " + e.toString());
    }
}

// ② CallerRunsPolicy —— 提交线程自己执行（r.run()）
public static class CallerRunsPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        if (!e.isShutdown()) {
            r.run();   // ← 由调用 execute 的线程直接执行！
        }
    }
}

// ③ DiscardPolicy —— 什么都不做（静默丢弃）
public static class DiscardPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
    }
}

// ④ DiscardOldestPolicy —— 丢弃队首，重新提交
public static class DiscardOldestPolicy implements RejectedExecutionHandler {
    public void rejectedExecution(Runnable r, ThreadPoolExecutor e) {
        if (!e.isShutdown()) {
            e.getQueue().poll();   // 丢掉最老的任务
            e.execute(r);          // 再试一次新任务
        }
    }
}
```

### 1.3 CallerRunsPolicy 为什么能"流量削峰"

```
场景：瞬时流量暴增，队列满 + 线程满

拒绝任务 R → CallerRunsPolicy → 提交线程（如 Tomcat 的 HTTP 线程）自己执行 R

效果：
  ① 任务没有被丢（执行了）
  ② 提交线程被"占用"执行任务 → 它不能再提交新任务
     → 请求处理速度下降 → 上游流量自然被削掉
  ③ 线程池有喘息时间 → 处理完队列 → 恢复

→ "用提交线程的执行时间换线程池的恢复时间"
→ 注意副作用：提交线程被占用 → 如果是 Web 请求线程，响应会变慢
```

### 1.4 自定义拒绝策略（🛠️ 生产必备）

```java
// 生产规范：拒绝不能静默！要记录 + 监控 + 告警
public class BusinessRejectHandler implements RejectedExecutionHandler {
    private static final Logger log = LoggerFactory.getLogger(BusinessRejectHandler.class);
    private final AtomicLong rejectCount = new AtomicLong();  // 拒绝计数 → 上报监控

    @Override
    public void rejectedExecution(Runnable r, ThreadPoolExecutor executor) {
        long count = rejectCount.incrementAndGet();
        log.warn("线程池任务被拒绝，累计 {} 次，线程池状态: active={}, queue={}, pool={}",
                count,
                executor.getActiveCount(),
                executor.getQueue().size(),
                executor.getPoolSize());
        // ① 告警（钉钉/邮件/日志关键字）
        // ② 降级（写 MQ / 本地队列 / 丢弃并记录）
        // ③ 如果是核心业务 → 抛异常让上游感知
    }
}
```

## 2. 线程池参数配置（🛠️ 核心方法论）

### 2.1 参数配置公式

```
核心线程数配置（经验公式）：

CPU 密集型任务：
  corePoolSize = CPU 核数 + 1
  为什么 +1：防止某个线程因页缺失/暂停导致 CPU 空转

IO 密集型任务：
  corePoolSize = CPU 核数 × 2
  更精确：N_threads = N_cpu × (1 + W/C)
    W = 平均等待时间（IO 等待）
    C = 平均计算时间

  为什么 IO 密集可以多线程：
    线程在 IO 等待时让出 CPU → 更多线程能同时"等待 IO"
    每个线程大部分时间在等，小部分时间在算

如何获取 CPU 核数：
  Runtime.getRuntime().availableProcessors()
```

### 2.2 公式的局限（⚠️ 重要）

```
公式只是起点，不是答案！

原因：
  ① 任务是纯 CPU / 纯 IO 的很少，大多数是混合型
  ② W/C 的比例需要压测才能得到
  ③ 线程切换本身有开销（线程多了反而慢）

正确做法：
  1. 用公式算一个初始值
  2. JMH / 压测验证（阶段五会学）
  3. 观察监控指标（活跃线程/队列积压）动态调整
```

### 2.3 队列长度怎么定

```
队列长度的取舍：

  队列太长：
    → 任务积压严重，响应延迟越来越高
    → 用户看到的是"请求进去了但一直没结果"

  队列太短：
    → 容易触发拒绝策略
    → 但拒绝是"快速失败"，比无限排队好

经验：按"峰值 QPS × 可接受等待时间"估算
  如：峰值 1000 QPS，任务可接受排队 2 秒 → 队列 ≈ 2000
  ⚠️ 注意无界队列（默认 LinkedBlockingQueue）是 OOM 根源
```

### 2.4 拒绝策略与参数配合（组合拳）

```
生产常用组合：

组合 1（推荐：不丢任务 + 削峰）：
  ArrayBlockingQueue(1000) + CallerRunsPolicy
  → 队列满 → 提交线程自己执行（削峰）

组合 2（推荐：感知过载）：
  ArrayBlockingQueue(1000) + AbortPolicy + 自定义 handler 记录告警
  → 拒绝即告警，及时发现问题

组合 3（不推荐）：
  无界队列 + 任何策略 → OOM 风险

组合 4（允许丢任务）：
  ArrayBlockingQueue(1000) + DiscardPolicy
  → 非核心场景（如日志上报、埋点）
```

### 2.5 美团动态调参方案（◈◈ 了解）

```
问题：参数配置错了怎么办？改代码重新发布？太慢！

美团方案：配置中心动态调参
  ThreadPoolExecutor 提供了 setter 方法：
    setCorePoolSize(int)      ← 动态修改核心线程数
    setMaximumPoolSize(int)   ← 动态修改最大线程数
    setKeepAliveTime(...)     ← 动态修改空闲时间
    setRejectedExecutionHandler(...)  ← 动态换拒绝策略

实现思路：
  1. 线程池参数从配置中心读取（Apollo/Nacos）
  2. 配置变更监听器 → 调用 setter 动态调整
  3. 配合监控面板展示每个线程池的实时指标
  4. 支持人工干预：紧急降容 / 扩容

注意：setMaximumPoolSize 后，如果新值 < 当前线程数
  → 多余的线程会在空闲时被回收（getTask 的 timed 判断）
```

## 3. 线程池监控（🛠️ 生产必备）

### 3.1 核心监控指标

| 指标 | 方法 | 含义 | 告警阈值 |
|---|---|---|---|
| 活跃线程数 | `getActiveCount()` | 正在执行任务的线程 | 接近 poolSize 时告警 |
| 线程总数 | `getPoolSize()` | 当前池中线程数 | — |
| 队列积压 | `getQueue().size()` | 排队等待的任务数 | 持续增长时告警 |
| 完成任务数 | `getCompletedTaskCount()` | 累计完成任务 | 速率下降异常 |
| 历史最大线程数 | `getLargestPoolSize()` | 曾达到的最大线程数 | 接近 maxPool 告警 |
| 拒绝次数 | 自定义 handler 计数 | 被拒绝的任务数 | 大于 0 即告警 |
| 任务耗时 | 任务内记录 | 平均执行耗时 | 上升告警 |

### 3.2 监控实现模板

```java
public class ThreadPoolMonitor {
    private final ThreadPoolExecutor pool;
    private final ScheduledExecutorService scheduler =
            Executors.newScheduledThreadPool(1);

    public ThreadPoolMonitor(ThreadPoolExecutor pool) {
        this.pool = pool;
    }

    public void start() {
        scheduler.scheduleAtFixedRate(() -> {
            Map<String, Object> metrics = new HashMap<>();
            metrics.put("poolSize", pool.getPoolSize());
            metrics.put("activeCount", pool.getActiveCount());
            metrics.put("queueSize", pool.getQueue().size());
            metrics.put("completedTaskCount", pool.getCompletedTaskCount());
            metrics.put("largestPoolSize", pool.getLargestPoolSize());
            // → 上报 Prometheus / 日志 / 监控平台
            System.out.println(metrics);
        }, 0, 10, TimeUnit.SECONDS);   // 每 10 秒采集一次
    }
}
```

### 3.3 监控告警的决策逻辑

```
如何判断线程池"不健康"：

① 队列积压持续增长 + 活跃线程 = poolSize：
   → 线程池已满负荷，处理不过来 → 扩容 or 降级

② 拒绝次数 > 0：
   → 已触发拒绝 → 立即告警（任务丢失风险）

③ 活跃线程长期 = 0 但任务在队列：
   → 异常！有任务但没线程在跑 → 排查 bug

④ 完成任务数速率骤降：
   → 可能有任务卡死（死锁/外部依赖超时）
```

## 4. 优雅停机（🛠️ 生产必备）

### 4.1 shutdown vs shutdownNow 对比

| 维度 | `shutdown()` | `shutdownNow()` |
|---|---|---|
| 新任务 | 拒绝接收 | 拒绝接收 |
| 队列任务 | **继续执行完** | **清空并返回**（List<Runnable>） |
| 执行中任务 | 等待执行完 | **尝试中断**（interrupt） |
| 线程 | 自然退出 | 中断后退出 |
| 返回值 | void | 未执行的任务列表 |

```java
// shutdown()：温和关闭
pool.shutdown();
// → 已提交的任务（含队列中的）都会执行完
// → 之后提交的任务抛 RejectedExecutionException

// shutdownNow()：暴力关闭
List<Runnable> unfinished = pool.shutdownNow();
// → 队列中的任务被清空，返回给你（自己处理：落库/重发/丢弃）
// → 执行中的任务收到 interrupt（能否停取决于任务是否响应中断）
// → 不响应中断的任务会继续执行（interrupt 只是"请求"不是"强制"）
```

### 4.2 awaitTermination —— 等待终止

```java
// 等待线程池终止（最多等 N 秒）
boolean terminated = pool.awaitTermination(30, TimeUnit.SECONDS);
if (!terminated) {
    // 30 秒还没终止 → 仍有任务在跑（不响应中断）
    // 处理：记录日志 / 强制关闭（不推荐） / 继续等待
}
```

### 4.3 优雅停机标准三件套（⭐ 必背）

```java
public void gracefulShutdown(ThreadPoolExecutor pool, int waitSeconds) {
    pool.shutdown();                          // ① 停止接收新任务
    try {
        if (!pool.awaitTermination(waitSeconds, TimeUnit.SECONDS)) {
            // ② 等待超时 → 升级为强制关闭
            pool.shutdownNow();               // 中断执行中任务 + 清空队列
            if (!pool.awaitTermination(waitSeconds, TimeUnit.SECONDS)) {
                // ③ 再次超时 → 记录告警（可能有不响应中断的任务）
                log.error("线程池未能优雅关闭");
            }
        }
    } catch (InterruptedException e) {
        pool.shutdownNow();                   // 被中断 → 强制关闭
        Thread.currentThread().interrupt();
    }
}
```

```
两阶段关闭流程：

阶段 1：shutdown() → awaitTermination(30s)
  等待已提交任务自然完成（温和）

阶段 2：shutdownNow() → awaitTermination(30s)
  强制中断剩余任务（暴力）

为什么两阶段？
  先给任务一个"完成机会"（优雅）
  超时说明任务太慢或不响应中断 → 再强制（兜底）
```

### 4.4 Spring 应用中的优雅停机

```java
@Configuration
public class ThreadPoolConfig {
    @Bean(name = "orderExecutor", destroyMethod = "shutdown")
    public ThreadPoolExecutor orderExecutor() {
        return new ThreadPoolExecutor(...);
    }
}
// destroyMethod = "shutdown"：Spring 容器关闭时自动调用 shutdown()

// 或自定义关闭逻辑（⚠️ 注意：必须注入 bean，不能直接调用配置方法！
// 直接调用 orderExecutor() 会 new 一个新线程池实例再关闭 → 产生孤儿线程池泄漏）
@Configuration
public class ShutdownConfig {
    @Resource(name = "orderExecutor")
    private ThreadPoolExecutor orderExecutor;

    @Resource(name = "logExecutor")
    private ThreadPoolExecutor logExecutor;

    @PreDestroy
    public void shutdown() {
        // 应用关闭前：所有线程池优雅关闭
        orderExecutor.shutdown();
        logExecutor.shutdown();
    }
}
```

### 4.5 停机时"任务执行到一半"的问题

```java
// 任务执行一半被 shutdown → 数据一致性怎么办？

// 方案 1：任务支持中断，中断时回滚/补偿
```

## 5. Executors 工厂方法陷阱（🛠️ 回顾 + 完整）

| 工厂方法 | 线程数 | 队列 | 陷阱 |
|---|---|---|---|
| `newFixedThreadPool(n)` | n | 无界 LinkedBlockingQueue | **OOM 风险** |
| `newCachedThreadPool()` | 0~MAX_VALUE | SynchronousQueue | **线程爆炸风险** |
| `newSingleThreadExecutor()` | 1 | 无界队列 | **OOM 风险** |
| `newScheduledThreadPool(n)` | n | DelayedWorkQueue | 基本安全 |
| `newWorkStealingPool()` | CPU 核数 | 每个线程有私有双端队列 | ForkJoinPool 工作窃取模型 |

```
阿里规约：
  【强制】线程池不允许使用 Executors 去创建
  而是通过 ThreadPoolExecutor 的方式，
  这样的处理方式让写的同学更加明确线程池的运行规则，
  规避资源耗尽的风险
```

## 6. 生产注意事项 & 常见坑点

### 🕳️ 坑 1：无界队列 + 固定线程 = 必 OOM

```java
// ❌ 经典事故：任务堆积 → 内存耗尽 → 服务挂掉
Executors.newFixedThreadPool(10);   // 无界队列！

// ✅ 有界队列 + 拒绝策略
new ThreadPoolExecutor(10, 20, 60, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(1000), factory, handler);
```

### 🕳️ 坑 2：核心线程默认"懒启动"

```java
// 线程池刚创建时一个线程都没有！
// 第一个任务才触发创建核心线程

// ✅ 需要预热（如提前加载缓存）：
pool.prestartAllCoreThreads();   // 预启动所有核心线程
pool.prestartCoreThread();       // 预启动 1 个核心线程
```

### 🕳️ 坑 3：shutdown 后忘了 awaitTermination

```java
// ❌ shutdown() 后直接结束 → 应用退出，队列任务没执行完
pool.shutdown();
// 进程退出 → 队列中的任务丢失！

// ✅ 必须 awaitTermination 等待
pool.shutdown();
pool.awaitTermination(30, TimeUnit.SECONDS);
```

### 🕳️ 坑 4：shutdownNow 无法停止"不响应中断"的任务

```java
// ⚠️ interrupt() 只是设置中断标志，任务不检查就不停
pool.shutdownNow();
// 正在执行 while(true) { doSomething(); } 的任务不会停！

// ✅ 任务内部要响应中断：
while (!Thread.currentThread().isInterrupted()) {
    doSomething();
}
// 或捕获 InterruptedException 后退出
```

### 🕳️ 坑 5：任务里吞掉中断异常

```java
// ❌ 吞掉中断 → 任务永远不响应 shutdownNow
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    // 什么都不做 → 中断标志被清除 → 任务继续跑
}

// ✅ 恢复中断标志
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return;   // 或抛出
}
```

### 🕳️ 坑 6：一个应用多个线程池不加管理

```java
// ❌ 每个模块自己 new 线程池 → 线程数失控 + 无法统一监控
// ✅ 统一线程池管理组件（类似美团 DynamicTp）：
//    注册中心集中管理 + 统一命名 + 统一监控 + 动态调参
```

## 7. 面试高频考点

1. **4 种拒绝策略分别是什么？各自适用什么场景？**
   → Abort（抛异常，感知拒绝）/ CallerRuns（提交线程执行，削峰）/ Discard（静默丢）/ DiscardOldest（丢队首）。

2. **CallerRunsPolicy 为什么能削峰？有什么副作用？**
   → 提交线程执行任务 → 被占用无法提交新任务 → 流量自然下降。副作用：提交线程响应变慢。

3. **CPU 密集和 IO 密集的线程数怎么配？**
   → CPU 密集：核数+1；IO 密集：核数×2 或 N×(1+W/C)。公式只是起点，要压测验证。

4. **shutdown 和 shutdownNow 的区别？**
   → shutdown：等队列任务执行完；shutdownNow：清空队列+中断执行中任务，返回未执行列表。

5. **优雅停机的标准流程？**
   → shutdown → awaitTermination → 超时则 shutdownNow → awaitTermination → 仍超时记录告警。

## 8. 实战练习

### 练习 1：四种拒绝策略对比（60 分钟）★必做

```java
package com.sw.yang.concurrent.pool;

import org.junit.jupiter.api.Test;

import java.util.concurrent.*;

/**
 * 练习 1：验证四种拒绝策略的行为差异
 *
 * 配置：核心 1，最大 1，队列 1 → 提交 3 个任务 → 第 3 个必被拒绝
 */
public class RejectPolicyTest {

    private ThreadPoolExecutor createPool(RejectedExecutionHandler handler) {
        return new ThreadPoolExecutor(
                1, 1, 60, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(1),
                r -> { Thread t = new Thread(r); t.setName("reject-worker"); return t; },
                handler);
    }

    @Test
    public void testAbortPolicy() throws InterruptedException {
        ThreadPoolExecutor pool = createPool(new ThreadPoolExecutor.AbortPolicy());
        submit3Tasks(pool);  // 第 3 个抛 RejectedExecutionException
        pool.shutdown();
    }

    @Test
    public void testCallerRunsPolicy() throws InterruptedException {
        ThreadPoolExecutor pool = createPool(new ThreadPoolExecutor.CallerRunsPolicy());
        submit3Tasks(pool);  // 第 3 个由主线程（调用 execute 的线程）执行
        pool.shutdown();
        System.out.println("✅ CallerRunsPolicy：第 3 个任务由 " + Thread.currentThread().getName() + " 执行");
    }

    @Test
    public void testDiscardPolicy() throws InterruptedException {
        ThreadPoolExecutor pool = createPool(new ThreadPoolExecutor.DiscardPolicy());
        submit3Tasks(pool);  // 第 3 个静默丢弃
        pool.shutdown();
        System.out.println("✅ DiscardPolicy：第 3 个任务被静默丢弃（无异常无日志）");
    }

    @Test
    public void testDiscardOldestPolicy() throws InterruptedException {
        ThreadPoolExecutor pool = createPool(new ThreadPoolExecutor.DiscardOldestPolicy());
        submit3Tasks(pool);  // 第 3 个挤掉队首任务
        pool.shutdown();
        System.out.println("✅ DiscardOldestPolicy：第 3 个任务挤掉了队列里最老的任务");
    }

    private void submit3Tasks(ThreadPoolExecutor pool) {
        // 任务 1：占住唯一线程
        pool.execute(() -> {
            System.out.println("任务 1 执行（" + Thread.currentThread().getName() + "）");
            try { Thread.sleep(300); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        });
        // 任务 2：进队列
        pool.execute(() -> System.out.println("任务 2 执行（" + Thread.currentThread().getName() + "）"));
        // 任务 3：队列满 + 线程满 → 触发拒绝策略
        try {
            pool.execute(() -> System.out.println("任务 3 执行（" + Thread.currentThread().getName() + "）"));
        } catch (RejectedExecutionException e) {
            System.out.println("任务 3 被拒绝（AbortPolicy 抛异常）");
        }
    }
}
```

### 练习 2：优雅停机实战（60 分钟）★必做

```java
package com.sw.yang.concurrent.pool;

import org.junit.jupiter.api.Test;

import java.util.concurrent.*;

/**
 * 练习 2：优雅停机三件套（shutdown → awaitTermination → shutdownNow）
 */
public class GracefulShutdownTest {

    @Test
    public void testGracefulShutdown() throws InterruptedException {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                2, 4, 60, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(10),
                r -> { Thread t = new Thread(r); t.setName("grace-worker"); return t; },
                new ThreadPoolExecutor.CallerRunsPolicy());

        // 提交 5 个任务（每个 500ms，共需 2.5s 串行 / 更快并行）
        for (int i = 1; i <= 5; i++) {
            final int id = i;
            pool.execute(() -> {
                System.out.println("任务 " + id + " 开始（" + Thread.currentThread().getName() + "）");
                try { Thread.sleep(500); } catch (InterruptedException e) {
                    System.out.println("任务 " + id + " 被中断！");
                    Thread.currentThread().interrupt();
                    return;
                }
                System.out.println("任务 " + id + " 完成");
            });
        }

        System.out.println("=== 开始优雅停机 ===");
        pool.shutdown();   // ① 停止接收新任务，等待已提交的完成

        boolean terminated = pool.awaitTermination(3, TimeUnit.SECONDS);  // ② 最多等 3 秒
        if (!terminated) {
            System.out.println("=== 3 秒未完成 → shutdownNow ===");
            List<Runnable> unfinished = pool.shutdownNow();  // ③ 强制中断
            System.out.println("未完成任务数: " + unfinished.size());
            pool.awaitTermination(3, TimeUnit.SECONDS);
        }

        System.out.println("最终终止状态: " + pool.isTerminated());
        System.out.println("✅ 优雅停机流程执行完毕");
    }

    /**
     * 对比：不响应中断的任务 shutdownNow 也停不掉
     */
    @Test
    public void testUninterruptibleTask() throws InterruptedException {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                1, 1, 60, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(1),
                r -> { Thread t = new Thread(r); t.setName("stubborn"); return t; },
                new ThreadPoolExecutor.AbortPolicy());

        pool.execute(() -> {
            System.out.println("顽固任务开始执行...");
            // ❌ 不检查中断标志 → interrupt 无效
            long start = System.currentTimeMillis();
            while (System.currentTimeMillis() - start < 2000) {
                // 忙循环（不响应中断）
            }
            System.out.println("顽固任务执行完（中断对它无效！）");
        });

        pool.shutdownNow();   // 尝试中断
        boolean terminated = pool.awaitTermination(1, TimeUnit.SECONDS);
        System.out.println("1 秒后是否终止: " + terminated);
        System.out.println("✅ 演示：不响应中断的任务，shutdownNow 也停不掉（任务必须自己配合）");
        pool.awaitTermination(5, TimeUnit.SECONDS);
    }
}
```

```java
package com.sw.yang.concurrent.pool;

public class DynamicConfigTest {

    @Test
    public void testDynamicAdjust() throws InterruptedException {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                2, 4, 60, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(10),
                r -> { Thread t = new Thread(r); t.setName("dynamic-worker"); return t; },

                " 最大=" + pool.getMaximumPoolSize());

        // 扩容时必须先调大 maximumPoolSize，否则 corePoolSize 不能超过当前 maximumPoolSize。
        pool.setMaximumPoolSize(16);  // 动态扩容最大线程
        pool.setCorePoolSize(8);      // 动态扩容核心线程
        System.out.println("扩容后: 核心=" + pool.getCorePoolSize() +
                " 最大=" + pool.getMaximumPoolSize());

        // 提交一批任务验证
        for (int i = 0; i < 10; i++) {
            pool.execute(() -> {
                try { Thread.sleep(100); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            });
        }
        Thread.sleep(500);
        System.out.println("当前线程数: " + pool.getPoolSize() +
                " 活跃: " + pool.getActiveCount());

        // 模拟高峰期过去，降容
        pool.setCorePoolSize(1);
        pool.setMaximumPoolSize(2);
        System.out.println("降容后: 核心=" + pool.getCorePoolSize() +
                " 最大=" + pool.getMaximumPoolSize() +
                "（多余线程空闲后自动回收）");

        pool.shutdown();
        pool.awaitTermination(5, TimeUnit.SECONDS);
        System.out.println("✅ 动态调参演示完成（生产中由配置中心触发）");
    }
```

## 9. 自测题

1. **CallerRunsPolicy 的执行线程是谁？为什么能削峰？**
   <details><summary>答案</summary>

   执行线程是调用 execute() 的提交线程（如 Web 请求线程）。它执行任务期间无法再提交新任务 → 提交速率下降 → 削峰。副作用：提交线程被占用，响应变慢。
   </details>

2. **CPU 密集和 IO 密集线程数公式？公式的局限？**
   <details><summary>答案</summary>

   CPU 密集：N+1；IO 密集：N×2 或 N×(1+W/C)。局限：真实任务多为混合型，W/C 需要压测才能获得，公式只是起点。
   </details>

3. **shutdownNow 返回什么？任务都会停止吗？**
   <details><summary>答案</summary>

   返回未执行的任务列表（队列中清空的）。执行中的任务只是收到 interrupt 请求，不响应中断的任务不会停止。
   </details>

4. **优雅停机为什么是两阶段？**
   <details><summary>答案</summary>

   第一阶段 shutdown 给任务"自然完成的机会"（温和）；超时说明任务太慢/不响应中断 → 第二阶段 shutdownNow 兜底强制中断。两阶段平衡了"优雅"与"确定性"。
   </details>

5. **无界队列为什么是 OOM 根源？**
   <details><summary>答案</summary>

   队列无界 → 任务无限堆积在内存 → 内存耗尽 → OOM。且队列永远不满 → 永远不会创建临时线程 → maximumPoolSize 形同虚设。
   </details>
