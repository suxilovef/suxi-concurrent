## 1. 为什么需要 JMH

### 1.1 普通测试测不准性能

```java
// ❌ 错误的测法：System.currentTimeMillis 前后相减
long start = System.currentTimeMillis();
for (int i = 0; i < 1_000_000; i++) {
    doSomething();   // 编译器可能把循环优化掉！
}
long cost = System.currentTimeMillis() - start;
// 问题：
// ① JIT 优化：方法可能被内联/消除 → 测的是"空循环"
// ② 没有预热：第一次调用包含类加载/JIT 编译 → 结果虚高
// ③ 系统噪音：GC、OS 调度 → 结果不稳定
// ④ 测试代码本身有开销：循环、计时器

// ✅ 正确姿势：JMH（Java Microbenchmark Harness）
// 由 JIT 专家 Aleksey Shipilëv 主导开发，专门解决这些问题
```

### 1.2 JMH 解决了什么

```
① 预热（Warmup）：先跑几轮让 JIT 完成优化，再测
② 黑洞（Blackhole）：防止死代码消除
③ Fork 隔离：每个 benchmark 独立 JVM，互不干扰
④ 统计：多轮采样 + 标准差，给出置信区间
⑤ 模式：吞吐量 / 平均耗时 / 采样分布
```

### 2.2 第一个 Benchmark（完整可运行）

```java
package com.sw.yang.concurrent.jmh;

import org.openjdk.jmh.annotations.*;
import org.openjdk.jmh.runner.Runner;
import org.openjdk.jmh.runner.options.Options;
import org.openjdk.jmh.runner.options.OptionsBuilder;

import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicLong;

/**
 * 第一个 JMH 基准测试：AtomicLong vs synchronized 自增
 */
@BenchmarkMode(Mode.Throughput)        // 模式：吞吐量（每秒操作数）
@OutputTimeUnit(TimeUnit.SECONDS)      // 时间单位
@Warmup(iterations = 3, time = 1)      // 预热：3 轮，每轮 1 秒
@Measurement(iterations = 5, time = 1) // 测量：5 轮，每轮 1 秒
@Fork(1)                               // 独立 JVM 数
@State(Scope.Benchmark)                // 状态：所有线程共享
public class FirstBenchmark {

    private AtomicLong atomic = new AtomicLong(0);
    private long syncCount = 0;

    @Benchmark
    public long atomicIncrement() {
        return atomic.incrementAndGet();
    }

    @Benchmark
    public synchronized long syncIncrement() {
        return ++syncCount;
    }

    public static void main(String[] args) throws Exception {
        Options opt = new OptionsBuilder()
                .include(FirstBenchmark.class.getSimpleName())
                .build();
        new Runner(opt).run();
    }
}
```

### 2.3 核心注解速查

| 注解 | 作用 | 常用值 |
|---|---|---|
| `@Benchmark` | 标记被测方法 | — |
| `@BenchmarkMode` | 测试模式 | Throughput / AverageTime / SampleTime / SingleShotTime |
| `@OutputTimeUnit` | 结果时间单位 | TimeUnit.SECONDS / MILLISECONDS |
| `@Warmup` | 预热参数 | iterations=3, time=1 |
| `@Measurement` | 测量参数 | iterations=5, time=1 |
| `@Fork` | fork 的 JVM 数 | 1~3 |
| `@State` | 状态作用域 | Benchmark / Thread / Group |
| `@Setup` / `@TearDown` | 初始化 / 清理 | 类似 JUnit 的 Before/After |

### 2.4 四大模式

| 模式 | 含义 | 结果 | 适用 |
|---|---|---|---|
| `Throughput` | 吞吐量 | 每秒操作数（越大越好） | 高并发场景 |
| `AverageTime` | 平均耗时 | 每次操作毫秒/微秒（越小越好） | 响应时间敏感 |
| `SampleTime` | 采样分布 | 各百分位耗时（p50/p90/p99） | 分析延迟分布 |
| `SingleShotTime` | 单次执行 | 冷启动/一次性操作 | 启动耗时类 |

## 3. JMH 五大陷阱（⭐ 必会）

### 陷阱 1：死代码消除（Dead Code Elimination）

```java
// ⚠️ 先澄清一个关键机制：JMH 会自动消费 benchmark 方法的返回值！
//    public long bad() { ...; return sum; } —— 返回了就不会被消除
//    真正会死代码消除的是：void 方法 + 计算结果没被使用

// ❌ 结果被"优化掉"（void 方法 + sum 没被消费）：
@Benchmark
public void bad() {
    long sum = 0;
    for (int i = 0; i < 100; i++) {
        sum += i;      // sum 计算结果没人用 → JIT 把整个循环删了！
    }
    // 没有 return、没有 bh.consume → 死代码！
}

// ✅ 用 Blackhole 消费结果：
@Benchmark
public void good(Blackhole bh) {
    long sum = 0;
    for (int i = 0; i < 100; i++) {
        sum += i;
    }
    bh.consume(sum);   // ★ 黑洞：让 JIT 无法消除计算
}
```

```
为什么需要 Blackhole？
  JIT 发现"计算结果没被使用" → 整个计算是死代码 → 直接删除
  → 你测的变成了"空方法" → 结果毫无意义
  → Blackhole.consume() 模拟"结果被使用" → 阻止消除

什么时候需要 Blackhole：
  ✅ benchmark 返回 void 且计算结果是局部变量 → 必须 consume
  ✅ 方法内部有中间结果需要保留 → 必须 consume
  ❌ benchmark 直接 return 结果 → JMH 自动消费，无需手动
```

### 陷阱 2：在 @Benchmark 方法里写循环

```java
// ❌ 循环应该在"调用方"（JMH 自己会循环调用）
@Benchmark
public void bad() {
    for (int i = 0; i < 1000; i++) {   // 内层循环会被优化
        doWork();
    }
}
// 问题：JIT 可能把循环展开/消除，测的是优化后的结果，不是真实性能

// ✅ 方法体只做"一次操作"，循环由 JMH 控制
@Benchmark
public void good() {
    doWork();   // JMH 自己会反复调用这个方法
}
```

### 陷阱 3：不预热就测

```java
// ❌ 没有预热 → 结果包含 JIT 编译时间
// 第一次调用：解释执行 → 第二次：C1 编译 → 第三次：C2 编译
// 每次结果都不同，且都比"稳定态"慢

// ✅ 预热让 JIT 完成优化，测的是稳定态
@Warmup(iterations = 5, time = 1)   // 5 轮 × 1 秒预热
```

### 陷阱 4：Fork 太少或太多

```java
// ❌ @Fork(0)：不 fork → 和其他 benchmark 共享 JVM
// 前一个 benchmark 的 JIT 编译/GC 影响后一个 → 结果污染

// ❌ @Fork(5)：太慢（每次 fork 都重新启动 JVM）

// ✅ @Fork(1~3) 是常用选择
// 生产标准：@Fork(3) 取 3 次独立 JVM 结果的平均
```

### 陷阱 5：@State 作用域选错

```java
// @State 三种作用域：
@State(Scope.Benchmark)   // 所有线程共享一个实例 ← 测试共享状态
@State(Scope.Thread)      // 每个线程一个实例 ← 测试线程私有状态
@State(Scope.Group)       // 每组一个实例

// ❌ 场景：测"多线程竞争同一计数器"
// 如果用 Scope.Thread → 每个线程各自一个计数器 → 没有竞争！
// 测出来的不是"竞争场景"的性能！

// ✅ 测竞争 → Scope.Benchmark（共享）
// ✅ 测线程私有（如 ThreadLocal）→ Scope.Thread
```

## 4. 锁竞争压测实战（🛠️ 核心场景）

### 4.1 压测目标

```
回答面试高频问题：synchronized vs ReentrantLock vs AtomicLong
在高/中/低竞争下，谁快？

结论预览（需要你自己跑验证）：
  低竞争：AtomicLong 最快（无锁）
  高竞争：synchronized 可能反超（JIT 优化 + 阻塞 vs 自旋）
  整体：差距没有想象中大，选型看功能而非性能
```

### 4.2 完整压测代码

```java
package com.sw.yang.concurrent.jmh;

import org.openjdk.jmh.annotations.*;
import org.openjdk.jmh.runner.Runner;
import org.openjdk.jmh.runner.options.Options;
import org.openjdk.jmh.runner.options.OptionsBuilder;

import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicLong;
import java.util.concurrent.locks.ReentrantLock;

/**
 * 锁竞争压测：AtomicLong vs synchronized vs ReentrantLock
 */
@BenchmarkMode(Mode.Throughput)
@OutputTimeUnit(TimeUnit.SECONDS)
@Warmup(iterations = 3, time = 1)
@Measurement(iterations = 5, time = 1)
@Fork(2)
@State(Scope.Benchmark)     // ★ 共享状态：所有线程竞争同一个计数器
public class LockBenchmark {

    private AtomicLong atomicCount = new AtomicLong(0);
    private long syncCount = 0;
    private long lockCount = 0;
    private final ReentrantLock lock = new ReentrantLock();

    @Benchmark
    public long atomicInc() {
        return atomicCount.incrementAndGet();
    }

    @Benchmark
    public synchronized long syncInc() {
        return ++syncCount;
    }

    @Benchmark
    public long lockInc() {
        lock.lock();
        try {
            return ++lockCount;
        } finally {
            lock.unlock();
        }
    }

    public static void main(String[] args) throws Exception {
        Options opt = new OptionsBuilder()
                .include(LockBenchmark.class.getSimpleName())
                .threads(8)                 // ★ 8 个线程竞争（高竞争）
                .build();
        new Runner(opt).run();
    }
}
```

### 4.3 调整竞争强度

```java
// 竞争强度的控制 = threads 参数
Options opt = new OptionsBuilder()
        .include(LockBenchmark.class.getSimpleName())
        .threads(1)     // 低竞争：单线程
        // .threads(8)  // 中竞争
        // .threads(32) // 高竞争
        .build();

// ⚠️ 注意：threads() 只能设置一次，多次链式调用是"覆盖"不是"多组"！
// 跑多组竞争强度 → 分别构建 Options，依次运行：
Options opt1 = new OptionsBuilder().include(...).threads(1).build();
Options opt2 = new OptionsBuilder().include(...).threads(8).build();
Options opt3 = new OptionsBuilder().include(...).threads(32).build();
new Runner(opt1).run();
new Runner(opt2).run();
new Runner(opt3).run();
```

## 5. @State 与 @Setup 详解

### 5.1 @Setup / @TearDown

```java
@State(Scope.Benchmark)
public class SetupBenchmark {

    private List<Integer> data;

    @Setup(Level.Trial)          // 每轮测试前执行一次
    public void init() {
        data = new ArrayList<>(1000);
        for (int i = 0; i < 1000; i++) data.add(i);
        System.out.println("初始化完成");
    }

    @TearDown(Level.Trial)
    public void cleanup() {
        System.out.println("清理完成");
    }

    @Benchmark
    public int sum() {
        int sum = 0;
        for (int i : data) sum += i;
        return sum;
    }
}

// Level 三个级别：
//   Trial：每次完整测试（预热+测量）前/后
//   Iteration：每轮迭代前/后
//   Invocation：每次方法调用前/后（极少用，开销大）
```

### 5.2 参数化（@Param）

```java
// 一次性测多组参数
@State(Scope.Benchmark)
public class ParamBenchmark {

    @Param({"10", "100", "1000"})   // 三组参数，自动生成三组结果
    private int size;

    private int[] array;

    @Setup
    public void init() {
        array = new int[size];
        for (int i = 0; i < size; i++) array[i] = i;
    }

    @Benchmark
    public long sum() {
        long sum = 0;
        for (int v : array) sum += v;
        return sum;
    }
}
```

## 6. 生产注意事项 & 常见坑点

### 🕳️ 坑 1：把 JMH 当单元测试跑

```java
// ❌ 每次构建都跑 JMH → 每次 10 分钟 → 团队烦死
// ✅ 单独 profile 或手动触发，不进 CI 常规流程
```

### 🕳️ 坑 2：测的是"共享可变状态"却没注意 @State

```java
// ❌ Scope.Thread + 共享计数器 → 每个线程独立 → 没竞争 → 测错场景
// ✅ 测竞争必须 Scope.Benchmark（共享）
```

### 🕳️ 坑 3：忽略了编译期常量

```java
// ❌ 计算结果是常量 → JIT 直接算出结果 → 测的是常量
@Benchmark
public int bad() {
    return 1 + 1;   // JIT 直接算出 2！方法体被替换为常量（常量折叠）
}

// ✅ 结果依赖运行期输入（字段，非编译期常量）
// 注意：Blackhole.consume() 返回 void，不能赋值！
@State(Scope.Benchmark)
public class GoodBenchmark {
    private int seed = 42;   // 运行期字段 → 无法常量折叠

    @Benchmark
    public int good() {
        return seed * 2;     // seed 是运行期值 → JIT 不能提前算出结果
    }
}
```

### 🕳️ 坑 4：在 Windows 上跑对比测试

```java
// ⚠️ Windows 的时钟精度/调度不如 Linux → 结果波动大
// ✅ 生产对比测试在 Linux 服务器上跑
// ✅ 测试机要"干净"：关闭其他应用、固定 CPU 频率（禁用睿频）
```

### 🕳️ 坑 5：压测结果没有保存

```java
// ✅ 结果输出到文件，方便对比历史
Options opt = new OptionsBuilder()
        .include(...)
        .result("result.json")   // 保存 JSON 结果
        .build();
// 或命令行：-rf json
```

## 7. 面试高频考点

1. **为什么普通计时测不准？JMH 解决了什么？**
   → JIT 优化（死代码消除/常量折叠）、没有预热、系统噪音、测试本身开销。JMH：预热 + 黑洞 + fork 隔离 + 统计。

2. **什么是死代码消除？Blackhole 干什么？**
   → JIT 发现结果未被使用 → 删除计算。Blackhole.consume() 模拟"结果被使用" → 阻止消除。

3. **@State 三种作用域的区别？测竞争为什么必须 Scope.Benchmark？**
   → Benchmark 共享实例 / Thread 每线程独立 / Group 每组。测竞争用 Benchmark（共享才竞争），用 Thread 就变成无竞争场景了。

4. **为什么需要预热？**
   → JVM 分层编译：解释执行 → C1 → C2。预热后 JIT 完成优化，测的是稳定态性能。

5. **Fork 是干什么的？**
   → 每个 benchmark 跑在独立 JVM 中，隔离 JIT/GC 状态，防止 benchmark 之间互相污染。

### 练习 2：锁竞争压测（60 分钟）★必做

```java
package com.sw.yang.concurrent.jmh;

import org.openjdk.jmh.annotations.*;
import org.openjdk.jmh.runner.Runner;
import org.openjdk.jmh.runner.options.Options;
import org.openjdk.jmh.runner.options.OptionsBuilder;

import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicLong;
import java.util.concurrent.locks.ReentrantLock;

/**
 * 练习 2：三种计数方案压测（AtomicLong / synchronized / ReentrantLock）
 *
 * 分别用 threads=1、8、32 跑三遍，观察竞争强度的影响
 */
@BenchmarkMode(Mode.Throughput)
@OutputTimeUnit(TimeUnit.SECONDS)
@Warmup(iterations = 3, time = 1)
@Measurement(iterations = 5, time = 1)
@Fork(1)
@State(Scope.Benchmark)
public class LockBenchmark {

    private AtomicLong atomicCount = new AtomicLong(0);
    private long syncCount = 0;
    private long lockCount = 0;
    private final ReentrantLock lock = new ReentrantLock();

    @Benchmark
    public void atomicInc(Blackhole bh) {
        bh.consume(atomicCount.incrementAndGet());
    }

    @Benchmark
    public synchronized void syncInc(Blackhole bh) {
        bh.consume(++syncCount);
    }

    @Benchmark
    public void lockInc(Blackhole bh) {
        lock.lock();
        try {
            bh.consume(++lockCount);
        } finally {
            lock.unlock();
        }
    }

    public static void main(String[] args) throws Exception {
        Options opt = new OptionsBuilder()
                .include(LockBenchmark.class.getSimpleName())
                .threads(8)          // 修改这里：1 / 8 / 32
                .result("lock-result-threads8.json")
                .build();
        new Runner(opt).run();
    }
}
```

### 练习 3：观察死代码消除（30 分钟）

```java
package com.sw.yang.concurrent.jmh;

import org.openjdk.jmh.annotations.*;
import org.openjdk.jmh.runner.Runner;
import org.openjdk.jmh.runner.options.Options;
import org.openjdk.jmh.runner.options.OptionsBuilder;

import java.util.concurrent.TimeUnit;

/**
 * 练习 3：亲眼看到死代码消除的效果
 *
 * 关键：两个方法都必须是 void！
 *   - 返回值方法会被 JMH 自动消费（不会消除）
 *   - void + 无 consume：sum 计算结果被 JIT 删除 → 吞吐量"巨大"
 *   - void + bh.consume：真实计算 → 吞吐量明显下降
 */
@BenchmarkMode(Mode.Throughput)
@OutputTimeUnit(TimeUnit.SECONDS)
@Warmup(iterations = 2, time = 1)
@Measurement(iterations = 3, time = 1)
@Fork(1)
@State(Scope.Benchmark)
public class DeadCodeBenchmark {

    @Benchmark
    public void noBlackhole() {
        long sum = 0;
        for (int i = 0; i < 1000; i++) {
            sum += i;
        }
        // sum 未被使用 → JIT 可能把整个循环删掉（死代码消除）
    }

    @Benchmark
    public void withBlackhole(Blackhole bh) {
        long sum = 0;
        for (int i = 0; i < 1000; i++) {
            sum += i;
        }
        bh.consume(sum);   // 强制使用结果 → 计算无法被消除
    }

    public static void main(String[] args) throws Exception {
        Options opt = new OptionsBuilder()
                .include(DeadCodeBenchmark.class.getSimpleName())
                .build();
        new Runner(opt).run();
        System.out.println("对比两个方法的吞吐量差异（noBlackhole 通常虚高）");
    }
}
```

## 9. 自测题

1. **为什么普通 System.currentTimeMillis 测性能不准？**
   <details><summary>答案</summary>

   JIT 优化（死代码消除/常量折叠/内联）、没有预热（类加载+分层编译）、系统噪音（GC/调度）、测试代码自身开销。
   </details>

2. **Blackhole 是干什么的？不用会怎样？**
   <details><summary>答案</summary>

   模拟"结果被使用"，阻止 JIT 死代码消除。不用 → 计算结果被优化删除 → 测的是空方法 → 结果虚高无意义。
   </details>

3. **@State 三种作用域？测竞争为什么必须 Benchmark？**
   <details><summary>答案</summary>

   Benchmark（共享）/ Thread（每线程独立）/ Group（组共享）。测竞争用 Benchmark——Scope.Thread 时每个线程有独立计数器，根本没有竞争。
   </details>

4. **为什么需要预热？不预热会怎样？**
   <details><summary>答案</summary>

   JVM 分层编译（解释 → C1 → C2），预热让 JIT 完成优化，测稳定态。不预热 → 结果包含编译开销且不稳定。
   </details>

5. **Fork 的作用？为什么默认要 >= 1？**
   <details><summary>答案</summary>

   每个 benchmark 独立 JVM，隔离 JIT/GC 状态，防止 benchmark 互相污染。Fork(0) 共享 JVM → 前一个的编译/GC 影响后一个的结果。
   </details>
