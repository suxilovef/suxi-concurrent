## 1. Java 对象内存布局

### 1.1 整体布局

```
一个 Java 对象在堆内存中的布局（64 位 JVM，默认开启压缩指针）：

┌─────────────────────────────────────────────────────┐
│                    对象头（Object Header）            │
│  ┌────────────────────────┬──────────────────────┐  │
│  │  Mark Word（8 字节）    │  Klass Pointer       │  │
│  │  存储锁状态/哈希/年龄等   │  （类型指针，4 字节）    │  │
│  └────────────────────────┴──────────────────────┘  │
├─────────────────────────────────────────────────────┤
│                   实例数据（Instance Data）            │
│  对象的实际字段（int、long、引用...）                    │
├─────────────────────────────────────────────────────┤
│                   对齐填充（Padding）                  │
│  使对象总大小是 8 的倍数（HotSpot 要求 8 字节对齐）      │
└─────────────────────────────────────────────────────┘
```

| 组成部分 | 大小（64 位 + 压缩指针） | 说明 |
|---|---|---|
| Mark Word | 8 字节 | **锁状态的核心存储位置** |
| Klass Pointer | 4 字节（压缩）/ 8 字节（不压缩） | 指向类的元数据 |
| 实例数据 | 可变 | 各字段的实际值 |
| 对齐填充 | 0~7 字节 | 凑成 8 的倍数 |

### 1.2 压缩指针（CompressedOops）

```
-XX:+UseCompressedOops（64 位默认开启）

作用：把 8 字节的引用压缩成 4 字节
效果：对象头从 16 字节减到 12 字节，堆占用更小
限制：堆超过 32GB 时无法压缩（这就是为什么大堆建议 32GB 以下）
```

> ○ 压缩指针的知识主要用于调优和面试加分，日常开发不需要关心。知道"64 位 JVM 对象头默认 12 字节"即可。

## 2. Mark Word 深度解析（核心）

### 2.1 Mark Word 是什么

> **Mark Word 是对象头中最重要的部分，它像一个"状态机"：同一个 8 字节，在不同锁状态下存不同的内容。**

```
Mark Word（64 位 JVM）在不同锁状态下的位布局：

─────────────────────────────────────────────────────────────
1. 无锁状态（normal，01）：
    [ unused:25 | identity_hashcode:31 | cms_free:1 | age:4 | biased_lock:0 | 01 ]
    ↑哈希码     ↑GC分代年龄    ↑偏向锁标志位    ↑锁标志位

2. 偏向锁状态（biased，01）：
    [ thread:54 | epoch:2 | unused:1 | age:4 | biased_lock:1 | 01 ]
    ↑偏向线程ID     ↑批量重偏向用的epoch    ↑偏向锁标志=1

3. 轻量级锁状态（thin lock，00）：
    [ ptr_to_lock_record:62 | 00 ]
    ↑指向栈帧中 Lock Record 的指针

4. 重量级锁状态（fat lock，10）：
    [ ptr_to_ObjectMonitor:62 | 10 ]
    ↑指向 ObjectMonitor 的指针

5. GC 标记状态（11）：
    [ 空指针/标记信息 | 11 ]
─────────────────────────────────────────────────────────────
```

### 2.2 关键位含义

| 位段 | 无锁 | 偏向锁 | 轻量锁 | 重量锁 |
|---|---|---|---|---|
| 锁标志位（最后 2 位） | 01 | 01 | 00 | 10 |
| 偏向锁标志（第 3 位） | 0 | **1** | — | — |
| 存储内容 | 哈希码 + 年龄 | 线程 ID + epoch + 年龄 | Lock Record 指针 | ObjectMonitor 指针 |

```
判断锁状态的规则（从低位看）：

最后 2 位 == 01 且 第 3 位 == 0 → 无锁
最后 2 位 == 01 且 第 3 位 == 1 → 偏向锁
最后 2 位 == 00 → 轻量级锁
最后 2 位 == 10 → 重量级锁
最后 2 位 == 11 → GC 标记（不可锁）
```

> ⭐⭐⭐ **面试要求：能手画出这张表，能解释每个状态存什么。**

## 3. 锁升级全链路（核心中的核心）

### 3.1 升级总览

```
              ┌───────────────────────────────────────┐
              │               无锁（01）                │
              │   hash | age | biased_lock=0 | 01     │
              └──────────────┬────────────────────────┘
                             │ 单线程访问（同一线程反复获取）
                             ▼
              ┌───────────────────────────────────────┐
              │              偏向锁（01）               │
              │   thread_id | epoch | age | 1 | 01    │
              └──────────────┬────────────────────────┘
                             │ 有其他线程竞争（CAS 替换失败）
                             ▼
              ┌───────────────────────────────────────┐
              │            轻量级锁（00）               │
              │   ptr_to_LockRecord | 00              │
              └──────────────┬────────────────────────┘
                             │ 竞争加剧（自旋超限/有线程等待）
                             ▼
              ┌───────────────────────────────────────┐
              │            重量级锁（10）               │
              │   ptr_to_ObjectMonitor | 10           │
              └───────────────────────────────────────┘

注意：锁只能升级，不能降级（除 GC 时 Mark Word 会恢复无锁位）
```

### 3.2 为什么需要锁升级？

```
初衷：大多数同步代码在运行时，"竞争"远没有想象中激烈：
  - 单线程执行（如早期的单核、无竞争的代码）→ 用重量级锁太浪费
  - 多线程但交错执行 → 竞争窗口极短

→ 设计分级：
  低成本的无锁/偏向锁处理低竞争 → 只有当竞争真正发生才升级
  → 这就是"越级使用重量级锁"被淘汰的原因
```

### 3.3 偏向锁（Biased Locking）

**适用场景**：**同一线程**反复获取同一把锁（无竞争）。

```
获取过程（第一次进入）：

1. 检查 Mark Word 是否为"可偏向状态"（biased_lock=1 且 thread_id 为空）
2. 如果是 → CAS 将线程 ID 写入 Mark Word 的 thread 位段
3. CAS 成功 → 当前线程获得偏向锁，以后无需任何 CAS/锁操作，直接进入
4. CAS 失败（说明有其他线程获得过偏向锁）→ 触发偏向锁撤销

后续进入（持有偏向锁的线程再次进入）：
  1. 检查 thread_id == 当前线程？
  2. 是 → 直接进入（零开销！这就是偏向锁的意义）
  3. 否 → 撤销
```

**图解**：

```
线程 A 第一次进入：                   线程 A 后续进入：
┌──────────────────────────┐      ┌──────────────────────────┐
│ Mark Word: biased=1      │      │ Mark Word: thread=A       │
│ thread_id = (空)         │      │ 检查 thread_id == A?      │
│ CAS(thread_id, A)        │      │ 是 → 直接进入（零开销）     │
└──────────────────────────┘      └──────────────────────────┘
```

**偏向锁撤销（Revoke）—— 昂贵操作**：

```
当线程 B 访问被线程 A 偏向锁定的对象：

1. 线程 B 尝试 CAS 替换 thread_id → 失败（因为已有 A）
2. 触发"偏向锁撤销"
3. 撤销需要在全局安全点（SafePoint）执行 ← 所有线程都要停下来！
4. 撤销时：
   - 检查线程 A 是否还活着
   - 若 A 已退出临界区 → 将 Mark Word 恢复为无锁状态
   - 若 A 仍在临界区 → 升级为轻量级锁（对象被"移交"给 A）
5. 撤销完成后，线程 B 重新走"无锁 → 轻量级锁"流程

→ 撤销一次偏向锁的代价 ≈ 一次 STW（Stop The World）级别的操作
→ 这也是 JDK 15 默认禁用偏向锁、JDK 21 彻底废弃的原因之一
```

**偏向锁延迟启动**：

```
JVM 参数：-XX:BiasedLockingStartupDelay（默认 4000ms）

原因：JVM 启动时大量类加载，对象的哈希码/年龄等信息需要初始化，
     启动 4 秒内先不用偏向锁（避免无意义的撤销）

→ 所以"刚启动就打印 Mark Word"看到的是无锁状态，4 秒后才是可偏向
```

**批量重偏向 / 批量撤销（◈◈ 了解）**：

```
批量重偏向（Bulk Rebias）：
  当同一类的大量对象频繁撤销偏向锁 → 将 epoch +1，让旧的偏向全部失效
  一次操作解决"一个类所有对象的偏向状态"，而不是逐个撤销

批量撤销（Bulk Revoke）：
  当批量重偏向后仍然频繁撤销 → 关闭整个类的偏向功能

触发阈值：对象数 > 20（重偏向），撤销次数 > 40（撤销）
```

### 3.4 轻量级锁（Thin Lock）

**适用场景**：多线程交替访问（竞争窗口极短，如"线程 A 用完线程 B 立刻用"）。

```
获取过程：

1. 如果对象处于无锁/可偏向状态（但禁用偏向）→ 线程在栈帧中创建 Lock Record
2. Lock Record 中保存 Mark Word 的副本（Displaced Mark Word）
3. CAS 将对象 Mark Word 中的指针替换为指向 Lock Record
4. CAS 成功 → 持有轻量级锁
5. CAS 失败 → 表示有竞争 → 膨胀为重量级锁

释放过程：
1. CAS 将 Mark Word 恢复为 Displaced Mark Word
2. 恢复成功 → 释放完成
3. 恢复失败（说明已经膨胀）→ 走重量级锁的释放流程
```

**图解**：

```
线程 A 的栈帧：                   对象 Mark Word：
┌──────────────────┐      ┌────────────────────────┐
│ Lock Record       │      │ [ptr_to_LockRecord]|00 │
│  Displaced Mark   │ ←─── │  （指向线程 A 的 Lock Record）│
│  Word（原Mark副本）│      └────────────────────────┘
└──────────────────┘
```

**自旋（Spin Lock）**：

```
轻量级锁获取失败后，线程不会立刻阻塞，而是自旋等待：
  while (Mark Word != 指向我的 Lock Record) {
      // 空转，等待持有者释放
  }

自旋的意义：
  如果持有者很快释放锁 → 自旋等待比阻塞+唤醒更快
  自旋的代价：占用 CPU 时间片（忙等）

自适应自旋（Adaptive Spinning，JDK 6+）：
  JVM 根据历史情况动态调整自旋次数：
  - 上次自旋成功 → 增加自旋次数
  - 上次自旋失败 → 减少自旋次数甚至不自旋
```

### 3.5 重量级锁（Fat Lock）

**适用场景**：竞争激烈（多个线程长期竞争）。

```
膨胀过程（从轻量级锁升级）：

1. 线程 B 自旋失败（或发现已有重量级锁）
2. 分配并初始化 ObjectMonitor 对象
3. 将 Mark Word 指针替换为指向 ObjectMonitor
4. 线程 B 进入 ObjectMonitor 的 _EntryList 等待队列
5. 线程 B 挂起（进入内核态阻塞）
```

**ObjectMonitor 数据结构**：

```
ObjectMonitor（HotSpot 内部结构）：
┌──────────────────────────────┐
│ _owner: Thread*               │  ← 持有锁的线程
│ _recursions: int              │  ← 重入计数
│ _EntryList: ObjectWaiter*     │  ← 等待获取锁的线程队列
│ _WaitSet: ObjectWaiter*       │  ← 调用了 wait() 的线程队列
│ _count: int                   │
│ _cxq: ...                     │  ← 竞争队列（自旋失败的进入）
└──────────────────────────────┘

Owner 获取锁流程：
  Thread 自旋 → CAS _count → 进入 _cxq → 移到 _EntryList → park() 挂起
  被唤醒 → 从 _EntryList 取出 → 成为 _owner

Owner 释放锁流程：
  _owner = null → 唤醒 _EntryList 中一个线程 → 该线程 CAS 抢锁
```

**重量级锁的开销**：

```
阻塞/唤醒一个线程 = 内核态操作：
  线程挂起 → 用户态→内核态切换 → 内核调度 → 线程恢复 → 内核态→用户态
  → 每次上下文切换约 1~10 微秒（纳秒级指令相比是天文数字）

这就是"重量级锁为什么重"的根本原因
```

### 3.6 锁升级触发条件汇总

| 状态 → 状态 | 触发条件 | 代价 |
|---|---|---|
| 无锁 → 偏向锁 | 第一次获取锁（偏向功能开启时） | 一次 CAS |
| 偏向锁 → 偏向锁 | 同一线程再次获取 | 0（直接检查 thread_id） |
| 偏向锁 → 无锁 | 偏向线程退出临界区 + 被其他线程竞争 | SafePoint 撤销（昂贵） |
| 偏向锁 → 轻量级锁 | 偏向线程仍在临界区，其他线程竞争 | SafePoint 撤销 + CAS |
| 无锁 → 轻量级锁 | 偏向关闭或已撤销，单线程获取 | 一次 CAS |
| 轻量级锁 → 重量级锁 | CAS 失败 + 自旋超限 或 有线程等待 | 对象膨胀 |
| 重量级锁 | 竞争激烈时长期保持 | 每次获取/释放都有内核态切换 |

## 4. JOL 实操：亲眼看到锁状态

### 4.1 引入依赖

```xml
<dependency>
    <groupId>org.openjdk.jol</groupId>
    <artifactId>jol-core</artifactId>
    <version>0.17</version>
    <scope>test</scope>
</dependency>
```

### 4.2 核心代码

```java
package com.sw.yang.concurrent.sync;

import org.openjdk.jol.info.ClassLayout;
import org.junit.jupiter.api.Test;

/**
 * 练习：使用 JOL 观察锁状态变化
 */
public class JolLockDemo {

    private static final class LockObject {
        // 空对象，只有对象头
    }

    @Test
    public void testLockStates() throws InterruptedException {
        LockObject obj = new LockObject();

        System.out.println("=== 1. 无锁状态 ===");
        System.out.println(ClassLayout.parseInstance(obj).toPrintable());

        // 重点看最后一行：
        // 01 00 00 00 ... 00  → 最后 2 位 01，第 3 位 0 → 无锁
        // 有 hash 值（01 后面 31 位）→ 对象已调用 hashCode()

        // 注意：JVM 启动默认 4 秒后才有偏向锁，测试需要先等待
        Thread.sleep(4000);
        System.out.println("=== 2. 偏向锁状态（等待 4 秒后）===");
        System.out.println(ClassLayout.parseInstance(obj).toPrintable());
        // 期望看到：第 3 位 = 1（biased_lock=1），线程 ID 位段为空

        // 使用偏向锁
        synchronized (obj) {
            System.out.println("=== 3. 已获取锁（偏向锁）===");
            System.out.println(ClassLayout.parseInstance(obj).toPrintable());
            // 期望看到：thread 位段 = 当前线程 ID
        }
    }
}
```

### 4.3 JOL 输出解读

```
无锁：     00000000 00000000 ... 00000001
          ← unused + hash + age + [0] + [01]

偏向锁：   00000000 00000000 ... 00000101
          ← thread(空) + epoch + age + [1] + [01]

轻量级锁： 00000000 00000000 ... 00110000
          ← ptr_to_LockRecord + [00]

重量级锁： 00000000 00000000 ... 00010010
          ← ptr_to_ObjectMonitor + [10]
```

> 输出是**小端序**，最右边的是低位字节，判断锁状态看最后两位。

## 5. JIT 编译器对锁的优化

### 5.1 锁消除（Lock Elimination）

```
场景：JIT 通过逃逸分析发现"对象不会逃逸出当前线程/方法" → 同步可以去掉

典型例子：
  StringBuffer sb = new StringBuffer();
  sb.append("a");   // append 是 synchronized 的
  sb.append("b");
  String s = sb.toString();

  JIT 分析：sb 没有逃逸出当前方法 → 不需要加锁 → 消除所有 synchronized
  → 所以单线程用 StringBuffer 也不会慢（当然直接用 StringBuilder 更好）
```

### 5.2 锁粗化（Lock Coarsening）

```
场景：同一对象连续多次加锁/解锁 → 合并为一个大锁块

典型例子：
  for (int i = 0; i < 100; i++) {
      synchronized (lock) {   // 100 次加锁/解锁
          doSomething();
      }
  }

  JIT 优化为：
  synchronized (lock) {        // 一次加锁
      for (int i = 0; i < 100; i++) {
          doSomething();
      }
  }
  // 但注意：锁粗化后锁持有时间变长，高竞争场景反而不利
```

### 5.3 逃逸分析（Escape Analysis）

```
JIT 的逃逸分析判断对象能否逃逸出方法：

-XX:+DoEscapeAnalysis（JDK 6u23+ 默认开启）

三种逃逸状态：
  不逃逸 → 栈上分配（对象不进入堆，GC 都不用管）
  方法逃逸 → 被其他方法引用，但不被线程共享
  线程逃逸 → 被其他线程访问（必须用同步）

相关优化：
  栈上分配 + 标量替换（把对象拆成多个变量）
  锁消除（依赖逃逸分析）
```

## 6. 偏向锁的"生前身后"：JDK 15 的抉择

| JDK 版本 | 偏向锁状态 |
|---|---|
| JDK 6~14 | 默认开启 |
| JDK 15 | **默认禁用**（`-XX:+UseBiasedLocking` 开启） |
| JDK 21 | **完全移除**（相关代码被删除） |

```
为什么放弃偏向锁？

1. 撤销成本高：撤销需要在 SafePoint 暂停所有线程（STW 级别）
2. 收益变小：现代应用普遍多线程竞争，偏向锁命中率下降
3. 维护复杂：与 JIT/GC 的交互导致大量边缘 bug
4. 硬件进步：CAS 成本下降，无锁方案（LongAdder 等）性能更好

→ 你用的 Java 17 默认没有偏向锁！JDK 8 有！
→ 学习锁升级时要区分版本：JDK 8 是"四态升级"，JDK 17 是"三态升级"
```

```
Java 17 的锁升级路径：

无锁（01）→ 轻量级锁（00）→ 重量级锁（10）
（没有偏向锁这一级）

Java 8 的锁升级路径：

无锁（01）→ 偏向锁（01）→ 轻量级锁（00）→ 重量级锁（10）
```

> ⚠️ **面试关键**：一定要说清楚你讲的是哪个 JDK 版本。JDK 15+ 默认无偏向锁，这是 2020 年之后的新知识，很多旧资料还在讲"四态"。

## 7. 生产注意事项 & 常见坑点

### 🕳️ 坑 1：调用 hashCode() 会让偏向锁失效

```java
// 对象一旦调用了 hashCode()，Mark Word 中要存储 hash 值
// → 没有空间存线程 ID → 该对象永远无法进入偏向锁状态
obj.hashCode();  // 之后这个对象最多只能到轻量级锁

// 规律：hash 和 偏向线程 ID 互斥！存了 hash 就不能偏向
```

### 🕳️ 坑 2：重写 hashCode 会让 hash 提前占用 Mark Word

```java
// 如果类重写了 hashCode()，每次 new 都会调用 → 对象刚创建就"用完"了
// 偏向锁位段被清空 → 所有实例都走"无锁 → 轻量级锁"
// （所以实际开发中很多对象其实进不了偏向锁）
```

### 🕳️ 坑 3：wait/notify 只能用于重量级锁

```java
synchronized (obj) {
    obj.wait();  // 调用 wait 时，锁会自动升级为重量级锁
    // 因为 wait 需要 ObjectMonitor 的 _WaitSet 结构！
}
// 也就是说：wait/notify 触发的膨胀是不可逆的
```

### 🕳️ 坑 4：锁粗化在高竞争场景适得其反

```java
// 低竞争：锁粗化收益大（减少加锁解锁次数）
// 高竞争：锁粗化让持有时间变长 → 更多线程等待 → 反而变慢
// 结论：不要过度依赖 JIT 优化，代码层面就应写合适的锁粒度
```

### 🕳️ 坑 5：认为"锁只能升级不能降级"是绝对的

```java
// 常规情况下锁只能升级不能降级（JVM 规范层面）
// 但注意：
// 1. GC 时对象在 SafePoint 上会短暂恢复到无锁状态（回收后）
// 2. 偏向锁被撤销时，如果原线程已退出临界区 → 会恢复到无锁
// 3. JDK 15 后根本没有偏向锁
```

/**
 * 练习 1：用 JOL 观察无锁 / 偏向锁 / 轻量级锁 / 重量级锁
 *

    private static final class LockObject {
    }

    @Test
    public void testLockStates() throws InterruptedException {
        LockObject obj = new LockObject();

        System.out.println("=== 1. 无锁状态（刚创建）===");
        System.out.println(ClassLayout.parseInstance(obj).toPrintable());
        // 观察：最后 2 位是 01，第 3 位是 0 → 无锁

        // 等待偏向锁延迟结束（默认 4 秒）
        Thread.sleep(4000);

        System.out.println("=== 2. 等待 4 秒后（可偏向但未偏向）===");
        System.out.println(ClassLayout.parseInstance(obj).toPrintable());
        // 观察：第 3 位变为 1 → 可偏向

        System.out.println("=== 3. 获取锁后（偏向锁）===");
        synchronized (obj) {
            System.out.println(ClassLayout.parseInstance(obj).toPrintable());
            // 观察：thread 位段有值 → 偏向锁
        }

        System.out.println("=== 4. 释放锁后 ===");
        System.out.println(ClassLayout.parseInstance(obj).toPrintable());
        // 观察：偏向锁保留（不是无锁！）→ 同一线程下次进入零开销
    }

    @Test
    public void testHashCodeKillsBiasing() throws InterruptedException {
        LockObject obj = new LockObject();
        Thread.sleep(4000); // 等待偏向锁就绪

        System.out.println("=== 调用 hashCode 之前 ===");
        System.out.println(ClassLayout.parseInstance(obj).toPrintable());

        obj.hashCode(); // 关键操作！

        System.out.println("=== 调用 hashCode 之后 ===");
        System.out.println(ClassLayout.parseInstance(obj).toPrintable());
        // 观察：biased_lock 位变为 0，且不再可能进入偏向锁
    }
}

## 10. 自测题

1. **Mark Word 在不同锁状态下存储的内容分别是什么？**
   <details><summary>答案</summary>

   无锁：hash + age + biased=0 + 01
   偏向：thread_id + epoch + age + biased=1 + 01
   轻量：指向 Lock Record 的指针 + 00
   重量：指向 ObjectMonitor 的指针 + 10
   GC：标记信息 + 11
   </details>

2. **为什么偏向锁撤销很昂贵？**
   <details><summary>答案</summary>

   撤销需要在 SafePoint 执行——所有线程都必须停在这个安全点。加上撤销过程中要判断原线程状态（是否存活、是否在临界区），一次撤销 ≈ 一次 STW 级操作。这就是 JDK 15 禁用偏向锁的原因之一。
   </details>

3. **Java 17 和 Java 8 的锁升级路径有什么区别？**
   <details><summary>答案</summary>

   JDK 8：无锁 → 偏向锁 → 轻量级锁 → 重量级锁（四态）
   JDK 17：无锁 → 轻量级锁 → 重量级锁（三态，JDK 15 起默认禁用偏向锁）
   </details>

4. **轻量级锁和重量级锁各自解决什么问题？开销区别在哪？**
   <details><summary>答案</summary>

   轻量级：解决"竞争窗口极短"的场景，用 CAS + 自旋避免内核态切换；
   重量级：解决"竞争激烈"的场景，用 ObjectMonitor 管理等待队列；
   开销：轻量级全程用户态（微秒内），重量级有上下文切换（微秒到毫秒级）。
   </details>

5. **调用对象的 hashCode() 之后，为什么不能进入偏向锁？**
   <details><summary>答案</summary>

   Mark Word 是共享存储：偏向锁需要 54 位存线程 ID，hash 需要 31 位存哈希码。两者互斥，hashCode() 一旦被调用（存入 Mark Word），该对象就无法进入偏向状态，只能走轻量级锁路径。
   </details>
