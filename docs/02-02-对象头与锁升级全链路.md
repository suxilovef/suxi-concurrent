## 第一章 对象头：8 字节承载什么

### 1.1 对象内存布局

```
一个 Java 对象在堆内存中的布局（64 位 JVM，默认开启压缩指针）：

┌─────────────────────────────────────────────────────┐
│                    对象头（Object Header）            │
│  ┌────────────────────────┬──────────────────────┐  │
│  │  Mark Word（8 字节）    │  Klass Pointer       │  │
│  │  存储锁状态/哈希/年龄等   │  （类型指针，4 字节）    │  │
│  └────────────────────────┴──────────────────────┘  │
├─────────────────────────────────────────────────────┤
│                   实例数据（Instance Data）            │
│  对象的实际字段（int、long、引用...）                    │
├─────────────────────────────────────────────────────┤
│                   对齐填充（Padding）                  │
│  使对象总大小是 8 的倍数（HotSpot 要求 8 字节对齐）      │
└─────────────────────────────────────────────────────┘
```

| 组成部分 | 大小（64 位 + 压缩指针） | 说明 |
|---|---|---|
| Mark Word | 8 字节 | **锁状态的核心存储位置** |
| Klass Pointer | 4 字节（压缩）/ 8 字节（不压缩） | 指向类的元数据 |
| 实例数据 | 可变 | 各字段的实际值 |
| 对齐填充 | 0~7 字节 | 凑成 8 的倍数 |

### 1.2 Mark Word 五种读法

> **Mark Word 是对象头中最重要的部分，它像一个"状态机"：同一个 8 字节，在不同锁状态下存不同的内容。**

```
Mark Word（64 位 JVM）在不同锁状态下的位布局：

─────────────────────────────────────────────────────────────
1. 无锁状态（normal，01）：
    [ unused:25 | identity_hashcode:31 | cms_free:1 | age:4 | biased_lock:0 | 01 ]
    ↑哈希码     ↑GC分代年龄    ↑偏向锁标志位    ↑锁标志位

2. 偏向锁状态（biased，01）：
    [ thread:54 | epoch:2 | unused:1 | age:4 | biased_lock:1 | 01 ]
    ↑偏向线程ID     ↑批量重偏向用的epoch    ↑偏向锁标志=1

3. 轻量级锁状态（thin lock，00）：
    [ ptr_to_lock_record:62 | 00 ]
    ↑指向栈帧中 Lock Record 的指针

4. 重量级锁状态（fat lock，10）：
    [ ptr_to_ObjectMonitor:62 | 10 ]
    ↑指向 ObjectMonitor 的指针

5. GC 标记状态（11）：
    [ 空指针/标记信息 | 11 ]
─────────────────────────────────────────────────────────────
```

**怎么读这张表（新手友好版）**：

```
1. 每行是一个 64 位二进制数，从左到右是 bit63 → bit0（高位到低位），
   每个「名字:位数」是一段位域（bit field）
2. 最后 2 位 lock 是「状态标签」——JVM 每次先看它，决定其余位怎么解读
3. 每行的位数加起来都是 64：
   - 无锁：25 + 31 + 1 + 4 + 1 + 2 = 64
   - 偏向：54 + 2 + 1 + 4 + 1 + 2 = 64
   - 轻量/重量：62 + 2 = 64
```

**各字段含义**：

| 位段 | 位数 | 含义 |
|---|---|---|
| `lock` | 2 | 状态标签：01 普通对象、00 轻量锁、10 重量锁、11 GC 标记 |
| `unused` | 25（无锁）/ 1（偏向） | 保留位，恒为 0，给未来扩展或对齐用 |
| `identity_hashcode` | 31 | 对象身份哈希（Object.hashCode() / System.identityHashCode() 的值），懒计算：第一次真正调用才生成写入 |
| `cms_free` | 1 | 历史遗留位（CMS 时代用过），现代 JVM 基本闲置，当 unused 理解即可 |
| `age` | 4 | GC 分代年龄 0~15，每熬过一次 Minor GC +1，到阈值晋升老年代 |
| `biased_lock` | 1 | 第 3 位，是否偏向锁模式（配合 01 细分用） |
| `thread` | 54 | 偏向锁记录的「偏爱线程」（存线程指针） |
| `epoch` | 2 | 批量重偏向用的代次，让一批旧偏向一次性失效 |
| `ptr_to_lock_record` | 62 | 轻量级锁：指向线程栈上 Lock Record 的指针（低 2 位让给 lock 标签） |
| `ptr_to_ObjectMonitor` | 62 | 重量级锁：指向堆上 ObjectMonitor 的指针（低 2 位让给 lock 标签） |
| GC 标记信息 | 62 | lock=11 时整块交给 GC 使用，存放标记信息，不参与锁状态 |

**JVM 的实际判定规则**：

```
读 8 字节 → 看最后 2 位：
  00 → 轻量级锁，其余 62 位 = 指向线程栈上 Lock Record 的指针
  10 → 重量级锁，其余 62 位 = 指向堆上 ObjectMonitor 的指针
  11 → 正在被 GC 标记
  01 → 再看第 3 位 biased_lock：
         0 → 无锁（存 hash + 年龄）
         1 → 偏向锁（存线程 ID + epoch + 年龄）
```

### 1.3 为什么能这么设计

**核心思想**：

```
1. 同一个 8 字节，五种解读——类似 C 语言的 union，加锁不增加对象大小
2. tagged pointer 技巧：Lock Record / ObjectMonitor 指针都按 8 字节对齐，
   低 2 位本来就是 0 → 「62 位指针 + 2 位标签」不丢指针精度
3. 各状态把空间让给当下最需要的东西：
   - 无锁：没人竞争 → 存对象基本信息（hash + 年龄）
   - 偏向：同一线程反复进出 → 存「谁偏爱了它」（线程 ID + epoch），换来零开销进入
   - 轻量：出现竞争 → 指向线程栈上的 Lock Record（详细账本搬到栈上）
   - 重量：竞争激烈 → 指向堆上的 ObjectMonitor（owner、等待队列都在这）
   - GC：整块给 GC 用
4. hash 和偏向互斥的根源：31 位 hash 和 54 位线程 ID 抢的是同一块存储
```

> 📌 **实测对照（JDK 21 + JOL 0.17）见 §4.3** —— 含 `new Object()` 与调 `hashCode()` 后的 Mark Word 原始值，以及 JDK 8 上「先 new 再 sleep」vs「先 sleep 再 new」的关键对照（这一步顺序搞反就永远看不到偏向位）。

### 1.4 关键位速查

| 位段 | 无锁 | 偏向锁 | 轻量锁 | 重量锁 |
|---|---|---|---|---|
| 锁标志位（最后 2 位） | 01 | 01 | 00 | 10 |
| 偏向锁标志（第 3 位） | 0 | **1** | — | — |
| 存储内容 | 哈希码 + 年龄 | 线程 ID + epoch + 年龄 | Lock Record 指针 | ObjectMonitor 指针 |

```
判断锁状态的规则（从低位看）：

最后 2 位 == 01 且 第 3 位 == 0 → 无锁
最后 2 位 == 01 且 第 3 位 == 1 → 偏向锁
最后 2 位 == 00 → 轻量级锁
最后 2 位 == 10 → 重量级锁
最后 2 位 == 11 → GC 标记（不可锁）
```

> ⭐⭐⭐ **面试要求：能手画出这张表，能解释每个状态存什么。**

### 1.5 压缩指针（CompressedOops）

```
-XX:+UseCompressedOops（64 位默认开启）

作用：把 8 字节的引用压缩成 4 字节
效果：对象头从 16 字节减到 12 字节，堆占用更小
限制：堆超过 32GB 时无法压缩（这就是为什么大堆建议 32GB 以下）
```

> ○ 压缩指针主要用于调优和面试加分，日常开发不需要关心。知道"64 位 JVM 对象头默认 12 字节"即可。

## 第二章 锁升级：按竞争程度分档定价

### 2.1 为什么需要分级

```
初衷：大多数同步代码在运行时，"竞争"远没有想象中激烈：
  - 单线程执行（如早期的单核、无竞争的代码）→ 用重量级锁太浪费
  - 多线程但交错执行 → 竞争窗口极短

→ 设计分级：
  低成本的无锁/偏向锁处理低竞争 → 只有当竞争真正发生才升级
  → 这就是"越级使用重量级锁"被淘汰的原因
```

### 2.2 链路总览与触发条件

```
              ┌───────────────────────────────────────┐
              │               无锁（01）                │
              │   hash | age | biased_lock=0 | 01     │
              └──────────────┬────────────────────────┘
                             │ 单线程访问（同一线程反复获取）
                             ▼
              ┌───────────────────────────────────────┐
              │              偏向锁（01）               │
              │   thread_id | epoch | age | 1 | 01    │
              └──────────────┬────────────────────────┘
                             │ 有其他线程竞争（CAS 替换失败）
                             ▼
              ┌───────────────────────────────────────┐
              │            轻量级锁（00）               │
              │   ptr_to_LockRecord | 00              │
              └──────────────┬────────────────────────┘
                             │ 检测到竞争（CAS 失败）即膨胀
                             ▼
              ┌───────────────────────────────────────┐
              │            重量级锁（10）               │
              │   ptr_to_ObjectMonitor | 10           │
              └───────────────────────────────────────┘

注意：锁只能升级，不能降级。例外与补充：
- GC 标记时 Mark Word 临时进入 11 状态（暂存标记信息），不参与锁状态
- 偏向锁被撤销会落到"不可偏向"（0x01，见 §2.3）——那是撤销，不是主动降级
- 偏向开启时新对象"出生即可偏向"（biased=1、thread=空），
  首次加锁只是写 thread ID，并非从 biased=0 的无锁"升级"而来（见 §2.3）
- 【真正的降级】空闲 monitor 会被安全点回收（deflate），对象头恢复成无锁
  → "不降级"指**持有者不主动降级**，不是"对象永远停在重量级锁"（见第六章坑 5）

⚠️ 这张图是「结果的状态」的串法，**不是因果链**——真实因果是下一节按「读到的位」分流的。
```

**触发条件汇总**（面试最该默写出来的东西）

> ⚠️ **别按"状态 → 状态 → 触发条件"记这张表**——那样记必然乱。
> 真相是：**加锁只有一个事件**（某个线程尝试获取锁），去向完全由
> 「**它当场读到的 Mark Word**」决定。所以下面按**读到的位**索引。

#### 表 A：一次「加锁尝试」的去向

| 读到的 Mark Word | 结果 | 代价 |
|---|---|---|
| `lock=00`（已是 thin）或 `lock=01, biased=0`（不可偏向） | CAS 写 Lock Record 指针 → **轻量级锁**；CAS 失败 → 膨胀 → 重量级锁 | 一次 CAS / 膨胀 |
| `lock=01, biased=1, thread=空`（匿名偏向） | CAS 写 `thread=我` → **偏向锁** | 一次 CAS |
| `lock=01, biased=1, thread=我` | **不变**，一个字节都不写 → 偏向锁 | 0（一次读 + 比较） |
| `lock=01, biased=1, thread=A`，epoch **一致**，**A 已死** | 直接改写 → **不可偏向**（`0x01`） | 便宜 |
| `lock=01, biased=1, thread=A`，epoch **一致**，A 存活且**不在**临界区 | SafePoint 停住 A 后改写 → **不可偏向**（`0x01`） | STW 级 |
| `lock=01, biased=1, thread=A`，epoch **一致**，A 存活且**在**临界区 | 膨胀，`owner` 记成 A → **重量级锁**（对象被"移交"给 A） | 膨胀 |
| `lock=01, biased=1, thread=A`，epoch **已过期** | CAS 改成我 → **偏向锁**（换人） | 一次 CAS |
| `lock=10` | 走重量级锁的竞争流程 | 内核态 |

> 📌 中间六行是**同一个事件**（线程 B 访问被 A 偏向的对象），去向由三个谓词逐层分出：
> **epoch 是否有效** → **A 是否存活** → **A 是否在临界区**。
> 这才是「偏向锁为什么贵」的完整分叉——不是"有竞争就撤销"一句话能概括的。
> （三个谓词的因果见 §2.3；"撤销为什么必须停 SafePoint"见 §3.1）

#### 表 B：释放 / 重入 / wait / 回收

| 事件 | 结果 | 代价 |
|---|---|---|
| 释放轻量级锁，CAS 还回 Displaced Mark Word **成功** | **无锁**（hash/age 归还对象头） | 一次 CAS |
| 释放轻量级锁，CAS 还回**失败**（说明已膨胀） | 转走重量级锁的释放流程 | — |
| 重入轻量级锁 | 新建 Lock Record，但**不存** Displaced Mark Word（只标记"我已持有"） | 一次 CAS |
| 调用 `wait()` / `wait(ms)` | **强制膨胀**成重量级锁——`wait` 需要 `_WaitSet`（见第六章坑 3） | 膨胀（不可逆） |
| 最后一个线程退出、锁池空 | monitor 变为**空闲** | — |
| 空闲 monitor 在安全点被**回收**（deflate） | 对象头恢复成**无锁**（hash 保留） | 安全点批量做 |

> 📌 表 B 最后两行是「锁只能升级不能降级」的**真正例外**：HotSpot 会在安全点回收空闲的
> monitor（`deflate_idle_monitors`）。所以"不降级"的准确含义是
> **持有者不会主动降级**，而不是"对象永远停在重量级锁"（见第六章坑 5）。

### 2.3 偏向锁（Biased Locking）

**适用场景**：**同一线程**反复获取同一把锁（无竞争）。

> 前提：偏向开启时，**新对象出生即"可偏向"**（biased_lock=1、thread=空），
> 所以"夺取偏向"这一步通常直接命中；真正的"无锁 biased=0"只出现在
> 延迟期内出生的对象 / 算过 hash / 撤销后 / JDK15+。
>
> ⚠️ **顺序有讲究**：偏向位是 `new` 那一刻由**类原型头**盖上去的，
> 所以"等延迟"必须等**在 `new` 之前**；`new` 出来之后再等，Mark Word 不会自己变（实测见 §4.2）。
> （延迟本身 JDK 8 是 4000ms，JDK 15+ 默认已是 0 —— 见 §4.1 的版本对照表）

**获取过程：只有一条路径——读一次 Mark Word，按 thread 位段的当前值三岔**

```
读 Mark Word（前提：biased_lock == 1）
│
├─ thread == 空（匿名偏向）→ 重偏向：这是条没人认领的记录，直接 CAS 改成我
│                            ├─ 成功 → 拿到偏向锁
│                            └─ 失败 → 有别的线程在抢，重读后回到本判断
├─ thread == 当前线程      → 直接进入，一个字节都不写  ← 这就是"后续进入"
└─ thread == 别的线程      → 这条偏向记录还有效吗？——看 epoch
                             ├─ epoch 与类的当前 epoch 一致 → 有效 → **撤销**
                             │    必须问"A 在不在临界区"：死活判断 → 活则 SafePoint
                             └─ epoch 已过期（批量重偏接触发过）→ 已作废 → **重偏向**
                                  直接 CAS 改成我，不用问 A 的状态
```

> 📌 **为什么分界线是 epoch（而不是"别的什么条件"）——见 §3.2。**

**"第一次进入"和"第 n 次进入"不是两条代码分支**，而是上面同一条路径读到的**两种状态**——
"第一次"是**线程的历史**，不是对象的属性。对象里没有计数器，也不可能有：

```
想记录"这是第几次" → 每次进入都得往 Mark Word 写一笔（且 54 位 thread 位段已占满，没地方放）
而偏向锁的全部意义 → 稳态进出临界区「零共享写」（见下面"第一性原理"）
→ "零写入"和"能计数"物理互斥，偏向锁选了前者
```

对象唯一记得、也只在**状态改变的那一次**记的，是"**谁**"。稳态进入连"我来过"都不留痕：

> 📌 **实测证据见 §4.4**：同一对象在 JDK 8（偏向锁）与 JDK 17（三态）下进出的 Mark Word 逐位对照。
> 那是「偏向锁为什么不能计数」的直接证据：**要计数就得写，写了就不是偏向锁了**。

**偏向锁撤销（Revoke）—— 昂贵操作**：

```
当线程 B 访问被线程 A 偏向锁定的对象：

1. 线程 B 读到 thread 位段**既不是空、也不是自己** → 判定"已偏向别人"
   （注意：依据是这一次**普通读**，不是"CAS 失败"；CAS 失败只说明"我读到的 mark 在 CAS 前被改了"，
     重读后仍回到同一个判断）
2. 先看 epoch：只有**记录仍有效**（epoch 与类的当前 epoch 一致）才走到这里；
   epoch 已过期则走上面的"重偏向"快路径，压根不会撤销
3. 先判断线程 A 是否还存活——这决定撤销的代价：
   - A 已终止 → 它不可能再碰这个对象 → 直接改写 Mark Word，无需停下任何人（便宜）
   - A 仍存活 → 必须让 A 在全局安全点（SafePoint）停下才能安全改写
     ← 所有线程都要暂停，这才付出 STW 级别的代价
4. 撤销时：
   - 若 A 已退出临界区 → Mark Word 置成**不可偏向**（biased_lock=0，0x…01）
     ⚠️ **不是"回到匿名可偏向"**（实测，JDK 8，A 已死 / A 存活两种场景都实测过）：
     ```
     撤销前（A 偏向） 0x0000022800218805  偏向锁 thread=0x8a000862
     B 持锁中         0x0000003c0ffff2f8  轻量级锁（不是 biased:B！）
     B 释放后         0x0000000000000001  不可偏向 ← 撤销后的落点
     ```
     也就是说 **biased_lock 被清 0，这个对象永久失去偏向资格**——和第六章坑 1 里
     "算过 hash"是同一个机制。撤销的代价除了 STW，还有"回收掉这个对象的偏向能力"
     （这正是 JVM 要发明批量重偏向、而不是让每个对象都被撤销掉的原因，见下文）
   - 若 A 仍在临界区 → 膨胀成重量级锁，owner 记成 A（对象被"移交"给 A）
5. 撤销完成后，线程 B 走**轻量级锁**流程（实测 `lock=00`）——
   不存在"撤销完顺手把偏向给 B"，因为对象已经被置成不可偏向了

→ 撤销的代价取决于 A 是否存活：A 已死则便宜，A 活着才 ≈ 一次 STW（Stop The World）
→ 这也是 JDK 15 默认禁用偏向锁、JDK 18 彻底移除的原因之一
```

> 📌 **为什么撤销必须让持有线程停在 SafePoint——第一性原理在 §3.1**（含「读 / CAS / flag 都解决不了」的三条反证）。

**偏向锁延迟启动**：

```
JVM 参数：-XX:BiasedLockingStartupDelay

原因：JVM 启动阶段（类加载、初始化等）存在大量多线程竞争，
     过早启用偏向锁会频繁触发昂贵的撤销（SafePoint 级别）；
     延迟一段时间，等启动竞争高峰过去后再启用
     （OpenJDK 官方对延迟原因没有明确文档，这是社区普遍认同的解释）

默认值随版本变化（实测）：
  JDK 8                                    → 4000ms
  JDK 15+（含 JDK 17 显式 -XX:+UseBiasedLocking）→ 0ms，等于没有延迟

→ 所以 JDK 8 上"启动后立刻 new"出来的对象是无锁（0x…01），
  必须 **sleep 在 new 之前** 才能拿到可偏向对象（0x…05）；
  JDK 17 上没这回事，new 出来直接就是 0x…05。
  ⚠️ 注意作用点是"**之后 new 的对象**"，不是"已经存在的对象等一等"。
```

**批量重偏向 / 批量撤销（◈◈ 了解）**：

```
批量重偏向（Bulk Rebias）：
  当同一类的大量对象频繁撤销偏向锁 → 将 epoch +1，让旧的偏向全部失效
  一次操作解决"一个类所有对象的偏向状态"，而不是逐个撤销

批量撤销（Bulk Revoke）：
  当批量重偏向后仍然频繁撤销 → 关闭整个类的偏向功能

触发阈值：对象数 > 20（重偏向），撤销次数 > 40（撤销）
```

> 📌 **为什么要有「批量」这一层——见 §3.2**（含撤销为什么必须靠批量摊薄成本的因果）；**触发点实测见 §4.5**。

### 2.4 轻量级锁（Thin Lock）

**适用场景**：多线程交替访问（竞争窗口极短，如"线程 A 用完线程 B 立刻用"）。

**Lock Record 是什么？**

```
Lock Record 是轻量级锁在线程栈上建的一个「记账小本子」（HotSpot 里叫 BasicObjectLock）：
- 位于线程自己的栈帧里，线程私有，别的线程看不到
- 结构很小（约 2~3 个字），包含两个核心字段：
  ① Displaced Mark Word：进入临界区时保存的原始 Mark Word 副本（hash/age 寄存在这）
  ② 指向锁对象的引用：记录「我锁的是谁」

一个线程可以有很多个 Lock Record：
- 同时锁 N 个不同对象 → N 个 Lock Record（每个对象一个）
- 同一把锁重入/递归 → 每次 monitorenter 还会新建一个（重入的记录不保存
  Displaced Mark Word，只标记「我已持有」）
- 嵌套多深、锁多少对象，栈上就有多少，动态增长，没有固定上限
```

**Lock Record vs ObjectMonitor**：

| | Lock Record | ObjectMonitor |
|---|---|---|
| 位置 | 线程栈上 | 堆上 |
| 数量 | 每线程、每次加锁各建一个 | 每个被锁对象一个（全局唯一） |
| 归属 | 线程私有，释放时销毁 | 对象长期持有，膨胀后一直挂 |
| 用于 | 轻量级锁 | 重量级锁 |

> 一句话：Lock Record 是「锁的使用记录」（按线程按次数），ObjectMonitor 是「锁的本身」（按对象一个）。

```
获取过程：

1. 如果对象处于无锁/可偏向状态（但禁用偏向）→ 线程在栈帧中创建 Lock Record
2. Lock Record 中保存 Mark Word 的副本（Displaced Mark Word）
3. CAS 将对象 Mark Word 中的指针替换为指向 Lock Record
4. CAS 成功 → 持有轻量级锁
5. CAS 失败 → 表示有竞争 → 膨胀为重量级锁

释放过程：
1. CAS 将 Mark Word 恢复为 Displaced Mark Word
2. 恢复成功 → 释放完成
3. 恢复失败（说明已经膨胀）→ 走重量级锁的释放流程
```

**图解**：

```
线程 A 的栈帧：                   对象 Mark Word：
┌──────────────────┐      ┌────────────────────────┐
│ Lock Record       │      │ [ptr_to_LockRecord]|00 │
│  Displaced Mark   │ ←─── │  （指向线程 A 的 Lock Record）│
│  Word（原Mark副本）│      └────────────────────────┘
└──────────────────┘
```

**自旋（Spin Lock）**：

> ⚠️ **常见错误说法**：轻量级锁 CAS 失败后"先自旋，自旋超限再升级重量级锁"。这是 JDK 5 时代的模型。JDK 6+ 的真实顺序是：**竞争发生时当场膨胀，自旋发生在膨胀之后的 monitor 获取路径上**（详见 §2.5）。

```
轻量级锁 CAS 失败后，线程不会"原地空转等 Mark Word 变回来"，而是立刻进入膨胀流程：
  1. inflate() 内部先做 PreInflateSpin（固定小次数，默认 10）：
     边转边再试一次 CAS——若锁恰好释放，直接抢到 thin lock，省掉一次膨胀
  2. PreInflateSpin 内仍抢不到 → 当场膨胀成重量级锁（不可逆）
  3. 膨胀后线程才进入 monitor 的获取流程：
     TryLock（CAS _owner）→ 自适应自旋 → 失败 → 进入 _cxq → park() 挂起

自旋的意义：
  自旋发生在 monitor 层面（ObjectMonitor::TrySpin），目的是避免 park/unpark 的上下文切换：
  持有者很快释放 → 自旋几十纳秒就抢到，比一次 1~10 微秒的上下文切换快得多
  自旋的代价：占用 CPU 时间片（忙等）

自适应自旋（Adaptive Spinning，JDK 6+）：
  JVM 根据历史情况动态调整自旋次数：
  - 上次自旋成功 → 增加自旋次数
  - 上次自旋失败 → 减少自旋次数甚至不自旋
```

### 2.5 重量级锁（Fat Lock）

**适用场景**：竞争激烈（多个线程长期竞争）。

```
膨胀过程（从轻量级锁升级）：

> 触发点不是"自旋超限"，而是**检测到竞争**：轻量级锁的 CAS 一失败就立刻膨胀。

1. 线程 B 对薄锁的 CAS 失败 → 检测到竞争 → 进入 inflate()
2. inflate() 先做 PreInflateSpin（默认 10 次）：边转边再试一次 CAS
   - 抢到了 → 返回薄锁，不膨胀
   - 仍失败 → 分配并初始化 ObjectMonitor 对象
3. 将 Mark Word 指针替换为指向 ObjectMonitor（此后不可逆）
4. 线程 B 进入 monitor 的获取流程（不是直接排队）：
   TryLock（CAS _owner）→ 自适应自旋 → 失败 → 进入 _cxq 等待队列
5. 线程 B 挂起（进入内核态阻塞）
```

**ObjectMonitor 里面长什么样？**

```
它内部的三个队列（_cxq / _EntryList / _WaitSet）怎么分工、线程在里面的完整轨迹、
"被唤醒 ≠ 成为 owner" 的来龙去脉 —— 全部在 [02-03 §3](./02-03-wait-notify与ObjectMonitor.md)。
那里是讲这块的【唯一】地方，本篇不重复。

本篇只记一句骨架：
  抢锁失败 → 记名进队列 → park 挂起
  owner 退出 → 挑一个继任者 → unpark 它
  被唤醒者 →【重新 CAS 竞争】，赢了才成为 owner   ← 这就是 synchronized 非公平的来源
```

**重量级锁的开销**：

```
阻塞/唤醒一个线程 = 内核态操作：
  线程挂起 → 用户态→内核态切换 → 内核调度 → 线程恢复 → 内核态→用户态
  → 每次上下文切换约 1~10 微秒（纳秒级指令相比是天文数字）

这就是"重量级锁为什么重"的根本原因
```

### 2.6 升级时 Mark Word 里的信息去哪了？（不丢，是搬家）

> 很多人以为锁升级后 hash、age 等信息「丢了」。其实 JVM 的原则是：**对象本身的信息（identity hash、GC 年龄）不能丢，只是换地方存**。锁升级时真正变化的只有锁状态数据（thread、epoch、指针）。

**可偏向 → 已偏向（写入线程 ID）：根本没有数据需要搬**

```
能进入偏向锁的对象，必然还没算过 identity hash：
- 算过 hash → Mark Word 上半部分被 hash 占用，biased_lock 位被清 0 → 永远进不了偏向锁
- 没算过 hash → 上半部分（unused/hash/cms_free）本来就是 0，没有内容可搬

而且 age 在两种布局里的位置完全一样（都是 bits 3~6）：

  无锁：  [ unused:25 | identity_hashcode:31 | cms_free:1 | age:4 | biased_lock:0 | 01 ]
  偏向：  [ thread:54  | epoch:2 | unused:1    | age:4 | biased_lock:1 | 01 ]
                                        ↑ age 原地不动

所以"夺偏向"这一步只是：CAS 把线程 ID 写进上半部分（biased_lock 位在 `new` 时就已经是 1，不用动），零信息损失。
```

**无锁 → 轻量级锁：hash/age 复制到线程栈（Displaced Mark Word）**

```
进入临界区时，先把原始 Mark Word（含 hash、age）复制到线程栈的 Lock Record，
这个副本叫 Displaced Mark Word；Mark Word 腾出来存指向 Lock Record 的指针。

释放时：把 Displaced Mark Word CAS 回 Mark Word → hash/age 回到对象头。
（只要还停在轻量级锁，就一直是「借出去再还回来」）
```

**轻量级 → 重量级锁（膨胀）：数据转存进 ObjectMonitor**

```
膨胀时，Lock Record 里的 Displaced Mark Word 被转存到 ObjectMonitor 的 header 字段，
之后 identityHashCode 从 monitor 里读，值保持不变。

注意：膨胀后锁不会降级，Mark Word 永远指向 ObjectMonitor，
所以对象头里再也「看不到」hash/age 了——但它们在 monitor 里，没丢。
```

**各状态读 identity hash 的路径**：

```
无锁 / 轻量级锁：直接读 Mark Word（轻量级锁借出后会还回来）
重量级锁：从 ObjectMonitor 的 header 读
偏向锁：不可能带 hash（算过 hash 就进不了偏向锁）
```

> 📌 **实测验证见 §4.6**（含"膨胀后 hash 依然读得到、值不变"的逐步对照）。

### 2.7 版本分岔：偏向锁的「生前身后」

| JDK 版本 | 偏向锁状态 |
|---|---|
| JDK 6~14 | 默认开启 |
| JDK 15 | **默认禁用 + 废弃**（`-XX:+UseBiasedLocking` 仍可开启） |
| JDK 18 | **完全移除**（相关代码被删除，选项仅作兼容提示） |

```
为什么放弃偏向锁？

1. 撤销成本高：撤销要让存活的偏向线程在 SafePoint 停下（STW 级别，见 §3.1）
2. 收益变小：现代应用普遍多线程竞争，偏向锁命中率下降
3. 维护复杂：与 JIT/GC 的交互导致大量边缘 bug
4. 硬件进步：CAS 成本下降，无锁方案（LongAdder 等）性能更好

→ 你用的 Java 17 默认没有偏向锁！JDK 8 有！
→ 学习锁升级时要区分版本：JDK 8 是"四态升级"，JDK 17 是"三态升级"（见开头版本表）
```

> ⚠️ **面试关键**：一定要说清楚你讲的是哪个 JDK 版本。JDK 15+ 默认无偏向锁是 2020 年之后的新知识，很多旧资料还在讲"四态"。

## 第三章 深入：两个「为什么」（▷ 面试不考）

> 📌 整章标 `▷`：**面试不问，二遍法第一遍可以整块跳过**。但如果你想知道「偏向锁为什么这么贵」，这里是第一性原理。

### 3.1 ▷ 为什么撤销必须让持有线程停在 SafePoint

**为什么必须让持有线程在安全点停下？（第一性原理）**：

```
偏向锁的代价结构直接决定了这个"为什么"：

1. 偏向锁的核心：持有线程进出临界区对共享的 Mark Word 零写入
   → "A 此刻在不在临界区内"只存在于 A 自己的执行状态里（PC + 栈），
     没有任何共享内存记录它
2. 撤销要改写 Mark Word，改写前必须知道这个事实：
   - A 不在临界区 → 对象空闲，可安全改写
   - A 在临界区 → 不能偷，必须膨胀成 monitor 并把 owner 记成 A
3. 为什么"读"、"CAS"、"flag"都解决不了：
   - 读不到：没有共享载体，A 进没进临界区只有 A 自己知道
   - CAS 通知不到：A 进入临界区后就不再读 Mark Word（退出也是 no-op），
     改写掉 Mark Word，A 的旧信念不会跟着更新
   - 加 flag：flag 是一次共享写，重新引入偏向锁想消灭的开销，
     且"读 bias 决定进入"到"写 flag"之间 B 照样能偷，窗口无解
   → "零共享写"和"别人能随时判断你进没进临界区"物理上互斥，偏向锁选了前者
4. SafePoint 怎么解决：让 A 停在"栈是可信快照"的规范点，遍历 A 的栈数进入次数：
   - 0 次 → A 不在临界区 → 安全改写
   - >0 次 → A 在临界区 → 膨胀成 monitor，owner=A
5. 为什么所有线程都停（不只 A）：
   - Mark Word 是任何线程的 fast path 都可能正在读的，改写要对所有读者原子
   - 批量重偏向/撤销（epoch）涉及一类对象的所有持有者，要全局一致更新
   → 经典实现 = 全局安全点的 VM_Operation，"stop the world" 名副其实
6. A 已死为什么不用停：A 死了 = 平凡地回答了"不在临界区"，直接改写即可
   → 这就是撤销代价"看运气"的原因
```

### 3.2 ▷ 为什么分界线是 epoch，以及「批量」这一层为什么存在

> 这两件事**互为前提**：epoch 是批量的载体，批量的意义是省掉逐个撤销。所以放在一节里讲，拆开会让因果断掉。

**第一层：为什么分界线是 epoch（而不是别的条件）**

```
两种慢路径的代价差在哪？
- 撤销贵，贵在**必须知道原线程 A 此刻在不在临界区**——这个事实只存在于 A 自己的栈里
  （偏向锁零共享写的必然结果，见 §3.1），只能停下 A 去数
- 重偏便宜，便宜在**不用问任何人**：只有"这条记录已经不作数了"时才走这条路，
  既然不作数，A 在不在临界区就无关紧要

→ 所以判定的本质是「**这条偏向记录还有没有效力**」，而效力的标记就是 epoch：
  epoch 是批量重偏向（只在安全点发生）用来把一整批旧记录**同时作废**的版本号，
  对象身上存一个、类的原型头里存一个，两个不一致 = 这条记录已被整体作废
```

**第二层：为什么要有「批量」这一层**

```
撤销是把对象"一次性用坏"（偏向后永久不可偏向），还附带 SafePoint STW。
如果每来一个对象就撤一次，同一个类有多少对象就要 STW 多少轮。

→ 所以 JVM 数着：同一个类的撤销次数
   到 20 → 做一次批量重偏向：在安全点上把整类的 epoch +1
           一整批对象的偏向同时作废 → 之后遇到它们就能走便宜的"重偏向"
   到 40 → 重偏了还不行，说明这个类根本不适合偏向 → 整类关闭偏向功能

→ 一句话：**批量是把「逐个付出的 STW 成本」摊薄成「按类付一次」**。
```

> JDK 17 -XX:+UseBiasedLocking            ：new 出来就是 0x…05（可偏向），无需等待
> JDK 17 -XX:+UseBiasedLocking -XX:BiasedLockingStartupDelay=4000：
>                                           new 出来是 0x…01，先 sleep 再 new 才是 0x…05
> ```

### 4.2 怎么读 JOL 输出

```
无锁：     00000000 00000000 ... 00000001
          ← unused + hash + age + [0] + [01]

偏向锁：   00000000 00000000 ... 00000101
          ← thread(空) + epoch + age + [1] + [01]

轻量级锁： 00000000 00000000 ... 00110000
          ← ptr_to_LockRecord + [00]

重量级锁： 00000000 00000000 ... 00010010
          ← ptr_to_ObjectMonitor + [10]
```

> 输出是**小端序**，最右边的是低位字节，判断锁状态看最后两位。

### 4.3 Mark Word 五态对照（JDK 21 + JOL 0.17）

> 产出：`sync/JolLockDemoTest#testLockStates`

```
new Object()        → mark = 0x0000000000000001   (non-biasable; age: 0)
调用 hashCode() 后  → mark = 0x0000007c75222b01   (hash: 0x7c75222b; age: 0)
```

- 末尾 `01`：lock = 01（普通对象）
- 第 3 位 = 0：non-biasable（JDK 15+ 默认无偏向锁，JOL 直接标 non-biasable）
- `0x7c75222b`：31 位身份哈希（实测确认小于 2 的 31 次方）
- `age: 0`：还没经历过 GC

**JDK 8 上的关键对照 —— 顺序搞反就永远看不到偏向位**：

```
先 new，再 sleep 4.1s  → 0x0000000000000001  biased_lock=0（等了也白等）
先 sleep 4.1s，再 new  → 0x0000000000000005  biased_lock=1
```

> `0x05` = `0b0101`：第 3 位 = 1（可偏向），后两位 = 01（普通对象）。
> **偏向位是 `new` 那一刻从类原型头盖上去的**——已经存在的对象不会因为等了 4 秒就变成可偏向（机制见 §2.3）。

### 4.4 偏向锁的「零写入」证据

> 产出：JDK 8 + `Unsafe` 直读对象头 Mark Word；对照组在 JDK 17 默认（三态）下跑

```
实测（JDK 8 + Unsafe 直读对象头 Mark Word）：
  延迟期后 new           0x0000000000000005   thread = 空
  第 1 次 synchronized   0x00000230ba083805   thread = 0x8c2e820e
  释放后                 0x00000230ba083805   ← 与持锁时逐位相同
  第 2 次 synchronized   0x00000230ba083805   ← 同上，一个字节都没动
→ 「持锁中 / 已释放」「第 1 次 / 第 n 次」全都无法从对象身上读出来

对照：同一台机器上关掉偏向锁（JDK 17 默认），同一个对象：
  持锁中  0x000000c34e9ff820  lock=00   ← 写一次（把 Lock Record 指针装进 Mark Word）
  释放后  0x0000000000000001  lock=01   ← 又写一次（CAS 还回 Displaced Mark Word）
→ 轻量级锁每次进出临界区写 Mark Word 两次，偏向锁一次都不写。
  这就是「偏向锁为什么不能计数」的直接证据：**要计数就得写，写了就不是偏向锁了**。
```

**顺带一个反直觉的实测 —— 撤销后落到「不可偏向」，不是「回到匿名可偏向」**：

```
撤销前（A 偏向） 0x0000022800218805  偏向锁 thread=0x8a000862
B 持锁中         0x0000003c0ffff2f8  轻量级锁（不是 biased:B！）
B 释放后         0x0000000000000001  不可偏向 ← 撤销后的落点
```

> 「撤销完顺手把偏向给 B」不存在——对象已被置成不可偏向，B 只能走轻量级锁（机制见 §2.3）。

### 4.5 批量重偏接触发点实测（JDK 8）

> 产出：对同一个类连做 30 轮「A 偏向 → main 来抢」

```
轮次        main 持锁中           走哪条路
1 ~ 19      thin(lock=00)        撤销
20          biased:main          重偏向  ← 批量重偏接触发（阈值 20）
21 ~ 30     thin(lock=00)        撤销    ← 计数已清零，重新开始数

→ 切换点正好落在第 20 轮，一分不差；也印证了"重偏向只在 epoch 过期时才有"，
  因为第 20 轮之后 A 的新偏向又带着新 epoch，于是重新变回"有效记录"→ 继续走撤销
```

> 机制见 §3.2。

### 4.6 升级时 hash / age 真的没丢（JDK 21 + JOL 0.17）

> 产出：`sync/WaitUpgradeTest`（wait 触发膨胀）+ `sync/JolLockDemoTest`

```
1. new Object()                mark = 0x0000000000000001   （无锁，无 hash）
2. 调 identityHashCode         mark = 0x0000007c75222b01   （hash = 0x7c75222b = 2088051243）
3. synchronized 块内（wait前）  mark = 0x000000e85c1ff330   （thin lock，hash 不在 Mark Word 里）
4. wait 膨胀成重量级锁          mark = 0x00000290ee2bc832   （fat lock，hash 依然不在 Mark Word 里）
5. 重量级锁下再读 identityHashCode → 2088051243（和步骤 2 相同）→ 没丢！
```

> 第 3、4 步的 Mark Word 里当然读不到 hash——`Lock Record 指针` / `ObjectMonitor 指针` 把它挤走了。但第 5 步证明它只是**搬了家**（栈上的 Displaced Mark Word → ObjectMonitor 的 header 字段），值一位没变。机制见 §2.6。

## 第五章 JIT 层的锁优化

### 5.1 锁消除（Lock Elimination）

```
场景：JIT 通过逃逸分析发现"对象不会逃逸出当前线程/方法" → 同步可以去掉

典型例子：
  StringBuffer sb = new StringBuffer();
  sb.append("a");   // append 是 synchronized 的
  sb.append("b");
  String s = sb.toString();

  JIT 分析：sb 没有逃逸出当前方法 → 不需要加锁 → 消除所有 synchronized
  → 所以单线程用 StringBuffer 也不会慢（当然直接用 StringBuilder 更好）
```

### 5.2 锁粗化（Lock Coarsening）

```
场景：同一对象连续多次加锁/解锁 → 合并为一个大锁块

典型例子：
  for (int i = 0; i < 100; i++) {
      synchronized (lock) {   // 100 次加锁/解锁
          doSomething();
      }
  }

  JIT 优化为：
  synchronized (lock) {        // 一次加锁
      for (int i = 0; i < 100; i++) {
          doSomething();
      }
  }
  // 但注意：锁粗化后锁持有时间变长，高竞争场景反而不利
```

### 5.3 逃逸分析（Escape Analysis）

```
JIT 的逃逸分析判断对象能否逃逸出方法：

-XX:+DoEscapeAnalysis（JDK 6u23+ 默认开启）

三种逃逸状态：
  不逃逸 → 栈上分配（对象不进入堆，GC 都不用管）
  方法逃逸 → 被其他方法引用，但不被线程共享
  线程逃逸 → 被其他线程访问（必须用同步）

相关优化：
  栈上分配 + 标量替换（把对象拆成多个变量）
  锁消除（依赖逃逸分析）
```

## 第六章 生产注意事项 & 常见坑点

### 🕳️ 坑 1：调用 hashCode() 会让偏向锁失效

```java
// 对象一旦调用了 hashCode()，Mark Word 中要存储 hash 值
// → 没有空间存线程 ID → 该对象永远无法进入偏向锁状态
obj.hashCode();  // 之后这个对象最多只能到轻量级锁

// 规律：hash 和 偏向线程 ID 互斥！存了 hash 就不能偏向
```

**为什么算过 hash 就进不了偏向锁？**

```
Mark Word 一共只有 8 字节（64 位），而 hash 和偏向线程 ID 都想要这块存储，加起来放不下：

  identity_hashcode 需要  31 位
  thread（偏向线程ID）需要 54 位
  epoch               需要  2 位
  age                 需要  4 位
  biased_lock         需要  1 位
  lock                需要  2 位
                        合计  94 位  ＞  64 位  ✗

看布局更直观——两种状态的上半部分（bits 7~63）是同一块存储的两种读法：
  无锁：  [ unused:25 | identity_hashcode:31 | cms_free:1 | age:4 | biased_lock:0 | 01 ]
  偏向：  [ thread:54  | epoch:2 | unused:1    | age:4 | biased_lock:1 | 01 ]

hash 需要 bits 8~38，thread 需要 bits 10~63，重叠区 bits 10~38，大面积重叠，无法共存。
```

**为什么不能把 hash 挪到别处单独存？**

```
1. Mark Word 是对象身上唯一「永远可读」的 8 字节：identityHashCode() 必须随时能读到 hash，
   对象头之外没有第二个「随时随身携带」的存储
2. 偏向锁的核心理念是「持有期间不建 Lock Record」（零开销进出临界区）：
   轻量级锁可以把 hash 借到栈上的 Lock Record，因为那个记录本来就要建；
   但偏向锁刻意不建，没有天然的地方放 hash
3. 为 hash 给偏向对象加额外存储，会破坏「对象头固定 8 字节、零额外开销」的设计
```

**HotSpot 的选择：互斥 + 谁先占谁赢**

```
- 先算 hash → Mark Word 被 hash 占用，biased_lock 位被清 0，对象永久失去偏向资格
  （之后只能走「无锁 → 轻量级锁」路径）
- 先偏向 → 之后再调 identityHashCode()，JVM 先在 SafePoint 撤销偏向，腾出位置再写 hash

顺带：age 是唯一不用搬家的字段——两种布局都故意把 age 放在 bits 3~6 同一位置
（HotSpot 源码注释明确要求 age 位与锁位相邻）
```

> 设计合理性：会算 identity hash 的对象，通常是被塞进 HashMap 当 key、被多线程共享的对象，偏向锁命中率本来就低，牺牲偏向换 hash 的普适可用性是划算的。

### 🕳️ 坑 2：别混淆——重写 hashCode 不会自动占用 Mark Word

```java
// identity hash 是懒计算的：只有真正调用 Object.hashCode() / System.identityHashCode()
// 才会把哈希码写入 Mark Word → 该对象从此无法进入偏向锁
obj.hashCode();               // 触发 identity hash → hash 位段被占用
System.identityHashCode(obj); // 同理

// 注意：类重写 hashCode() 并不会在 new 时自动调用、也不会占用 Mark Word
// 重写后的 hashCode() 只是普通方法；只有没重写 hashCode 的类被调用 hashCode()
// 或显式调用 identityHashCode 才会占用 hash 位段
// 例：没重写 hashCode 的对象放进 HashMap 当 key，存 key 时就会占用 → 无法偏向
```

### 🕳️ 坑 3：wait/notify 只能用于重量级锁

```java
synchronized (obj) {
    obj.wait();  // 调用 wait 时，锁会自动升级为重量级锁
    // 因为 wait 需要 ObjectMonitor 的 _WaitSet 结构！
}
// 也就是说：wait/notify 触发的膨胀是不可逆的
```

> 为什么是"必须"膨胀、以及 `_WaitSet` 在里面怎么运转 → 见 [02-03 §3](./02-03-wait-notify与ObjectMonitor.md)。

### 🕳️ 坑 4：锁粗化在高竞争场景适得其反

```java
// 低竞争：锁粗化收益大（减少加锁解锁次数）
// 高竞争：锁粗化让持有时间变长 → 更多线程等待 → 反而变慢
// 结论：不要过度依赖 JIT 优化，代码层面就应写合适的锁粒度
```

### 🕳️ 坑 5：认为"锁只能升级不能降级"是绝对的

```java
// 常规情况下锁只能升级不能降级（JVM 规范层面）
// 但注意：
// 1. GC 标记时 Mark Word 临时进入 11 状态（暂存标记信息），不参与锁状态
// 2. 偏向锁被撤销时（原线程退出临界区）→ 落到**不可偏向**（biased_lock=0，0x…01），
//    对象就此永久失去偏向资格（实测见 §2.3 第 4 步）
// 3. JDK 15 后根本没有偏向锁
// 4. 【真正的降级】空闲的 monitor 会在安全点被回收（deflate_idle_monitors），
//    对象头恢复成无锁（identity hash 保留）→ 对象确实从重量级锁"回到"了无锁
```

**第 4 条要单独说清楚**，因为它表面上和"不降级"直接冲突：

| | 含义 |
|---|---|
| "不降级"真正指的是 | **持有者不会主动降级**——轻量级锁的线程不可能因为"竞争变少了"就自己退回偏向锁；膨胀对持有路径也是不可逆的 |
| 但它**不等于** | "对象永远停在重量级锁"。**空闲**（无人持有、锁池空）的 monitor 会被 HotSpot 在安全点回收 |
| 回收之后 | 对象头恢复成无锁（`01`），**identity hash 保留**（原本存在 monitor 的 `_header` 里，回收时写回对象头） |

> 所以准确的说法是：**锁的"级别"由对象头当前状态决定，而对象头会被 JVM 主动重置**。
> 面试时说"锁只能升级"通常不算错（问的确实是持有路径），但被追问
> "那这个对象一辈子都是重量级锁吗"——答得出 deflate 就是加分项。

> 📌 完整的转移清单（含释放、重入、wait 强制膨胀、deflate 回收）见 §2.2 的表 B。

## 第七章 面试速查

1. **画一下 64 位 JVM 的 Mark Word 结构**
   → 无锁（hash+age+01）、偏向（thread+epoch+age+101）、轻量（ptr+00）、重量（ptr+10）

2. **锁升级的全过程？触发条件是什么？**
   → 别背"无锁→偏向→轻量→重量"这条线，要答**它是由「当场读到的 Mark Word」分流出来的**（§2.2 表 A）：
     - 读到 `biased=0` → CAS 写 Lock Record：成功即轻量级，失败即膨胀
     - 读到 `biased=1, thread=空` → 写线程 ID（**不是从"无锁"升级来的**，可偏向位在 `new` 时就盖好了）
     - 读到 `biased=1, thread=我` → 一个字节都不写
     - 读到 `biased=1, thread=别人` → 看 epoch：有效→撤销（再看对方死活/在不在临界区，三种去向）；过期→重偏向
   → 一句话收尾：**加锁只有一个事件，"升级路径"是状态谓词分出来的结果。注意 JDK 15+ 无偏向锁。**

3. **偏向锁为什么会被废弃？**
   → 撤销需 SafePoint STW、收益变小、维护复杂、JDK 15 默认禁用、21 移除。

4. **轻量级锁和重量级锁的本质区别？**
   → 轻量级：CAS 抢锁（用户态，无等待队列）；重量级：ObjectMonitor + 自旋 + 阻塞唤醒（内核态）。

5. **什么情况下 synchronized 会直接升级到重量级锁？**
   → 三条路，缺一不可：
     ① 检测到竞争（CAS 失败即膨胀，无需自旋超限）
     ② 调用了 wait/notify（需要 `_WaitSet`，即使零竞争也强制膨胀）
     ③ **撤销偏向锁时，原偏向线程 A 仍在临界区** → 膨胀并把 owner 记成 A（对象被"移交"给 A）
   （①② 见 §2.2 表 A/表 B，③ 见 §2.3 第 4 步）

6. **为什么调用 hashCode 后对象不能进入偏向锁？**
   → Mark Word 同一存储区域：存了 hash 就没空间存线程 ID，两者互斥。

2. **为什么偏向锁撤销很昂贵？**
   <details><summary>答案</summary>

   撤销要判断原线程状态：若已终止，直接改写 Mark Word，无需 STW；若仍存活，必须让它在安全点停下，所有线程停在这个安全点，一次撤销 ≈ 一次 STW 级操作。这就是 JDK 15 禁用偏向锁的原因之一。
   </details>

3. **Java 17 和 Java 8 的锁升级路径有什么区别？**
   <details><summary>答案</summary>

   JDK 8：无锁 → 偏向锁 → 轻量级锁 → 重量级锁（四态）
   JDK 17：无锁 → 轻量级锁 → 重量级锁（三态，JDK 15 起默认禁用偏向锁）
   </details>

4. **轻量级锁和重量级锁各自解决什么问题？开销区别在哪？**
   <details><summary>答案</summary>

   轻量级：解决"竞争窗口极短"的场景，用 CAS 抢锁避免内核态切换（自旋实际发生在膨胀后的 monitor 里）；
   重量级：解决"竞争激烈"的场景，用 ObjectMonitor 管理等待队列；
   开销：轻量级全程用户态（微秒内），重量级有自旋 + 上下文切换（微秒到毫秒级）。
   </details>

5. **调用对象的 hashCode() 之后，为什么不能进入偏向锁？**
   <details><summary>答案</summary>

   Mark Word 是共享存储：偏向锁需要 54 位存线程 ID，hash 需要 31 位存哈希码。两者互斥，hashCode() 一旦被调用（存入 Mark Word），该对象就无法进入偏向状态，只能走轻量级锁路径。
   </details>
