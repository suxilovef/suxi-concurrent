## 1. AQS 是什么

### 1.1 一句话定义

> **AQS（AbstractQueuedSynchronizer）是 JUC 中所有锁和同步器的基础框架。它用 `state` 状态位 + CLH 双向队列，提供了一套"获取锁失败 → 排队等待 → 唤醒"的通用机制。**

```
基于 AQS 构建的类：
┌───────────────────────────────────────────────┐
│  ReentrantLock        → AQS 独占模式            │
│  ReentrantReadWriteLock → AQS 独占+共享模式      │
│  Semaphore            → AQS 共享模式            │
│  CountDownLatch       → AQS 共享模式            │
│  ThreadPoolExecutor.Worker → AQS 独占模式        │
│  SynchronousQueue     → 基于 AQS（早期版本）      │
└───────────────────────────────────────────────┘
```

### 1.2 设计思想：模板方法模式

```
AQS 做的事情（通用流程，已经实现好）：
  ✅ 队列管理（入队、出队、唤醒）
  ✅ 线程阻塞/唤醒（park/unpark）
  ✅ 中断处理、超时处理
  ✅ 条件队列（ConditionObject）

子类要做的事情（模板方法，交给子类实现）：
  ❓ tryAcquire(int)    — 独占方式尝试获取
  ❓ tryRelease(int)    — 独占方式尝试释放
  ❓ tryAcquireShared(int) — 共享方式尝试获取
  ❓ tryReleaseShared(int) — 共享方式尝试释放
  ❓ isHeldExclusively() — 是否独占持有
```

```java
// 子类只需实现 tryAcquire/tryRelease 两个方法
// 排队、阻塞、唤醒全部由 AQS 处理！
public class MyLock {
    // 内部继承 AQS
    private static class Sync extends AbstractQueuedSynchronizer {
        @Override
        protected boolean tryAcquire(int arg) {
            // CAS 将 state 从 0 改成 1
            return compareAndSetState(0, 1);
        }

        @Override
        protected boolean tryRelease(int arg) {
            setState(0);  // 释放：state 归零
            return true;
        }
    }
}
```

## 2. AQS 核心三要素

### 2.1 要素 1：state（同步状态）

```java
public abstract class AbstractQueuedSynchronizer {
    // 同步状态：volatile 保证可见性，CAS 保证原子性
    private volatile int state;

    // 三个访问方法
    protected final int getState() { return state; }
    protected final void setState(int newState) { state = newState; }
    protected final boolean compareAndSetState(int expect, int update) {
        return unsafe.compareAndSwapInt(this, stateOffset, expect, update);
    }
}
```

```
state 的含义由子类定义（AQS 不关心具体含义）：

ReentrantLock:    state = 可重入次数（0=未持有，N=重入 N 次）
Semaphore:        state = 剩余许可证数
CountDownLatch:   state = 剩余需要 countDown 的次数
ReentrantReadWriteLock: 高 16 位读锁计数 + 低 16 位写锁计数

→ state 是所有同步语义的载体！
```

### 2.2 要素 2：CLH 双向队列

```
AQS 的队列是 CLH 锁队列的变体（双向链表 + CAS 入队）：

          ┌──────┐    ┌──────┐    ┌──────┐    ┌──────┐
          │ head │ →→ │ Node │ →→ │ Node │ →→ │ tail │
          └──────┘    └──────┘    └──────┘    └──────┘
             ↑  ←← ←← ←← ←← ←← ←← ←← ←← ←←   ↑
            dummy节点      prev 指针          指向最后一个节点
           （不存线程）      双向指针             CAS 入队点
```

```
关键特征：

1. 队列 = 获取锁失败的线程的"等待室"
2. head 是哑节点（dummy），不存储实际线程
3. 入队：CAS 更新 tail（乐观锁，无锁入队）
4. 出队：获得锁的线程是 head.next，出队时 head 前移
5. 队列中没有"优先级"，FIFO 顺序等待
```

### 2.3 要素 3：Node 节点

```java
static final class Node {
    // 节点模式
    static final Node SHARED = new Node();   // 共享模式标记
    static final Node EXCLUSIVE = null;      // 独占模式标记

    // waitStatus 的五种状态
    static final int CANCELLED =  1;  // 取消（等待超时/中断）
    static final int SIGNAL    = -1;  // 后继节点需要被唤醒
    static final int CONDITION = -2;  // 在条件队列中等待
    static final int PROPAGATE = -3;  // 共享模式传播唤醒
    static final int INIT      =  0;  // 初始状态

    volatile int waitStatus;     // 节点状态
    volatile Node prev;          // 前驱节点
    volatile Node next;          // 后继节点
    volatile Thread thread;      // 该节点对应的线程
    Node nextWaiter;             // 指向下一个等待 condition 的节点

    Node() { }  // 用于创建 head 哑节点和 SHARED 标记
    Node(Thread thread, Node mode) { ... }  // 用于 addWaiter
    Node(Thread thread, int waitStatus) { ... }  // 用于条件队列
}
```

### 2.4 waitStatus 五种状态详解（⭐）

| 状态 | 值 | 含义 | 谁设置 | 何时出现 |
|---|---|---|---|---|
| CANCELLED | 1 | 节点已取消 | 线程自己（中断/超时） | 等待中被打断 |
| SIGNAL | -1 | 我的后继在等我唤醒 | 后继节点（park 前设到前驱上） | 排队等待 park 时 |
| CONDITION | -2 | 在条件队列中 | 调用 await 时 | 等待 condition |
| PROPAGATE | -3 | 传播唤醒 | 共享模式释放时 | Semaphore/CountDownLatch |
| 0 | 0 | 初始状态 | —（新入队；unparkSuccessor 释放时也 CAS 回 0） | 新入队节点 / 唤醒后 |

```
SIGNAL 的含义（最关键）：

A 节点在 park 之前，把前驱节点的 waitStatus 设为 SIGNAL
→ 前驱释放锁时，看到后驱是 SIGNAL → 知道要唤醒它
→ "我睡之前告诉前面的：你醒的时候记得叫我"

CANCELLED 的含义：
线程在等待中被中断/超时 → 节点标记 CANCELLED → 出队时被清理
```

## 3. 独占模式 acquire 全流程（核心中的核心）

> ⭐⭐⭐ **要求：能画出这条调用链，能逐行讲解每个方法**

### 3.1 整体调用链

```
lock() 调用的入口（嵌套结构，非顺序展开）：
  acquire(1)
  │
  ├─ ① tryAcquire(1)              ← 子类实现：尝试获取锁
  │      成功 → return（短路，后面全不执行）
  │
  └─ ② acquireQueued( ③ addWaiter(Node.EXCLUSIVE), arg )
                      └─────────┬─────────┘
                 addWaiter 嵌在参数位：先执行完（CAS 入队，必然成功）→ 返回 node
      │
      └─ for(;;) 循环尝试 + 阻塞：
            前驱是 head → tryAcquire 成功 → setHead → return interrupted
            否则 → shouldPark → park（睡）→ 唤醒 → 回到循环头
      │
      └─ ④ interrupted == true → selfInterrupt()   ← 补中断标志
```

> 嵌套关系：`addWaiter` 嵌在 `acquireQueued` 的参数位，`acquireQueued` 嵌在 `if` 的条件位。
> **求值顺序由嵌套深度决定：内层先于外层**（①②③④ 为求值顺序）。

### 3.2 acquire() 源码（入口）

```java
public final void acquire(int arg) {
    if (!tryAcquire(arg) &&                          // ① 尝试获取（子类实现）
        acquireQueued(addWaiter(Node.EXCLUSIVE), arg)) // ② 失败则入队 + 阻塞等待
        selfInterrupt();                              // ③ 被中断过则补中断标志
}
```

```
① tryAcquire：子类实现（ReentrantLock 里就是 CAS 改 state）
② 失败 → addWaiter 入队 → acquireQueued 循环等待
③ acquireQueued 返回 true = 等待期间被中断过 → 补上中断标志
   （注意：acquire 不会抛出 InterruptedException，只是记录中断）
```

### 3.3 tryAcquire() 模板方法

```java
// AQS 默认实现：直接抛异常
// 子类必须重写（ReentrantLock/Semaphore 各自实现自己的获取逻辑）
protected boolean tryAcquire(int arg) {
    throw new UnsupportedOperationException();
}
```

### 3.4 addWaiter() 入队（源码）

```java
private Node addWaiter(Node mode) {
    Node node = new Node(Thread.currentThread(), mode);  // 创建节点
    Node pred = tail;
    if (pred != null) {                                  // 快速路径：队列非空
        node.prev = pred;
        if (compareAndSetTail(pred, node)) {             // CAS 更新 tail
            pred.next = node;                            // 双链连接
            return node;
        }
    }
    enq(node);                                           // 完整路径：CAS 失败或队列空
    return node;
}
```

```
入队细节：
1. 快速路径：tail 不为空 → 直接 CAS 尝试入队
2. CAS 失败（并发竞争）→ 走 enq() 完整路径
3. 队列为空 → 先初始化 head/tail 哑节点，再入队
```

### 3.5 enq() 完整入队（源码）

```java
private Node enq(final Node node) {
    for (;;) {                                          // 自旋
        Node t = tail;
        if (t == null) {                                 // ① 队列为空：初始化
            if (compareAndSetHead(new Node()))           //   创建哑节点
                tail = head;
        } else {                                         // ② 队列非空：CAS 入队
            node.prev = t;
            if (compareAndSetTail(t, node)) {
                t.next = node;
                return t;
            }
        }
    }
}
```

```
为什么 head 必须是"哑节点"？
第一性原理：CLH 的设计是"持锁者不在队列里" —— 队列只装等待者
→ 出队 = 获锁者自己 setHead（清空 thread）+ p.next = null 断开旧 head
→ 若 head 存真实线程，head 可能是个"还没被唤醒的等待者"：释放者就得
  分辨"唤醒 head 自己还是 head.next"，且获锁/释放会并发操作同一个节点
→ 哑节点让不变式干净：head 永远是"已获锁的占位符"，head.next 永远是
  等待最久的人 → 释放者只需盯 head.next
（对比经典 CLH：持锁者留在队首；AQS 变体选择"获锁者前移"，
  代价是 CAS tail 入队 + prev 指针，换来出队零竞争）
```

### 3.6 acquireQueued() 核心等待循环（源码）

```java
final boolean acquireQueued(final Node node, int arg) {
    boolean failed = true;    // 是否失败（用于 finally 清理）
    try {
        boolean interrupted = false;   // 是否被中断过
        for (;;) {
            final Node p = node.predecessor();   // ① 获取前驱
            if (p == head && tryAcquire(arg)) {  // ② 前驱是 head → 尝试获取
                setHead(node);                   // ③ 成功 → 自己是新 head
                p.next = null;                   // ④ 断开旧 head（GC 回收）
                failed = false;
                return interrupted;              // 返回是否被中断过
            }
            if (shouldParkAfterFailedAcquire(p, node) &&  // ⑤ 准备 park
                parkAndCheckInterrupt()) {                // ⑥ 阻塞 + 检查中断
                interrupted = true;
            }
        }
    } finally {
        if (failed)
            cancelAcquire(node);   // 异常时取消节点
    }
}
```

```
核心逻辑：
① 只有"前驱是 head"的节点才有资格尝试获取锁（FIFO 公平性）
② tryAcquire 成功 → 自己成为 head（获得锁）
③ 失败 → shouldParkAfterFailedAcquire → park（阻塞）
④ 被唤醒后回到 ① 重新循环
```

### 3.7 shouldParkAfterFailedAcquire()（源码）

```java
private static boolean shouldParkAfterFailedAcquire(Node pred, Node node) {
    int ws = pred.waitStatus;
    if (ws == Node.SIGNAL)               // ① 前驱已经是 SIGNAL → 放心睡
        return true;
    if (ws > 0) {                        // ② 前驱已取消（CANCELLED=1）
        do {
            node.prev = pred = pred.prev;  // 跳过取消的前驱
        } while (pred.waitStatus > 0);
        pred.next = node;
    } else {                             // ③ 前驱是 0 / PROPAGATE
        compareAndSetWaitStatus(pred, ws, Node.SIGNAL);  // 设为 SIGNAL
    }
    return false;                        // 这次不睡，再转一圈（保证 SIGNAL 已生效）
}
```

```
关键点：
- 第一次调用：前驱是 0 → 设置 SIGNAL → 返回 false → 外层循环再试一次
- 第二次调用：前驱是 SIGNAL → 返回 true → 才真正 park

→ 为什么必须转一圈才 park（因果链）：
  ① park 前必须保证前驱的 SIGNAL 已经可见 —— 否则丢失唤醒：
     本线程检查前驱状态（还没设 SIGNAL）→ 恰好前驱 release，
     看到 waitStatus == 0 → 不 unpark → 本线程才 park → 永远睡死
  ② 所以先 CAS 设 SIGNAL，再转一圈重试：既确认 SIGNAL 已生效，
     又顺手再试一次获取 —— 这一圈期间锁若刚好被释放，直接拿到锁，
     省掉一次 park/unpark + 上下文切换
  → 不是"保险"，而是"正确性前置条件 + 顺手的优化"
```

### 3.8 parkAndCheckInterrupt()（源码）

```java
private final boolean parkAndCheckInterrupt() {
    LockSupport.park(this);          // 阻塞当前线程
    return Thread.interrupted();     // 返回是否被中断（并清除中断标志）
}
```

> LockSupport.park 是 AQS 阻塞线程的底层工具（基于 Unsafe.park）。park 的 permit（许可）机制——unpark 可提前、中断返回不抛异常——是 AQS 所有唤醒设计的根基，前置知识见 [02-04-LockSupport与park机制](./02-04-LockSupport与park机制.md)。

> ⚠️ **JDK 8 Windows 平台细节（幽灵信号）**：这里的 `Thread.interrupted()` 承担两层职责——语义上"消费中断标志、防止无限空转"；机制上"耗尽 interrupt() 遗留的 SetEvent 残留（幽灵信号）"。若只清标志不耗尽信号，带标志 park 立即返回时留下的 SetEvent 会挂在事件对象上，让**下一次** park 也立即返回——即空转从"无限"降级为"有限几次（2~3 轮）"。acquireQueued 每轮都重查条件，多一轮迭代无害；Windows console 输出还会复活幽灵（多一轮），实证见 [02-04 §4 平台差异](./02-04-LockSupport与park机制.md)。

### 3.9 独占模式释放：release()（源码）

```java
public final boolean release(int arg) {
    if (tryRelease(arg)) {                 // ① 尝试释放（子类实现）
        Node h = head;
        if (h != null && h.waitStatus != 0) // ② 队列非空且 head 有后继
            unparkSuccessor(h);            // ③ 唤醒后继节点
        return true;
    }
    return false;
}
```

```java
private void unparkSuccessor(Node node) {
    int ws = node.waitStatus;
    if (ws < 0)
        compareAndSetWaitStatus(node, ws, 0);   // 清空 SIGNAL 状态
    Node s = node.next;
    if (s == null || s.waitStatus > 0) {        // 后继为空或已取消
        s = null;
        for (Node t = tail; t != null && t != node; t = t.prev)
            if (t.waitStatus <= 0)              // 从尾部往前找最近的未取消节点
                s = t;
    }
    if (s != null)
        LockSupport.unpark(s.thread);           // 唤醒该线程
}
```

```
释放细节：
1. tryRelease 成功（state 归零）→ 唤醒队首等待者
2. 如果后继节点已取消 → 从 tail 往前找最近的"活着"的节点
3. unpark 唤醒后，该线程从 parkAndCheckInterrupt 返回 → 回到 acquireQueued 循环
```

### 3.10 独占模式全流程总结图

```
线程 T1：acquire(1)
  tryAcquire → 成功 → 持有锁（state=1，owner=T1）
  
线程 T2：acquire(1)
  tryAcquire → 失败（state=1）
  addWaiter → 入队（队尾）
  acquireQueued → 前驱不是 head → shouldPark → SIGNAL → park 阻塞

T1 执行完 → release(1)
  tryRelease → 成功（state=0）
  unparkSuccessor → 唤醒 T2

T2 醒来 → acquireQueued 循环
  前驱是 head → tryAcquire → 成功 → 自己成为新 head → 返回
```

### 3.11 补充：公平锁 vs 非公平锁（概念澄清）

> 上面 3.2~3.10 的全流程是**公平**的 —— AQS 队列本身 FIFO，先来先得。
> **"不公平"不是 AQS 提供的，是子类在入队前允许"插队"**（如 ReentrantLock 的 `NonfairSync.lock()` 先 CAS 抢一把，抢不到才入队）。

**一句话定义：**
- **公平（Fair）**：先来先得。谁先调用 `lock()`，谁先拿到锁。获取顺序 = 排队顺序。
- **非公平（Nonfair）**：允许插队。新来的线程和排队中的线程"赛跑"，谁先抢到算谁的，不保证先来先得。

**非公平的插队窗口 = 锁空闲（state == 0）的瞬间**（通常也就是锁刚释放到下一个获取之间的空窗期）

```
T1 释放锁的瞬间：
  新来的 T4：人已在 CPU 上 → CAS(0→1) 瞬间成功 → 插队成功 ✅
  队首的 T2：刚被 unpark 唤醒（OS 唤醒有开销）→ 醒来发现锁被抢 → 继续睡 ❌

→ 用个别线程的等待时间，换全体线程的吞吐量（省掉一次唤醒 + 上下文切换）
```

> ⚠️ 持锁期间新来的线程 CAS 一定失败，照样排队 → **非公平 ≠ 完全乱序**。
> ReentrantLock 默认非公平（`new ReentrantLock()`），公平需显式 `new ReentrantLock(true)`。详见 03-02 篇。

## 4. 共享模式 acquireShared 全流程

### 4.1 与独占模式的区别

```
独占模式（ReentrantLock）：同一时刻只能一个线程持有
共享模式（Semaphore/CountDownLatch）：多个线程可以同时"持有"

| 维度 | 独占 acquire | 共享 acquireShared |
|---|---|---|
| 获取 | tryAcquire | tryAcquireShared |
| 入队 | addWaiter(EXCLUSIVE) | addWaiter(SHARED) |
| 等待 | acquireQueued | doAcquireShared |
| 成功后 | setHead | setHeadAndPropagate（还要传播！） |
| 释放 | release | releaseShared |
```

### 4.2 acquireShared 入口

```java
public final void acquireShared(int arg) {
    if (tryAcquireShared(arg) < 0)   // 返回值：<0 失败，>=0 成功
        doAcquireShared(arg);        // 失败 → 排队
}

// 子类示例：Semaphore.tryAcquireShared
// 返回剩余许可数（>=0 表示成功）
```

### 4.3 doAcquireShared 核心循环

```java
private void doAcquireShared(int arg) {
    final Node node = addWaiter(Node.SHARED);   // 共享模式入队
    boolean failed = true;
    try {
        boolean interrupted = false;
        for (;;) {
            final Node p = node.predecessor();
            if (p == head) {
                int r = tryAcquireShared(arg);       // 尝试获取
                if (r >= 0) {
                    setHeadAndPropagate(node, r);    // ★ 成功 → 设置 head + 传播
                    p.next = null;
                    failed = false;
                    return;
                }
            }
            if (shouldParkAfterFailedAcquire(p, node) &&
                parkAndCheckInterrupt())
                interrupted = true;
        }
    } finally {
        if (failed) cancelAcquire(node);
    }
}
```

### 4.4 setHeadAndPropagate 传播机制（共享模式的核心）

```java
private void setHeadAndPropagate(Node node, int propagate) {
    Node h = head;
    setHead(node);                          // 自己是新 head
    if (propagate > 0 || h == null || h.waitStatus < 0 ||
        (h = head) == null || h.waitStatus < 0) {
        Node s = node.next;
        if (s == null || s.isShared())      // 后继是共享模式
            doReleaseShared();              // ★ 继续唤醒下一个
    }
}
```

```
为什么需要传播（Propagate）？
第一性原理：共享模式下"唤醒"不能与"某次释放"一一配对
—— 一次释放可能让多个线程同时获准进入，而每个释放只唤醒一个人，
   剩下没被唤醒的等待者就会一直睡到下一次释放（许可"白送"）

场景（Semaphore 发 3 个许可，4 个线程等待）：
  释放 1 个许可 → 唤醒队首
  队首线程被唤醒后 tryAcquireShared 成功（还剩 2 个许可）
  → 如果不传播，剩下 2 个许可就浪费了，其他线程继续睡

  → setHeadAndPropagate 会继续唤醒下一个共享节点
  → 直到没有许可或没有等待者

⚠️ 传播还守着一个更隐蔽的正确性（JDK-6801020，历史修过的丢失唤醒 bug）：
  doReleaseShared 是"释放线程"读 head 再唤醒 head.next，
  setHeadAndPropagate 是"获锁线程"改 head —— 两者并发存在竞态：
    释放者刚读完 head（SIGNAL）→ 获锁者 setHead 换人
    → 释放者按旧 head 唤醒一个已不是队首的节点
  → 所以 setHeadAndPropagate 要同时检查旧 head 和新 head 的
    waitStatus < 0（任一 < 0 说明还有释放动作在路上，必须继续传播），
    doReleaseShared 里 if (h == head) break 也是同一竞态的稳定性检查
  → 传播本质是"防丢唤醒"，不只是"多叫几个人"
```

### 4.5 doReleaseShared 共享释放

```java
private void doReleaseShared() {
    for (;;) {
        Node h = head;
        if (h != null && h != tail) {
            int ws = h.waitStatus;
            if (ws == Node.SIGNAL) {                 // 需要唤醒后继
                if (!compareAndSetWaitStatus(h, Node.SIGNAL, 0))
                    continue;                        // CAS 失败重试
                unparkSuccessor(h);                  // 唤醒
            } else if (ws == 0 &&
                     !compareAndSetWaitStatus(h, 0, Node.PROPAGATE))
                continue;                            // 设置传播状态
        }
        if (h == head)                               // 没有新变化 → 结束
            break;
    }
}
```

## 5. 可中断与可超时获取（◈◈）

### 5.1 可中断：acquireInterruptibly

```java
public final void acquireInterruptibly(int arg) throws InterruptedException {
    if (Thread.interrupted())
        throw new InterruptedException();        // ① 先检查中断
    if (!tryAcquire(arg))
        doAcquireInterruptibly(arg);             // ② 失败 → 可中断的排队
}

private void doAcquireInterruptibly(int arg) throws InterruptedException {
    final Node node = addWaiter(Node.EXCLUSIVE);
    ...
    for (;;) {
        ...
        if (shouldParkAfterFailedAcquire(p, node) &&
            parkAndCheckInterrupt())
            throw new InterruptedException();    // ★ 中断时直接抛异常（不是记录！）
    }
}
```

> **区别**：`acquire()` 被中断只是记录标志；`acquireInterruptibly()` 被中断直接抛异常。

### 5.2 可超时：tryAcquireNanos

```java
public final boolean tryAcquireNanos(int arg, long nanosTimeout)
        throws InterruptedException {
    if (Thread.interrupted())
        throw new InterruptedException();
    return tryAcquire(arg) ||
        doAcquireNanos(arg, nanosTimeout);       // 带超时的排队
}

private boolean doAcquireNanos(int arg, long nanosTimeout) {
    long deadline = System.nanoTime() + nanosTimeout;
    final Node node = addWaiter(Node.EXCLUSIVE);
    ...
    for (;;) {
        if (p == head && tryAcquire(arg)) { ... return true; }
        nanosTimeout = deadline - System.nanoTime();
        if (nanosTimeout <= 0L) {                // 超时！
            cancelAcquire(node);                 // 取消节点
            return false;
        }
        if (shouldParkAfterFailedAcquire(p, node) &&
            nanosTimeout > spinForTimeoutThreshold)
            LockSupport.parkNanos(this, nanosTimeout);  // 有限时间 park
    }
}

// spinForTimeoutThreshold = 1000ns
// 剩余时间 < 1000ns 就不再 park（park 本身有开销，小于阈值直接自旋）
```

### 5.3 cancelAcquire 节点清理（○）

```
触发：中断或超时
处理：
1. 节点的 thread 置空
2. 跳过前面所有 CANCELLED 节点
3. 如果是 tail → CAS 更新 tail
4. 如果不是 tail 且有有效后继 → 连接前后节点（出队）
5. 否则唤醒后继（防止唤醒丢失）
```

## 6. ConditionObject 条件队列

### 6.1 Condition 是什么

```
对比：

synchronized 的等待：Object.wait/notify（只有 1 个等待队列）
AQS 的等待：Condition.await/signal（可以有多个条件队列！）

例子（有界队列）：
  notEmpty = lock.newCondition();   // 队列非空的条件
  notFull  = lock.newCondition();   // 队列不满的条件
  → 生产者 await(notFull)，消费者 await(notEmpty)
  → 精确唤醒，不会"唤醒错误的人"
```

### 6.2 Condition 的两种队列

```
AQS 中有两种队列：

同步队列（Sync Queue）：
  获取锁失败的线程 → CLH 队列 → 等待获取锁

条件队列（Condition Queue）：
  调用 await() 的线程 → 单链表（nextWaiter 连接）→ 等待条件满足

关系：条件队列中的线程释放了锁（await 时），
     被 signal 后 → 从条件队列移到同步队列（重新抢锁）
```

### 6.3 await() 全流程

```java
public final void await() throws InterruptedException {
    if (Thread.interrupted())
        throw new InterruptedException();
    Node node = addConditionWaiter();   // ① 加入条件队列
    int savedState = fullyRelease(node); // ② 完全释放锁（注意重入多次也全释放）
    int interruptMode = 0;
    while (!isOnSyncQueue(node)) {       // ③ 不在同步队列就 park
        LockSupport.park(this);
        if ((interruptMode = checkInterruptWhileWaiting(node)) != 0)
            break;
    }
    if (acquireQueued(node, savedState) && interruptMode != THROW_IE)  // ④ 重新获取锁
        interruptMode = REINTERRUPT;
    ...
}
```

```
await() 四步：
① 加入条件队列
② 完全释放锁（state 归零）—— 包括可重入的多次！
③ park 等待（直到被 signal 或中断）
④ 被唤醒后 → acquireQueued 重新抢锁（抢到锁后从 await 返回）

⚠️ "移入同步队列"是谁做的？是 signal 线程（transferForSignal → enq），
   不是被唤醒的线程。await 里的 while (!isOnSyncQueue(node)) 只是在等
   enq 完成（signal 之后短暂自旋），然后才进入 acquireQueued
```

### 6.4 signal() 全流程

```java
public final void signal() {
    if (!isHeldExclusively())           // ① 必须持有锁才能 signal
        throw new IllegalMonitorStateException();
    Node first = firstWaiter;           // ② 取队首等待节点
    if (first != null)
        doSignal(first);
}

private void doSignal(Node first) {
    do {
        if ((firstWaiter = first.nextWaiter) == null)
            lastWaiter = null;
        first.nextWaiter = null;        // 从条件队列断开
    } while (!transferForSignal(first) &&   // ③ 移到同步队列
             (first = firstWaiter) != null);
}

final boolean transferForSignal(Node node) {
    if (!compareAndSetWaitStatus(node, Node.CONDITION, 0))
        return false;                   // 已被取消 → 跳过
    Node p = enq(node);                 // ④ 入同步队列
    int ws = p.waitStatus;
    if (ws > 0 || !compareAndSetWaitStatus(p, ws, Node.SIGNAL))
        LockSupport.unpark(node.thread);  // ⑤ 必要时唤醒
    return true;
}
```

```
signal() 三步：
① 校验持有锁（跟 Object.notify 一样必须持锁）
② 条件队列队首出队
③ 移入同步队列（enq）→ 等待抢锁
④ 如果前驱已取消 → 直接 unpark（防止唤醒丢失）
```

### 6.5 await/signal vs wait/notify 对比

| 维度 | Object.wait/notify | Condition.await/signal |
|---|---|---|
| 所属 | Object（内置） | Lock（AQS） |
| 等待队列数量 | 1 个 | **多个（newCondition 任意个）** |
| 是否可中断 | 可（抛异常） | await / awaitUninterruptibly |
| 是否可超时 | wait(timeout) | await(timeout) / awaitNanos |
| 是否可指定唤醒 | 不能（notify 由实现决定唤哪一个，不保证公平） | **可以（多个 Condition 精确唤醒）** |
| 使用前提 | synchronized 内 | lock.lock() 后 |

## 8. 生产注意事项 & 常见坑点

### 🕳️ 坑 1：自定义 AQS 子类忘记实现模板方法

```java
// ❌ 直接继承 AQS 而不实现 tryAcquire
class BadLock extends AbstractQueuedSynchronizer { }

// 调用 acquire() → tryAcquire 抛 UnsupportedOperationException！

// ✅ 必须实现 tryAcquire/tryRelease 等模板方法
```

### 🕳️ 坑 2：state 的含义由子类决定，不要乱设

```java
// ❌ ReentrantLock 的 state 是重入次数
// 如果把 state 当"是否持有"（0/1），可重入就会失败
// 正确：lock 时 state+1，unlock 时 state-1，归零才释放
```

### 🕳️ 坑 3：await 会释放所有重入的锁

```java
// Condition.await 会完全释放锁（不管重入了几次）
// 返回时会重新获取全部重入次数（savedState 机制）
// → 不要在 await 前后对"锁状态"做假设
```

### 🕳️ 坑 4：signal 前必须持锁，但唤醒不保证立刻执行

```java
lock.lock();
try {
    condition.signal();  // 必须持锁（否则 IllegalMonitorStateException）
    // 被唤醒的线程不会立刻执行，它要先抢锁！
} finally {
    lock.unlock();
}
```

### 🕳️ 坑 5：忘记在 finally 中处理中断

```java
// ❌ 吞掉中断
try {
    lock.lockInterruptibly();
    condition.await();
} catch (InterruptedException e) {
    // 什么都不做
}

// ✅ 恢复中断标志或重新抛出
try {
    lock.lockInterruptibly();
    condition.await();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    throw e;
}
```

## 9. 面试高频考点

1. **AQS 是什么？核心三要素是什么？**
   → 同步器框架。state（同步状态）+ CLH 队列（等待队列）+ Node（节点）。模板方法模式。

2. **acquire 的全流程？**
   → tryAcquire → 失败 → addWaiter 入队 → acquireQueued 循环（前驱是 head 才 try，否则 park）→ 获得锁返回。

3. **为什么只有"前驱是 head"的节点才能尝试获取锁？**
   → FIFO 公平性。head 是"已获锁的占位符"（哑节点，不存线程），head.next 是等待最久的线程。保证"先来先得"。

4. **SIGNAL 状态的含义？为什么 park 前要把前驱设为 SIGNAL？**
   → 告诉前驱"释放锁时记得唤醒我"。避免"前驱释放锁了但没人唤醒我"的丢失唤醒问题。

5. **共享模式和独占模式的区别？传播机制是什么？**
   → 独占只有一个持有者；共享可多个同时。setHeadAndPropagate 在获取成功后继续唤醒下一个共享节点，让多余许可/计数"传播"下去。

6. **Condition 和 Object.wait/notify 的区别？**
   → 多条件队列、精确唤醒、可中断/超时控制更灵活。

### 练习 2：基于 AQS 实现信号量（45 分钟）★必做

```java
package com.sw.yang.concurrent.juc.aqs;

import org.junit.jupiter.api.Test;

import java.util.concurrent.locks.AbstractQueuedSynchronizer;

/**
 * 练习 2：基于 AQS 实现简易信号量（共享模式）
 *
 * 目标：
 * 1. 理解共享模式（tryAcquireShared/tryReleaseShared）
 * 2. 理解"返回值 <0 表示失败"的约定
 * 3. 验证同时最多 N 个线程进入
 */
public class MySemaphoreTest {

    static class MySemaphore {
        private static class Sync extends AbstractQueuedSynchronizer {
            Sync(int permits) {
                setState(permits);  // state = 剩余许可数
            }

            // 共享获取：许可数 -1
            @Override
            protected int tryAcquireShared(int acquires) {
                for (;;) {
                    int available = getState();
                    int remaining = available - acquires;
                    if (remaining < 0 || compareAndSetState(available, remaining)) {
                        return remaining;  // <0 表示获取失败
                    }
                }
            }

            // 共享释放：许可数 +1
            @Override
            protected boolean tryReleaseShared(int releases) {
                for (;;) {
                    int current = getState();
                    int next = current + releases;
                    if (compareAndSetState(current, next)) {
                        return true;
                    }
                }
            }
        }

        private final Sync sync;

        public MySemaphore(int permits) { sync = new Sync(permits); }

        public void acquire() { sync.acquireShared(1); }
        public void release() { sync.releaseShared(1); }
        public int availablePermits() { return sync.getState(); }
    }

    @Test
    public void testSemaphore() throws InterruptedException {
        MySemaphore semaphore = new MySemaphore(3);  // 最多 3 个并发
        final int[] concurrent = {0};
        final int[] maxConcurrent = {0};

        Thread[] threads = new Thread[10];
        for (int i = 0; i < 10; i++) {
            threads[i] = new Thread(() -> {
                try {
                    semaphore.acquire();
                    int cur = ++concurrent[0];
                    synchronized (maxConcurrent) {
                        if (cur > maxConcurrent[0]) maxConcurrent[0] = cur;
                    }
                    Thread.sleep(50);  // 模拟业务
                    concurrent[0]--;
                    semaphore.release();
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            });
            threads[i].start();
        }
        for (Thread t : threads) t.join();

        System.out.println("最大并发数: " + maxConcurrent[0]);
        System.out.println(maxConcurrent[0] <= 3 ? "✅ 最多 3 个并发（信号量生效）" : "❌ 超过 3 个并发！");
    }
}
```

### 练习 3：用 Lock + Condition 实现有界阻塞队列（60 分钟）★必做

```java
package com.sw.yang.concurrent.juc.aqs;

import org.junit.jupiter.api.Test;

import java.util.LinkedList;
import java.util.concurrent.locks.Condition;
import java.util.concurrent.locks.ReentrantLock;

/**
 * 练习 3：用 Lock + 双 Condition 实现有界阻塞队列（ArrayBlockingQueue 的简化版）
 *
 * 目标：
 * 1. 理解多 Condition 的"精确唤醒"
 * 2. 对比 wait/notifyAll 的"全部唤醒"
 */
public class MyBlockingQueueTest {

    static class MyBlockingQueue<E> {
        private final LinkedList<E> queue = new LinkedList<>();
        private final int capacity;
        private final ReentrantLock lock = new ReentrantLock();
        private final Condition notEmpty = lock.newCondition();  // 消费者等待：队列非空
        private final Condition notFull = lock.newCondition();   // 生产者等待：队列不满

        public MyBlockingQueue(int capacity) { this.capacity = capacity; }

        public void put(E e) throws InterruptedException {
            lock.lock();
            try {
                while (queue.size() >= capacity) {
                    notFull.await();      // 队列满 → 生产者等待
                }
                queue.add(e);
                notEmpty.signal();        // 精确唤醒一个消费者！（not notifyAll）
            } finally {
                lock.unlock();
            }
        }

        public E take() throws InterruptedException {
            lock.lock();
            try {
                while (queue.isEmpty()) {
                    notEmpty.await();     // 队列空 → 消费者等待
                }
                E e = queue.removeFirst();
                notFull.signal();         // 精确唤醒一个生产者！
                return e;
            } finally {
                lock.unlock();
            }
        }

        public int size() {
            lock.lock();
            try { return queue.size(); } finally { lock.unlock(); }
        }
    }

    @Test
    public void testBlockingQueue() throws InterruptedException {
        MyBlockingQueue<Integer> queue = new MyBlockingQueue<>(10);
        final int[] sum = {0};

        // 2 个生产者
        Thread[] producers = new Thread[2];
        for (int i = 0; i < 2; i++) {
            final int id = i;
            producers[i] = new Thread(() -> {
                try {
                    for (int j = 0; j < 100; j++) {
                        queue.put(id * 100 + j);
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }, "producer-" + id);
            producers[i].start();
        }

        // 3 个消费者
        Thread[] consumers = new Thread[3];
        for (int i = 0; i < 3; i++) {
            consumers[i] = new Thread(() -> {
                try {
                    while (true) {
                        Integer v = queue.take();
                        synchronized (sum) { sum[0] += v; }
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }, "consumer-" + i);
            consumers[i].start();
        }

        for (Thread t : producers) t.join();

        // 等消费者消费完（队列空 + 计数对得上）
        Thread.sleep(1000);
        System.out.println("队列残留: " + queue.size());

        // 计算理论总数：producer0 产出 0..99，producer1 产出 100..199
        int expected = 0;
        for (int i = 0; i < 100; i++) expected += i + (i + 100);
        System.out.println("预期总和: " + expected + ", 实际消费总和: " + sum[0]);
        System.out.println(sum[0] == expected ? "✅ 双 Condition 精确唤醒正确" : "❌ 数据不一致");
    }
}
```

## 11. 自测题

1. **AQS 的核心三要素是什么？各自的作用？**
   <details><summary>答案</summary>

   state：同步状态，volatile 保证可见性，含义由子类定义；
   CLH 队列：获取锁失败的线程排队等待（双向链表，CAS 入队）；
   Node：队列节点，存储线程、模式、waitStatus。
   </details>

2. **acquireQueued 中，为什么 park 前要把前驱节点的 waitStatus 设为 SIGNAL？**
   <details><summary>答案</summary>

   防止丢失唤醒。如果节点直接 park 而不设置 SIGNAL，前驱释放锁时不知道"有人等着被唤醒"，就不会调用 unpark，导致线程永远睡下去。SIGNAL 相当于"预约唤醒"。
   </details>

3. **为什么只有前驱是 head 的节点才尝试获取锁？这意味着什么公平性？**
   <details><summary>答案</summary>

   head 是"已持有锁"的哑节点，head.next 是排队最久的线程。只有它能尝试获取 → FIFO 先进先出。这是 AQS 的"排队公平性"。
   </details>

4. **共享模式的传播（Propagate）机制解决了什么问题？**
   <details><summary>答案</summary>

   防止"许可/信号浪费"。比如 Semaphore 释放 1 个许可，唤醒队首后队首成功获取（还剩 2 个许可），传播机制会继续唤醒下一个，直到许可耗尽或没有等待者。
   </details>

5. **await() 为什么能"完全释放"锁？重入多次怎么处理？**
   <details><summary>答案</summary>

   因为 await 期间其他线程要进入临界区调用 signal，如果不完全释放锁，死锁。实现：fullyRelease 记录当前 state（含重入次数）并归零；返回时 acquireQueued(node, savedState) 恢复原来的重入次数。
   </details>

6. **tryAcquire 返回 boolean，tryAcquireShared 返回 int，为什么返回值类型不同？**
   <details><summary>答案</summary>

   独占：要么成功要么失败 → boolean。
   共享：不仅要表示"成功/失败"，还要传递"剩余资源数"（如剩余许可）→ int。
   返回值 >= 0 表示成功（值本身有意义），< 0 表示失败。
   </details>
