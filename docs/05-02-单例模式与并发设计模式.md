## 1. 单例模式的并发安全（🛠️ 必考）

### 1.1 五种写法对比总览

| 写法 | 线程安全 | 延迟加载 | 防反射 | 防序列化 | 推荐度 |
|---|---|---|---|---|---|
| 饿汉式 | ✅ | ❌（类加载即创建） | ❌ | ❌ | 简单场景 |
| DCL 双检锁 | ✅ | ✅ | ❌ | ❌ | 面试必考 |
| 静态内部类 | ✅ | ✅ | ❌ | ❌ | **推荐** |
| 枚举 | ✅ | ✅ | ✅ | ✅ | **最推荐** |
| ThreadLocal 版 | ✅（每线程一份） | ✅ | ❌ | ❌ | 特殊场景 |

> ⚠️ 注：ThreadLocal 版严格说**不是单例**——它是"每个线程一个独立实例"，适合"每线程需要独立状态"的场景（如每线程一个 SimpleDateFormat）。放在此表只为对比完整性。

### 1.2 饿汉式

```java
// 类加载时创建实例（线程安全由类加载机制保证）
public class HungrySingleton {
    private static final HungrySingleton INSTANCE = new HungrySingleton();

    private HungrySingleton() {}

    public static HungrySingleton getInstance() {
        return INSTANCE;
    }
}

// 优点：简单、线程安全
// 缺点：类加载就创建 → 不用也创建 → 浪费内存
//      （如果构造很重，且可能永远用不到）
```

### 1.3 DCL 双检锁（面试必考）⭐

```java
public class DclSingleton {
    // ★ volatile 必须！防止 new 的重排序（半初始化对象）
    private static volatile DclSingleton instance;

    private DclSingleton() {}

    public static DclSingleton getInstance() {
        if (instance == null) {                    // ① 第一次检查（无锁快速路径）
            synchronized (DclSingleton.class) {
                if (instance == null) {            // ② 第二次检查（持锁复查）
                    instance = new DclSingleton(); // ③ 创建
                }
            }
        }
        return instance;
    }
}
```

```
DCL 的三个关键点（面试逐条讲）：

① 第一次检查（instance == null）：
   性能优化：大多数时候实例已存在，直接返回，避免每次都加锁

② 第二次检查（持锁后 instance == null）：
   防止重复创建：两个线程同时通过① → 线程A 拿锁创建 → 释放
   线程B 拿锁 → 如果不检查② → 又创建一个 → 两个实例！

③ volatile（为什么必须）：
   new DclSingleton() 分三步：
     1. 分配内存
     2. 初始化对象
     3. 引用赋值
   如果 2、3 被重排序（先赋值后初始化）：
     线程A 执行到 3（instance 非 null 但未初始化）
     线程B 在① 看到 instance != null → 直接返回半初始化对象 → 崩溃！
   volatile 禁止 2、3 重排序 → 安全
```

### 1.4 静态内部类（推荐）⭐

```java
public class HolderSingleton {
    private HolderSingleton() {}

    // 静态内部类：类加载时才初始化（延迟加载）
    private static class Holder {
        // 类加载机制保证：只会初始化一次（线程安全）
        private static final HolderSingleton INSTANCE = new HolderSingleton();
    }

    public static HolderSingleton getInstance() {
        return Holder.INSTANCE;
    }
}
```

```
为什么推荐静态内部类？

① 线程安全：类加载由 JVM 保证只执行一次（<clinit> 是线程安全的）
② 延迟加载：只有首次调用 getInstance() 才加载 Holder 类 → 才创建实例
③ 代码简单：没有 synchronized / volatile / null 检查

对比 DCL：
  同样安全 + 延迟加载，但代码更简单、无并发细节
  → 生产首选（不需要防反射时）
```

### 1.5 枚举单例（最推荐）⭐

```java
public enum EnumSingleton {
    INSTANCE;   // 唯一实例

    // 可以有自己的字段和方法
    private String config;

    public void setConfig(String config) {
        this.config = config;
    }

    public String getConfig() {
        return config;
    }
}

// 使用
EnumSingleton.INSTANCE.setConfig("prod");
```

```
枚举单例的四个天然保证（Effective Java 推荐）：

① 线程安全：枚举创建由 JVM 保证（类加载）
② 防反射：反射 newInstance() 遇到枚举直接抛 IllegalArgumentException
   （Enum 的构造器逻辑禁止反射创建）
③ 防序列化：序列化机制对枚举有特殊处理
   （反序列化返回的是已有的单例，不会创建新实例）
④ 延迟加载：首次访问时才初始化（懒加载）

结论：需要绝对安全的单例 → 枚举
     普通场景 → 静态内部类
```

### 1.6 防反射 / 防序列化攻击（◈◈）

```java
// 反射攻击：私有构造器也能被调用！
public class Singleton {
    private static volatile Singleton instance;
    private Singleton() {}

    public static Singleton getInstance() { ... }
}

// 攻击代码：
Constructor<Singleton> c = Singleton.class.getDeclaredConstructor();
c.setAccessible(true);              // 绕过 private
Singleton s2 = c.newInstance();     // 创建了第二个实例！

// ✅ 防御 1：构造器里检查
private Singleton() {
    if (instance != null) {
        throw new RuntimeException("禁止反射创建单例");
    }
}
// ⚠️ 局限：如果反射攻击发生在单例"首次创建之前"
//    （第一次就 newInstance）→ instance 还是 null → 防御无效！
//    多线程同时反射调用构造器也存在竞态。
//    → 这个防御只防"已有单例后的二次创建"

// ✅ 防御 2：用枚举（天然防反射，最彻底）
```

```java
// 序列化攻击：反序列化会创建新实例
// 序列化 → 反序列化 → 得到两个不同的实例

// ✅ 防御：实现 readResolve() 返回已有实例
protected Object readResolve() {
    return getInstance();   // 反序列化时返回单例，而不是新对象
}
```

## 2. 生产者-消费者模式（🛠️ 核心）

### 2.1 三种实现对比（回顾）

| 实现 | 代码量 | 精确唤醒 | 生产推荐 |
|---|---|---|---|
| wait/notifyAll | 最多（50 行） | ❌ | ❌ |
| Lock + Condition | 中等（40 行） | ✅ 双条件 | 手写时 |
| BlockingQueue | 最少（10 行） | ✅（内部） | **✅ 生产首选** |

```
三种实现已经分别在 02-03（wait/notify）、03-01（Lock+Condition）、
03-05（BlockingQueue）练过，这里总结选型：

  - 简单业务 → BlockingQueue（一行搞定）
  - 需要多条件精确控制 → Lock + Condition
  - 学习原理 → wait/notify
```

### 2.2 背压（Back Pressure）处理 🛠️

```
问题：生产者生产太快，消费者消费不过来 → 队列堆积

背压 = 让生产者"感知并适应"消费者的处理能力

四种背压策略：
  ① 阻塞（BlockingQueue.put）：
     队列满 → 生产者阻塞 → 天然背压
     ✅ 简单；❌ 生产者被卡住

  ② 有界队列 + 拒绝策略：
     队列满 → 丢弃/降级/记录
     ✅ 快速失败；❌ 可能丢数据

  ③ 有界队列 + CallerRuns：
     队列满 → 生产者自己执行（削峰）
     ✅ 不丢任务 + 自动限速

  ④ 动态调参：
     监控队列积压 → 动态调整消费者线程数
     ✅ 自适应；❌ 实现复杂

生产实践：
  先选 ②或③（有界队列）
  + 监控队列积压告警
  + 必要时动态扩容消费者
```

## 3. 限流器模式（🛠️ 核心）

### 3.1 四种限流算法

| 算法 | 原理 | 特点 | 适用 |
|---|---|---|---|
| 固定窗口计数器 | 每秒计数，超过阈值拒绝 | 简单，但**窗口临界突刺** | 简单限流 |
| 滑动窗口 | 窗口内细分格子计数 | 平滑，解决临界突刺 | 较平滑限流 |
| 漏桶 | 匀速流出（固定速率） | **平滑流出**，不管流入 | 平滑输出 |
| 令牌桶 | 匀速放令牌，突发可取多个 | **允许突发**（有令牌就行） | 允许突发流量 |

```
四算法对比示意图：

固定窗口：每秒最多 N 个
  |████████████|  <- 1 秒
  临界问题：0.9s 和 1.1s 各 N 个 → 0.2s 内 2N 个

滑动窗口：细粒度统计
  |██|██|██|██|  <- 每格统计，窗口滑动
  解决临界突刺

漏桶：匀速流出
  流入 ──→ [桶：容量固定] ──→ 匀速流出（固定速率）
  突发 → 桶溢出 → 丢弃；流出永远匀速

令牌桶：允许突发
  [令牌桶：每 1/r 秒放一个令牌，桶容量 b]
  请求 → 有令牌？→ 拿走令牌，放行（可连续拿多个 → 突发）
  无令牌 → 拒绝/等待
```

### 3.2 基于 Semaphore 的简易限流（并发数限流）

```java
// 限流类型 1：并发数限流（同时最多 N 个请求在处理）
public class ConcurrencyLimiter {
    private final Semaphore semaphore = new Semaphore(100);  // 最多 100 并发

    public boolean tryAcquire() {
        return semaphore.tryAcquire();   // 拿不到 → false（快速失败）
    }

    public void release() {
        semaphore.release();
    }
}

// 使用：
if (!limiter.tryAcquire()) {
    return "系统繁忙，请稍后重试";   // 降级
}
try {
    return doBusiness();
} finally {
    limiter.release();
}
```

### 3.3 基于令牌桶的手写限流器（★ 练习核心）

```java
// 简易令牌桶实现
public class TokenBucketLimiter {
    private final int capacity;          // 桶容量（最大令牌数）
    private final double refillRate;     // 每秒补充的令牌数
    private double tokens;               // 当前令牌数
    private long lastRefillTime;         // 上次补充时间

    public TokenBucketLimiter(int capacity, double refillRate) {
        this.capacity = capacity;
        this.refillRate = refillRate;
        this.tokens = capacity;          // 初始装满
        this.lastRefillTime = System.currentTimeMillis();
    }

    public synchronized boolean tryAcquire() {
        refill();                        // ① 先补充令牌
        if (tokens >= 1) {
            tokens -= 1;                 // ② 有令牌 → 拿走
            return true;
        }
        return false;                    // ③ 无令牌 → 拒绝
    }

    private void refill() {
        long now = System.currentTimeMillis();
        double elapsed = (now - lastRefillTime) / 1000.0;   // 经过的秒数
        tokens = Math.min(capacity, tokens + elapsed * refillRate);  // 补充
        lastRefillTime = now;
    }
}
```

```
令牌桶的关键特性：
  ① 匀速补充：每 1/refillRate 秒产生一个令牌
  ② 桶容量：最多攒 capacity 个（允许突发）
  ③ 请求消耗：每个请求拿走一个令牌
  ④ 无令牌 → 拒绝（限流生效）

与漏桶的区别：
  漏桶：流出速率恒定（突发会被"摊平"）
  令牌桶：只要桶里有令牌就能走（允许突发流量）
```

## 4. 读写锁模式（缓存）◈◈

```java
// 读多写少缓存：读锁并行，写锁独占
public class CacheWithLock {
    private final Map<String, Object> cache = new HashMap<>();
    private final ReentrantReadWriteLock lock = new ReentrantReadWriteLock();
    private final Lock readLock = lock.readLock();
    private final Lock writeLock = lock.writeLock();

    public Object get(String key) {
        readLock.lock();
        try {
            return cache.get(key);
        } finally {
            readLock.unlock();
        }
    }

    public void put(String key, Object value) {
        writeLock.lock();
        try {
            cache.put(key, value);
        } finally {
            writeLock.unlock();
        }
    }
}

// 升级版：缓存失效时"只允许一个线程重建"
public Object getOrLoad(String key) {
    // ① 读锁读
    readLock.lock();
    Object v;
    try {
        v = cache.get(key);
    } finally {
        readLock.unlock();
    }
    if (v != null) return v;          // 命中 → 返回

    // ② 未命中 → 写锁重建（double-check 防止重复重建）
    writeLock.lock();
    try {
        v = cache.get(key);           // 再次检查（其他线程可能已重建）
        if (v == null) {
            v = loadFromDB(key);      // 只有没被重建才加载
            cache.put(key, v);
        }
        return v;
    } finally {
        writeLock.unlock();
    }
}
```

```
缓存 + 锁的要点：
  读多写少 → 读写锁（读读并行）
  缓存击穿防护 → double-check（先查再锁再查）
  分布式环境 → 用分布式锁（阶段六）
```

## 6. 面试高频考点

1. **DCL 的 volatile 为什么必须？**
   → new 的三步（分配/初始化/赋值）可能重排序 → 其他线程看到半初始化对象。volatile 禁止重排序。

2. **五种单例写法的对比？生产选哪个？**
   → 普通场景静态内部类（简单+延迟+安全）；绝对安全（防反射序列化）用枚举；面试考 DCL。

3. **生产者消费者的三种实现？生产用哪个？**
   → wait/notify（原理）、Lock+Condition（精确唤醒）、BlockingQueue（生产首选）。

4. **四种限流算法的区别？**
   → 固定窗口（临界突刺）/ 滑动窗口（平滑）/ 漏桶（匀速流出）/ 令牌桶（允许突发）。

5. **什么是背压？怎么处理？**
   → 生产快于消费时的反馈机制。有界队列+拒绝/CallerRuns/阻塞/动态扩容。

## 7. 实战练习

### 练习 1：单例写法对比（45 分钟）★必做

```java
package com.sw.yang.concurrent.pattern;

import org.junit.jupiter.api.Test;

import java.lang.reflect.Constructor;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicReference;

/**
 * 练习 1：单例模式并发验证 + 反射攻击演示
 *
 * 目标：
 * 1. 验证 DCL / 静态内部类 / 枚举三种单例在多线程下都是单例
 * 2. 演示反射攻击 DCL，对比枚举天然防反射
 */
public class SingletonTest {

    // DCL 单例
    static class DclSingleton {
        private static volatile DclSingleton instance;
        private DclSingleton() {}
        public static DclSingleton getInstance() {
            if (instance == null) {
                synchronized (DclSingleton.class) {
                    if (instance == null) {
                        instance = new DclSingleton();
                    }
                }
            }
            return instance;
        }
    }

    // 静态内部类单例
    static class HolderSingleton {
        private HolderSingleton() {}
        private static class Holder {
            private static final HolderSingleton INSTANCE = new HolderSingleton();
        }
        public static HolderSingleton getInstance() {
            return Holder.INSTANCE;
        }
    }

    // 枚举单例
    enum EnumSingleton {
        INSTANCE
    }

    /**
     * 并发验证：100 个线程同时获取，必须是同一个实例
     */
    @Test
    public void testConcurrentSingleton() throws InterruptedException {
        int threads = 100;
        CountDownLatch start = new CountDownLatch(1);
        CountDownLatch done = new CountDownLatch(threads);
        AtomicReference<DclSingleton> ref = new AtomicReference<>();

        for (int i = 0; i < threads; i++) {
            new Thread(() -> {
                try {
                    start.await();              // 同时起跑
                    ref.compareAndSet(null, DclSingleton.getInstance());
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } finally {
                    done.countDown();
                }
            }).start();
        }
        start.countDown();
        done.await();

        // 再拿一个比较
        DclSingleton another = DclSingleton.getInstance();
        System.out.println(ref.get() == another
                ? "✅ 100 线程并发获取 DCL 单例 → 同一个实例"
                : "❌ 出现了多个实例！");

        // 静态内部类
        System.out.println(HolderSingleton.getInstance() == HolderSingleton.getInstance()
                ? "✅ 静态内部类单例"
                : "❌ 静态内部类异常");
        // 枚举
        System.out.println(EnumSingleton.INSTANCE == EnumSingleton.INSTANCE
                ? "✅ 枚举单例"
                : "❌ 枚举异常");
    }

    /**
     * 反射攻击演示：DCL 可被反射破坏，枚举不能
     */
    @Test
    public void testReflectionAttack() {
        // 攻击 DCL
        try {
            Constructor<DclSingleton> c = DclSingleton.class.getDeclaredConstructor();
            c.setAccessible(true);
            DclSingleton hacked = c.newInstance();
            System.out.println("❌ DCL 被反射攻击：创建了第二个实例！" +
                    (hacked != DclSingleton.getInstance()));
        } catch (Exception e) {
            System.out.println("DCL 构造器抛异常: " + e.getMessage());
        }

        // 攻击枚举（枚举没有无参构造器，且 JVM 禁止反射创建）
        try {
            Constructor<EnumSingleton> c = EnumSingleton.class.getDeclaredConstructor(String.class, int.class);
            c.setAccessible(true);
            EnumSingleton hacked = c.newInstance("HACKED", 99);
            System.out.println("❌ 枚举被反射攻击？" + (hacked != EnumSingleton.INSTANCE));
        } catch (Exception e) {
            System.out.println("✅ 枚举天然防反射: " + e.getClass().getSimpleName());
        }
    }
}
```

### 练习 2：令牌桶限流器（60 分钟）★必做

```java
package com.sw.yang.concurrent.pattern;

import org.junit.jupiter.api.Test;

import java.util.concurrent.atomic.AtomicInteger;

/**
 * 练习 2：手写令牌桶限流器 + 并发验证
 *
 * 目标：
 * 1. 理解令牌桶算法（匀速补充 + 桶容量 + 允许突发）
 * 2. 验证限流效果：请求速率被控制在 refillRate 附近
 */
public class TokenBucketTest {

    /**
     * 令牌桶实现（synchronized 保证线程安全）
     */
    static class TokenBucketLimiter {
        private final int capacity;       // 桶容量（最大令牌数）
        private final double refillRate;  // 每秒补充的令牌数
        private double tokens;            // 当前令牌数
        private long lastRefillTime;      // 上次补充时间

        TokenBucketLimiter(int capacity, double refillRate) {
            this.capacity = capacity;
            this.refillRate = refillRate;
            this.tokens = capacity;
            this.lastRefillTime = System.currentTimeMillis();
        }

        public synchronized boolean tryAcquire() {
            refill();
            if (tokens >= 1) {
                tokens -= 1;
                return true;
            }
            return false;
        }

        private void refill() {
            long now = System.currentTimeMillis();
            double elapsed = (now - lastRefillTime) / 1000.0;
            tokens = Math.min(capacity, tokens + elapsed * refillRate);
            lastRefillTime = now;
        }
    }

    @Test
    public void testTokenBucket() throws InterruptedException {
        // 每秒 20 个令牌，桶容量 20（允许 1 秒突发）
        TokenBucketLimiter limiter = new TokenBucketLimiter(20, 20.0);
        AtomicInteger passed = new AtomicInteger(0);
        AtomicInteger rejected = new AtomicInteger(0);

        // 10 个线程疯狂请求 2 秒
        Thread[] threads = new Thread[10];
        for (int i = 0; i < 10; i++) {
            threads[i] = new Thread(() -> {
                long deadline = System.currentTimeMillis() + 2000;
                while (System.currentTimeMillis() < deadline) {
                    if (limiter.tryAcquire()) {
                        passed.incrementAndGet();
                    } else {
                        rejected.incrementAndGet();
                    }
                }
            });
            threads[i].start();
        }
        for (Thread t : threads) t.join();

        System.out.println("放行: " + passed.get() + " 个请求");
        System.out.println("拒绝: " + rejected.get() + " 个请求");
        System.out.println("理论放行上限: 2 秒 × 20/s = 40（加上初始桶的 20 = 60）");
        System.out.println(passed.get() <= 60
                ? "✅ 限流生效（放行数未超过令牌上限）"
                : "❌ 限流失效！");
    }
}
```

### 练习 3：缓存击穿防护（45 分钟）

```java
package com.sw.yang.concurrent.pattern;

import org.junit.jupiter.api.Test;

import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.locks.ReentrantReadWriteLock;

/**
 * 练习 3：缓存击穿防护 —— 缓存失效时只允许一个线程重建
 *
 * 场景：热点 key 过期瞬间，100 个请求同时来 → 只能有一个去查库
 */
public class CacheBreakdownTest {

    static class SafeCache {
        private final Map<String, Object> cache = new HashMap<>();
        private final ReentrantReadWriteLock lock = new ReentrantReadWriteLock();
        private final AtomicInteger dbLoadCount = new AtomicInteger(0);  // 查库次数

        public Object getOrLoad(String key) {
            // ① 读锁快速路径
            lock.readLock().lock();
            Object v;
            try {
                v = cache.get(key);
            } finally {
                lock.readLock().unlock();
            }
            if (v != null) return v;

            // ② 写锁重建（double-check）
            lock.writeLock().lock();
            try {
                v = cache.get(key);          // 再次检查（别人可能已重建）
                if (v == null) {
                    v = loadFromDB(key);     // 只有第一次进来的人才查库
                    cache.put(key, v);
                }
                return v;
            } finally {
                lock.writeLock().unlock();
            }
        }

        private Object loadFromDB(String key) {
            dbLoadCount.incrementAndGet();   // 模拟查库
            try { Thread.sleep(50); } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
            return "data-" + key;
        }

        int getDbLoadCount() { return dbLoadCount.get(); }
    }

    @Test
    public void testCacheBreakdown() throws InterruptedException {
        SafeCache cache = new SafeCache();
        int threads = 100;
        CountDownLatch start = new CountDownLatch(1);
        CountDownLatch done = new CountDownLatch(threads);

        // 100 个线程同时请求同一个 key（模拟缓存击穿）
        for (int i = 0; i < threads; i++) {
            new Thread(() -> {
                try {
                    start.await();
                    cache.getOrLoad("hot-key");
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } finally {
                    done.countDown();
                }
            }).start();
        }
        start.countDown();
        done.await();

        System.out.println("100 个并发请求，实际查库次数: " + cache.getDbLoadCount());
        System.out.println(cache.getDbLoadCount() == 1
                ? "✅ 击穿防护生效（只有 1 次查库）"
                : "❌ 击穿了！查库 " + cache.getDbLoadCount() + " 次");
    }
}
```

## 8. 自测题

1. **DCL 的 volatile 为什么必须？去掉会发生什么？**
   <details><summary>答案</summary>

   new 操作分三步（分配内存/初始化/赋值引用），2、3 可能重排序。去掉 volatile → 其他线程可能在①看到"非 null 但未初始化"的实例 → 返回半初始化对象 → 崩溃。概率低但偶发，最难排查。
   </details>

2. **静态内部类为什么线程安全又延迟加载？**
   <details><summary>答案</summary>

   静态内部类只有在首次被访问时才加载（延迟加载）；类加载的 <clinit> 由 JVM 保证只执行一次且线程安全（类加载机制天然互斥）。
   </details>

3. **枚举单例为什么防反射、防序列化？**
   <details><summary>答案</summary>

   反射：JVM 禁止用反射创建枚举实例（newInstance 对枚举抛 IllegalArgumentException）；序列化：枚举反序列化有特殊处理，返回已有的单例实例。
   </details>

4. **令牌桶和漏桶的区别？各自适合什么场景？**
   <details><summary>答案</summary>

   漏桶：流出速率恒定（突发被摊平），适合平滑输出；令牌桶：桶里攒的令牌可被突发消耗（允许突发），适合允许短时突发的场景（如秒杀瞬间放量）。
   </details>

5. **缓存击穿怎么防护？**
   <details><summary>答案</summary>

   ① 本地：读写锁 + double-check（先读锁查 → 未命中写锁重建 → 再查一次）；② 分布式：分布式锁（阶段六）；③ 其他：热点 key 永不过期 + 逻辑过期。
   </details>
