## 可见性

### 1. 定义

可见性：线程 A 修改了共享变量，线程 B 应能读到这个修改——不是墙钟上的"立即"。

"读到"有**确定的可见点**：当写与读之间存在同步保证（happens-before 边）时，越过该边之后的读必看到该写；没有这条边，B 读旧值不违反任何承诺（硬件为何能造成这种情况，见 §3~§4）。

### 2. 整机存储阶梯（先看全景）

| 存储 | 是什么 | 归谁 | 放什么 | 量级 | 一致性由谁保证 |
|---|---|---|---|---|---|
| 寄存器 | 执行单元里的运算暂存区 | 本核 | 正在计算的临时值（可为纯中间结果，与主存无关） | ~百 B / 1 周期 | 无——仅供本核使用，其他核不可见 |
| Store Buffer 写缓冲 | 执行单元与 L1 之间的待写队列 | 本核 | 已执行完、尚未写进 L1 的写 | 几十~上百条 | 硬件自动排空进 L1；屏障可强制排空 |
| L1 缓存 | 本核一级缓存 | 本核 | 主存内容的副本 | ~几十 KB / 几周期 | MESI 自动同步 |
| L2 缓存 | 本核二级缓存（L1 未命中时查找） | 本核 | 主存内容的副本 | ~几 MB / 十几周期 | MESI 自动同步 |
| L3 缓存 | 全核共享的缓存 | 多核共享 | 主存内容的副本 | ~几十 MB | 多核共享，天然一致 |
| 主存 | 所有副本的权威源 | 整机 | 数据的原始存放位置 | GB 级 / 上百周期 | 本身是源，无需同步 |

### 3. 硬件已保证的可见性

一致性协议按**缓存行的地址**登记并同步副本：
- **L1 / L2**：MESI 自动同步——某核写入某缓存行后，向持有同一行副本的其他核广播作废；其他核下次读取时该行已失效，重新拉取。
- **L3**：多核共享，各核副本经它汇合，天然一致。

**主存**是所有副本的权威源。对**已发布到缓存的行**，L1/L2/L3 即使暂时读到旧值，也会在某个时刻被硬件纠正，**不会造成"永远看不到"**——但这个保证以"读写仍经缓存行发生"为前提。
但一致性协议只追踪"已发布到缓存的行"：一个值若**还没进入任何缓存行**（Store Buffer 中的写）、或**根本没有地址**（寄存器中的值），协议看不见它——这两处即下一节的原因。

### 4. 原因

**写侧——写还不是"已发布的行"**
写缓存行前必须先独占该行（作废其他核副本并等确认），这是跨核往返；直接等会让流水线停住，所以写先进 Store Buffer。于是一次写有两个时刻：**指令完成**（值进本核 Store Buffer，本核经转发即见）与**别人可见**（排空进 L1、作废广播完成后）。两刻不重合，读方落在中间就读到旧值；该窗口随排空进 L1 结束，是有界的。

**读侧——读不再发生**
循环内变量无同步更新，JIT 判定其不变，把值提升进寄存器，循环体不再发起读取。

## 原子性

### 1. 定义

原子性：操作**不可分割**——其他线程只看到操作前或操作后，看不到中间态；线程中途被切走不破坏它，只要切走时没留下中间态。

### 2. 原因

"读 → 改 → 写"分两次独立访存（读、写），二者之间可插入别人的同款操作，两次修改只生效一次（丢更新）。插入来源：

- **单核**：读后、写前被时间片切走；期间别人完成一次读改写；自己恢复后用旧值算的结果写回——覆盖对方；
- **多核**：无需切换，两核各自读改写同时进行，都从同一旧值起算，后写覆盖先写。

### 3. 解决办法

让"读 → 改 → 写"不被插入：
- **synchronized**：整段读改写框成临界区，同一时刻只有一个线程在执行（互斥）；
- **CAS / AtomicInteger**：`lock cmpxchg` 把"比较 + 交换"做成**单条原子指令**，本身不被插入；期望值不符（已被别人改）则重读重试。

## 有序性

### 1. 定义

有序性：共享变量的操作应按源码书写顺序生效（先写先见）。JMM 只保证由 happens-before 边相连的读写有序，边外任何顺序都合法。

### 2. 原因

编译器/JIT、CPU 为提速重排无依赖指令，只保证单线程结果不变（有数据依赖的必须保序）。跨线程无 HB，读方会看到重排后的顺序。

### 3. 解决办法

用 happens-before 边钉顺序：
- **volatile**：release 钉"写之前的普通写"、acquire 钉"读之后的普通读写"，方向不对称（详见下文《Volatile》）；
- **synchronized**：释放锁 happens-before 后续获取锁，临界区写对后继者有序可见。

## Volatile

volatile 变量两侧各是一个同步点，与配对线程构成一次握手。它把"跨线程"变成一条 happens-before 链，关键在两侧各钉相邻的普通访问、且方向不对称。

### 1. 两侧语义

条款：对 volatile 变量 v 的写 happens-before 之后任意线程对 v 的读。

- 写 v = release（发布）：读到本次 v 写的线程，连带可见 v 写之前本线程的全部修改。
- 读 v = acquire（收获）：本线程读到某次 v 写之后，其后续访问可见该次写发布的修改。

### 2. 一次握手与屏障位置

写方                        读方
data = 42;        // ①     while (!ready);          // ③ volatile 读
ready = true;     // ②     use(data);               // ④ 普通读

"读方必见 42"要求每环节不被重排拆开：
①→②：前序普通写先于发布点落定；②→③：写 v HB 读 v（同步）；③→④：消费后于收获点。

屏障布局（JSR-133 cookbook 实现）：
- v 写前插 StoreStore：钉"之前"的普通写，不落于 v 写之后；
- v 写后插 StoreLoad：钉后续 volatile 读，不越过 v 写；
- v 读后插 LoadLoad + LoadStore：钉"之后"的普通读写，不越过 v 读。

### 3. 屏障全景：4 种、命名即规则

屏障是插在两内存操作之间、命令二者不互相跨越的指令。名 = 规则：X = 屏障前的操作种类，Y = 屏障后的，保证 X 不落到 Y 之后。操作种类只有 Load/Store 两类、排两位 → 2×2 = 4 种：

| 屏障 | 规则 |
|---|---|
| LoadLoad | 前 Load 不落到后 Load 之后 |
| LoadStore | 前 Load 不落到后 Store 之后 |
| StoreStore | 前 Store 不落到后 Store 之后 |
| StoreLoad | 前 Store 不落到后 Load 之后（最强） |

StoreLoad 最贵：写对别的核可见，要把写从 Store Buffer 刷出去传播；其余三种只约束顺序、不等传播。volatile 用全这 4 种：写前 StoreStore、写后 StoreLoad、读后 LoadLoad + LoadStore（见 §2）。

平台按"自己会乱序哪些"选用屏障：
- x86（TSO）只允许 Store-Load 重排（后读越过滞留在写缓冲的前写），load-load / store-store / load-store 天然保序 → volatile 读免费（读后要的 LoadLoad/LoadStore 架构不会乱序），volatile 写 = 普通写 + `lock` 前缀（强制排空写缓冲，兼防 Store-Load）；
- ARM 弱序四种都可能乱序，该插的都插。

JDK 暴露同一粒度：`Unsafe`/`VarHandle` 的 `loadFence`≈LoadLoad、`storeFence`≈StoreStore、`fullFence`≈四者全管。

### 4. 方向为何不对称

写侧只禁一种穿越：把 v 写**之前**的普通写拖到 v 写**之后**。
- 为什么禁：v 写是读者获准观察的发布点，前序写若迟到才可见，读者看到 ready=true 时 data 仍旧值。此洞读方堵不上：读方再晚读 data，也早不过写方此刻尚未落定的写，只能由写方把前序写钉在发布前。
- 为何不禁反向：把 v 写之后的普通写提前，只会让读者多看见一份本不保证可见的更新，超出 release 承诺，方向无害。

读侧只禁一种穿越：把 v 读**之后**的普通读写提到 v 读**之前**。
- 为什么禁：读后的操作属握手之后的消费，提前 = 未握手先取数，读到旧值。
- 为何不禁反向：把 v 读之前的动作沉到读后，只会看到更晚状态，不会产生"越过握手读旧值"，方向无害。

一句话：release 向后挡（之前的不许迟到），acquire 向前挡（之后的不许提前）；缺任一侧，握手即断。

### 5. 物理原因：程序序 ≠ 对外可见序

"先 data 后 ready"默认不保证 data 先对外可见：编译器可把 data 的 store 下沉（sink）到 ready 之后；CPU 写先进 Store Buffer，排空节奏不受程序序约束。屏障命令两端不跨越，把程序序固化为对外可见序。

## 根源：并发与优化

```text
[安全基线] 单核 · 任务整段跑 · 单一内存 · 按源码序执行
   读=最新 / 一步做完 / 序=源码 —— 三大问题都不存在
  │  想更快，离开基线
  ▼
两大手段
  ├─ 并发：任务在指令粒度交错（单核分时 / 多核并行）
  │     └ 复合操作跨多条指令，指令之间可被交错切开
  │          → 原子性（丢更新）    ← 只需并发；缓存、乱序都不需要
  │
  └─ 优化：偏离"单一内存 · 按源码序"的朴素模型
        ├ 副本（每核私有缓存）/ Store Buffer / JIT 读不再发起
        │     并发观察到滞后 → 可见性（读旧值）
        └ 指令重排（编译 / CPU 乱序）
              并发观察到乱序 → 有序性（半初始化）

前提：还必须有"≥2 线程无同步访问同一共享变量"——否则无从交错、也无人观察。
```
