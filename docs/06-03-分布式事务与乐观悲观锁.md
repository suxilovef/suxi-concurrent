## 1. CAP 定理（⭐ 必考）

### 1.1 三个特性

```
CAP 定理（Brewer 提出，Gilbert 证明）：

C - Consistency（一致性）：所有节点同一时刻看到同一份数据
A - Availability（可用性）：每个请求都能得到响应（不保证最新）
P - Partition Tolerance（分区容错性）：网络分区时系统仍能运行
```

### 1.2 为什么 P 必须选（⭐ 必考）

```
网络分区（Partition）是"必然发生"的：
  机器宕机、网络抖动、机房隔离 → 节点之间失去联系

分区发生时，C 和 A 不可兼得：

  节点 1 和节点 2 失联，客户端向节点 1 写数据：
    ┌─ 保证 C：等节点 2 确认后才响应 → 节点 2 不可达 → 永远等 → 不可用 ✗
    └─ 保证 A：先响应成功 → 节点 2 的数据不一致 → 一致性被破坏 ✗

→ 分区必然发生 → 必须在 C 和 A 之间二选一：
  CP 系统：强一致（如 ZooKeeper、etcd）—— 分区时拒绝服务
  AP 系统：高可用（如 Redis 集群、Eureka）—— 分区时数据可能旧

→ "P 必须选"的真实含义：
  不是"选不选 P"，而是"承认 P 必然发生，然后在 C 和 A 中做选择"
```

### 1.3 常见系统的 CAP 取向

| 系统 | 取向 | 说明 |
|---|---|---|
| ZooKeeper / etcd | **CP** | 分区时宁可不可用，也要一致 |
| Redis 主从 | **AP** | 主从异步复制，从节点可能旧 |
| Eureka | **AP** | 注册中心可用性优先 |
| Nacos | 可配置 | 支持 CP 和 AP 切换 |
| 多数互联网业务 | **AP** | 最终一致 + 幂等兜底 |

## 2. BASE 理论

```
BASE = Basically Available（基本可用）+ Soft state（软状态）+ Eventually consistent（最终一致）

针对 AP 系统的补充理论：
  C 做不到强一致 → 退而求其次：最终一致

① 基本可用（Basically Available）
   系统大部分时间可用；故障时允许降级（限流、返回旧缓存）

② 软状态（Soft State）
   允许系统存在中间状态（数据正在同步中）

③ 最终一致（Eventually Consistent）
   经过一段时间（无新写入），所有副本最终达到一致

→ 互联网主流的分布式设计范式：
  先保证可用 → 数据用异步/补偿达到最终一致
  （Redis 缓存 + 数据库双写 → MQ 异步补偿）
```

## 3. 分布式事务方案（⭐ 核心）

### 3.1 为什么需要分布式事务

```
单机事务（ACID）：
  一个数据库内 → 本地事务（@Transactional）

分布式事务：
  一个业务操作涉及多个数据库/服务：
    下单 → 扣库存（库存服务）→ 扣余额（账户服务）→ 加积分（积分服务）
  → 每个服务有自己的数据库 → 无法用单机事务保证
  → 需要分布式事务协调多个库的一致性
```

### 3.2 方案总览

| 方案 | 一致性 | 性能 | 复杂度 | 适用 |
|---|---|---|---|---|
| **2PC**（两阶段提交） | 强一致 | 低（阻塞） | 中 | 少量库、强一致 |
| **TCC**（Try-Confirm-Cancel） | 最终一致 | 中 | **高**（业务补偿） | 核心资金链路 |
| **Saga**（长事务） | 最终一致 | 中 | 中 | 微服务长流程 |
| **本地消息表 + MQ** | 最终一致 | 高 | 低 | **互联网主流** |

### 3.3 2PC（两阶段提交）⭐

```
原理：事务管理器协调所有参与者，分两阶段提交

阶段 1（准备阶段 Prepare）：
  协调者 → 所有参与者："能提交吗？"
  参与者：执行事务，但不提交，返回"准备好了"（记录 undo/redo 日志）

阶段 2（提交/回滚 Commit/Abort）：
  全部准备成功 → 协调者 → 所有参与者："提交！"
  任一准备失败 → 协调者 → 所有参与者："回滚！"

经典例子：
  银行转账（A 扣款 + B 加款）
  阶段 1：A 库冻结扣款（不提交）+ B 库准备加款（不提交）→ 都返回 OK
  阶段 2：都 OK → A 提交 + B 提交 → 转账成功

问题：
  ① 阻塞：阶段 1 后参与者持有资源锁 → 协调者挂了 → 一直锁着
  ② 单点：协调者故障 → 整个事务卡死
  ③ 数据不一致：阶段 2 提交时部分参与者失败 → 无法回滚已提交的
  → 强一致但脆弱，生产很少直接用
```

### 3.4 TCC（Try-Confirm-Cancel）⭐

```
原理：业务层补偿 —— 把事务拆成三个阶段，每个阶段都是业务操作

T - Try（预留资源）：检查并锁定资源（如冻结库存 10 件）
C - Confirm（确认）：真正执行业务（扣减库存 10 件）
C - Cancel（取消）：回滚预留（释放冻结的 10 件）

流程：
  ① 所有参与者 Try 成功 → 全部 Confirm
  ② 任一参与者 Try 失败 → 全部 Cancel

例子（下单 + 扣库存）：
  Try：下单服务创建"待支付订单"；库存服务"冻结 10 件"
  Confirm：订单服务"订单生效"；库存服务"扣减冻结的 10 件"
  Cancel：订单服务"取消订单"；库存服务"释放冻结"

特点：
  ✅ 灵活（业务粒度控制）
  ❌ 实现复杂：每个操作都要写 Try/Confirm/Cancel 三套逻辑
  ❌ 必须考虑幂等（Confirm/Cancel 可能重复执行）
  → 适合资金/库存等核心链路（阿里系常用）
```

### 3.5 Saga（长事务）

```
原理：把长事务拆成一串本地事务，每个事务成功后触发下一个；
      失败则反向执行"补偿事务"

正常流程（下单 → 扣库存 → 扣款 → 发货）：
  下单成功 → 扣库存成功 → 扣款成功 → 发货成功

补偿流程（第 3 步失败）：
  扣款失败 → 补偿：撤销扣库存 → 撤销下单（反向回滚）

与 TCC 的区别：
  TCC：先 Try 预留全部资源，再统一 Confirm（两阶段风格）
  Saga：一个个串行执行，失败时反向补偿（链式风格）
  → TCC 更重（要预留），Saga 更轻（直接执行 + 补偿）
  → Saga 适合长流程（订单流转、审批流）

注意：
  Saga 的中间状态对其他系统可见（已扣库存但未扣款）
  → 需要业务容忍中间状态
```

### 3.6 本地消息表 + MQ（互联网主流）◈◈

```
思路：本地事务 + 消息队列 = 最终一致（最实用）

流程（下单 + 发消息给积分服务）：
  ① 开启本地事务：写订单表 + 写消息表（同一数据库，本地事务保证）
  ② 提交本地事务
  ③ 后台定时任务：扫描消息表"未发送"的消息 → 发送到 MQ
  ④ MQ 消费者（积分服务）：处理消息 → 加积分（幂等）
  ⑤ 消费成功 → 消息标记"已发送"（或删除）

核心保证：
  ① 和 ②：订单和消息在同一事务 → 要么都成功要么都失败
  ③：消息一定会被发送（定时任务重试）
  ④：消费者幂等（消息可能重复投递）
  → 最终一致：积分最终会加上

优点：实现简单、性能好、不用业务补偿
缺点：消息表耦合业务库；需要幂等设计
→ 生产最常用的方案（配合 RocketMQ 事务消息更优雅）
```

### 3.7 方案选型决策

```
选型决策树：

需要强一致（金额实时核对）？───是──→ 2PC（少量库）或 TCC（业务补偿）
    │否
长流程 + 可补偿？────────────是──→ Saga
    │否
性能优先 + 可最终一致？────────是──→ 本地消息表 + MQ ← 互联网主流
    │否
──────────────────────→ 看场景再定（或简单幂等即可）
```

## 4. 数据库乐观锁与悲观锁（🛠️ 必考）

### 4.1 悲观锁（SELECT ... FOR UPDATE）

```sql
-- 悲观锁：先锁后操作（认为一定会冲突）
BEGIN;
SELECT * FROM stock WHERE sku_id = 1 FOR UPDATE;  -- 锁住这行
-- 检查库存 → 扣减 → 提交
UPDATE stock SET count = count - 1 WHERE sku_id = 1;
COMMIT;

-- 特点：
--   锁住期间其他事务无法操作这行 → 安全但阻塞
--   适合：冲突概率高、需要立即锁定（转账、热点库存）
```

### 4.2 乐观锁（版本号）⭐

```sql
-- 乐观锁：先操作后校验（认为很少冲突）
-- 表结构：stock(sku_id, count, version)

-- 扣减：只有 version 匹配才更新
UPDATE stock
SET count = count - 1, version = version + 1
WHERE sku_id = 1 AND version = 5;    -- 期望版本号 5

-- 影响行数：
--   1 行 → 更新成功（version 从 5 → 6）
--   0 行 → 版本不匹配（别人已改过）→ 重试或失败

-- 特点：
--   无锁阻塞 → 性能好
--   冲突时更新失败 → 需要重试
--   适合：冲突概率低、读多写少（普通商品库存、配置）
```

### 4.3 两种锁的 Java 侧写法

```java
// 乐观锁重试（Java 侧）
public boolean deductStock(Long skuId, int count) {
    for (int retry = 0; retry < 3; retry++) {
        // ① 查询当前版本
        Stock stock = stockMapper.selectBySkuId(skuId);

        // ② 带版本号更新
        int rows = stockMapper.deductWithVersion(skuId, count, stock.getVersion());
        if (rows == 1) {
            return true;      // 更新成功
        }
        // ③ 更新失败（版本冲突）→ 重试
    }
    return false;   // 重试 3 次仍失败 → 返回失败（提示用户稍后重试）
}
```

```sql
-- 对应 SQL
UPDATE stock
SET count = count - #{count}, version = version + 1
WHERE sku_id = #{skuId} AND version = #{version}
```

### 4.4 乐观锁 vs 悲观锁选型（⭐ 必考）

| 维度 | 乐观锁（版本号） | 悲观锁（FOR UPDATE） |
|---|---|---|
| 原理 | 更新时校验版本 | 查询时锁定行 |
| 冲突处理 | 更新失败 → 重试 | 等待锁释放 |
| 性能 | 高（无锁等待） | 低（锁等待） |
| 阻塞 | 无 | 有 |
| 适用 | 冲突概率低 | 冲突概率高 |
| 典型 | 普通库存、配置更新 | 资金转账、热点库存 |

```
选型建议：
  冲突少 → 乐观锁（版本号 + 重试）
  冲突多 → 悲观锁（FOR UPDATE）
  秒杀热点库存 → 悲观锁 + 分布式锁（Redis）
  普通业务 → 乐观锁 + 幂等

生产实践：乐观锁重试次数要限制（3 次左右），避免无限重试
```

## 5. 生产注意事项 & 常见坑点

### 🕳️ 坑 1：乐观锁的版本号用错字段

```sql
-- ❌ 用 count 本身判断（数值恰好相等 → 误判）
UPDATE stock SET count = count - 1 WHERE sku_id = 1 AND count = 10;
-- 两个并发扣减：都读到 10 → 第一个成功变 9 → 第二个 9 != 10 → 失败
-- 但如果并发是"改回原值"（10→9→10）→ 误判成功！

-- ✅ 必须用独立版本号字段（单调递增）
UPDATE stock SET count = count - 1, version = version + 1
WHERE sku_id = 1 AND version = 5;
```

### 🕳️ 坑 2：悲观锁忘记开事务

```sql
-- ❌ FOR UPDATE 必须在事务里才有意义！
SELECT * FROM stock WHERE sku_id = 1 FOR UPDATE;   -- 不在事务里 → 立即释放
-- 检查 → 扣减（中间其他事务可能已改）→ 锁白加了！

-- ✅ 正确：BEGIN ... FOR UPDATE ... COMMIT
```

### 🕳️ 坑 3：TCC 的 Confirm/Cancel 忘记幂等

```java
// ❌ Confirm/Cancel 可能被重复执行（网络重试、协调者重放）
// → 必须幂等：用唯一事务 ID 判断是否已执行过
if (!alreadyProcessed(transactionId)) {
    doConfirm();
    markProcessed(transactionId);
}
```

### 🕳️ 坑 4：本地消息表的事务边界错误

```java
// ❌ 先发 MQ 再写库 → MQ 成功但库失败 → 消息发了业务没成
mq.send(msg);          // ① 先发消息
orderMapper.insert(o); // ② 写库失败 → 消息已发 → 不一致！

// ✅ 先写库（含消息表）→ 事务提交后再发
@Transactional
public void createOrder(Order o, MsgRecord msg) {
    orderMapper.insert(o);   // ① 订单
    msgMapper.insert(msg);   // ② 消息（同一事务）
}
// ③ 事务提交后 → 定时任务扫描消息表发送
```

### 🕳️ 坑 5：CAP 的"三选二"误解

```java
// ❌ 常见误解："CAP 是 C、A、P 三选二"
// ✅ 正确理解：P 是必选项（分区必然发生）
//    → 实际是在"分区发生时"选择 C 还是 A
//    → 无分区时 C 和 A 可以同时满足
```

## 6. 面试高频考点

1. **CAP 定理？为什么 P 必须选？**
   → C 一致性 / A 可用性 / P 分区容错。分区必然发生（宕机/网络抖动），分区时 C 和 A 不可兼得，必须二选一。

2. **BASE 理论？**
   → 基本可用 + 软状态 + 最终一致。AP 系统的补充：不强一致，最终一致。

3. **2PC / TCC / Saga 的区别？**
   → 2PC：两阶段（准备+提交），强一致但阻塞；TCC：Try 预留 + Confirm/Cancel 补偿，业务粒度；Saga：串行执行 + 反向补偿，适合长流程。

4. **本地消息表 + MQ 的原理？**
   → 写业务表 + 消息表（同一本地事务）→ 定时任务发 MQ → 消费者幂等处理 → 最终一致。

5. **乐观锁和悲观锁怎么选？**
   → 冲突少用乐观锁（版本号+重试）；冲突多用悲观锁（FOR UPDATE）；热点库存用悲观锁+分布式锁。

## 7. 实战练习

### 练习 1：数据库乐观锁扣库存（60 分钟）★必做

```java
package com.sw.yang.concurrent.distributed;

import org.junit.jupiter.api.Test;

import java.sql.*;

/**
 * 练习 1：乐观锁（版本号）扣库存 —— 模拟并发扣减
 *
 * 前置：本地 MySQL，创建表：
 *   CREATE TABLE stock (
 *     sku_id BIGINT PRIMARY KEY,
 *     count INT NOT NULL,
 *     version INT NOT NULL
 *   );
 *   INSERT INTO stock VALUES (1, 100, 0);
 *
 * 目标：10 个线程各扣 1 件，乐观锁保证最终 count = 90
 */
public class OptimisticLockTest {

    private static final String URL = "jdbc:mysql://localhost:3306/test?useSSL=false&serverTimezone=Asia/Shanghai";
    private static final String USER = "root";
    private static final String PASSWORD = "123456";

    /** 乐观锁扣减：带版本号更新 */
    private static int deductWithVersion(long skuId, int count, int version) throws SQLException {
        String sql = "UPDATE stock SET count = count - ?, version = version + 1 " +
                     "WHERE sku_id = ? AND version = ?";
        try (Connection conn = DriverManager.getConnection(URL, USER, PASSWORD);
             PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setInt(1, count);
            ps.setLong(2, skuId);
            ps.setInt(3, version);
            return ps.executeUpdate();   // 1 成功 / 0 版本冲突
        }
    }

    private static int getCount(long skuId) throws SQLException {
        String sql = "SELECT count FROM stock WHERE sku_id = ?";
        try (Connection conn = DriverManager.getConnection(URL, USER, PASSWORD);
             PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setLong(1, skuId);
            try (ResultSet rs = ps.executeQuery()) {
                rs.next();
                return rs.getInt(1);
            }
        }
    }

    @Test
    public void testOptimisticLock() throws Exception {
        // 前置检查
        try (Connection conn = DriverManager.getConnection(URL, USER, PASSWORD)) {
            System.out.println("✅ 已连接 MySQL（请确认已建 stock 表并插入 sku_id=1, count=100, version=0）");
        } catch (SQLException e) {
            System.out.println("⚠️ 无法连接 MySQL：" + e.getMessage());
            return;
        }

        final int threads = 10;
        final int[] success = {0};
        final int[] conflict = {0};
        Thread[] ts = new Thread[threads];

        for (int i = 0; i < threads; i++) {
            ts[i] = new Thread(() -> {
                // 乐观锁：查询版本 → 带版本更新 → 冲突重试（最多 5 次）
                for (int retry = 0; retry < 5; retry++) {
                    try {
                        // 查询当前版本
                        String q = "SELECT version FROM stock WHERE sku_id = 1";
                        int version;
                        try (Connection conn = DriverManager.getConnection(URL, USER, PASSWORD);
                             Statement st = conn.createStatement();
                             ResultSet rs = st.executeQuery(q)) {
                            rs.next();
                            version = rs.getInt(1);
                        }
                        // 带版本扣减
                        int rows = deductWithVersion(1, 1, version);
                        if (rows == 1) {
                            synchronized (success) { success[0]++; }
                            return;
                        }
                    } catch (SQLException e) {
                        // 数据库异常
                        return;
                    }
                }
                synchronized (conflict) { conflict[0]++; }   // 重试 5 次仍失败
            }, "thread-" + i);
            ts[i].start();
        }
        for (Thread t : ts) t.join();

        System.out.println("成功扣减: " + success[0] + " 次");
        System.out.println("冲突失败: " + conflict[0] + " 次");
        System.out.println("最终库存: " + getCount(1) + "（预期 100 - 10 = 90）");
        System.out.println(getCount(1) == 90
                ? "✅ 乐观锁生效：并发扣减不超卖"
                : "❌ 库存异常！");
    }
}
```

### 练习 2：悲观锁扣库存（30 分钟，对比用）

```java
package com.sw.yang.concurrent.distributed;

import org.junit.jupiter.api.Test;

import java.sql.*;

/**
 * 练习 2：悲观锁（SELECT ... FOR UPDATE）扣库存 —— 与乐观锁对比
 *
 * 原理：事务内锁行 → 其他事务等待 → 串行扣减 → 天然安全
 * 代价：并发性能低于乐观锁（锁等待）
 */
public class PessimisticLockTest {

    private static final String URL = "jdbc:mysql://localhost:3306/test?useSSL=false&serverTimezone=Asia/Shanghai";
    private static final String USER = "root";
    private static final String PASSWORD = "123456";

    @Test
    public void testPessimisticLock() throws Exception {
        try (Connection conn = DriverManager.getConnection(URL, USER, PASSWORD)) {
            System.out.println("✅ 已连接 MySQL");
        } catch (SQLException e) {
            System.out.println("⚠️ 无法连接 MySQL：" + e.getMessage());
            return;
        }

        final int threads = 10;
        final int[] success = {0};
        Thread[] ts = new Thread[threads];

        for (int i = 0; i < threads; i++) {
            ts[i] = new Thread(() -> {
                try (Connection conn = DriverManager.getConnection(URL, USER, PASSWORD)) {
                    conn.setAutoCommit(false);   // 开事务

                    // ① 锁行（悲观锁核心）
                    try (Statement st = conn.createStatement();
                         ResultSet rs = st.executeQuery(
                                 "SELECT count FROM stock WHERE sku_id = 1 FOR UPDATE")) {
                        rs.next();
                        int count = rs.getInt(1);
                        if (count <= 0) {
                            conn.rollback();
                            return;   // 库存不足
                        }
                    }

                    // ② 扣减
                    try (Statement st = conn.createStatement()) {
                        st.executeUpdate(
                                "UPDATE stock SET count = count - 1 WHERE sku_id = 1");
                    }

                    // ③ 提交（释放锁）
                    conn.commit();
                    synchronized (success) { success[0]++; }
                } catch (SQLException e) {
                    // 锁等待超时等异常
                }
            }, "thread-" + i);
            ts[i].start();
        }
        for (Thread t : ts) t.join();

        System.out.println("成功扣减: " + success[0] + " 次");
        System.out.println("✅ 悲观锁：事务内锁行，串行扣减（注意：执行前请把库存重置为 100）");
        System.out.println("对比：乐观锁无阻塞性能高，悲观锁有锁等待但无需重试");
    }
}
```

### 练习 3：模拟分布式事务失败与补偿（45 分钟）

```java
package com.sw.yang.concurrent.distributed;

import org.junit.jupiter.api.Test;

import java.util.concurrent.atomic.AtomicInteger;

/**
 * 练习 3：模拟 Saga 补偿 —— 理解"反向回滚"思想
 *
 * 场景：下单 → 扣库存 → 扣款 → 发货（4 步）
 *       第 3 步失败 → 反向补偿（撤销扣款 → 释放库存 → 取消订单）
 */
public class SagaCompensationTest {

    // 模拟各服务的"操作日志"（记录已执行步骤）
    private final java.util.List<String> executed = new java.util.ArrayList<>();
    private final java.util.List<String> compensated = new java.util.ArrayList<>();

    /** 执行步骤（模拟），failAtStep 时第 N 步抛异常 */
    private void executeSaga(int failAtStep) {
        try {
            step1_createOrder();      // ① 下单
            step2_deductStock();      // ② 扣库存
            if (failAtStep == 3) throw new RuntimeException("扣款失败");
            step3_deductMoney();      // ③ 扣款
            step4_ship();             // ④ 发货
            System.out.println("🎉 全流程成功");
        } catch (Exception e) {
            System.out.println("❌ 执行失败：" + e.getMessage() + " → 开始补偿");
            compensate();             // 反向补偿
        }
    }

    private void step1_createOrder() {
        executed.add("下单");
        System.out.println("✓ 下单成功");
    }

    private void step2_deductStock() {
        executed.add("扣库存");
        System.out.println("✓ 扣库存成功");
    }

    private void step3_deductMoney() {
        executed.add("扣款");
        System.out.println("✓ 扣款成功");
    }

    private void step4_ship() {
        executed.add("发货");
        System.out.println("✓ 发货成功");
    }

    /** 反向补偿：逆序撤销已执行的步骤 */
    private void compensate() {
        // 从后往前补偿
        for (int i = executed.size() - 1; i >= 0; i--) {
            String step = executed.get(i);
            switch (step) {
                case "扣库存":
                    compensated.add("释放库存");
                    System.out.println("↩ 补偿：释放库存");
                    break;
                case "下单":
                    compensated.add("取消订单");
                    System.out.println("↩ 补偿：取消订单");
                    break;
                case "扣款":
                    compensated.add("退回款项");
                    System.out.println("↩ 补偿：退回款项");
                    break;
                default:
                    // 发货后无需补偿（或记录售后）
            }
        }
        System.out.println("✅ 补偿完成，业务回到一致状态");
    }

    @Test
    public void testSagaSuccess() {
        System.out.println("=== 场景 1：全流程成功 ===");
        executeSaga(99);   // 不失败
    }

    @Test
    public void testSagaCompensation() {
        System.out.println("=== 场景 2：第 3 步失败 → 反向补偿 ===");
        executeSaga(3);    // 扣款失败
        System.out.println("\n执行过的步骤: " + executed);
        System.out.println("补偿执行的步骤: " + compensated);
        System.out.println("✅ Saga 反向补偿思想演示完成");
    }
}
```

## 8. 自测题

1. **CAP 定理？为什么 P 必须选？**
   <details><summary>答案</summary>

   C 一致性 / A 可用性 / P 分区容错。分区（宕机/网络抖动）是必然发生的，分区时 C 和 A 不可兼得——等确认则不可用，先响应则不一致。所以必须在分区发生时二选一（CP 或 AP）。
   </details>

2. **BASE 和 ACID 的关系？**
   <details><summary>答案</summary>

   ACID 是单机强一致模型；BASE 是分布式 AP 系统的妥协模型：基本可用 + 软状态 + 最终一致。分布式系统通常"用 ACID 保证单库、用 BASE 协调多库"。
   </details>

3. **2PC 的问题？为什么生产少用？**
   <details><summary>答案</summary>

   阻塞（准备阶段持有资源锁）、单点（协调者故障卡死）、数据不一致（提交阶段部分失败无法回滚）。强一致但脆弱。
   </details>

4. **TCC 和 Saga 的区别？**
   <details><summary>答案</summary>

   TCC：先 Try 预留全部资源 → 统一 Confirm/Cancel（两阶段风格，重但可控）；Saga：串行执行 + 失败反向补偿（链式，轻但中间状态可见）。TCC 适合资金，Saga 适合长流程。
   </details>

5. **乐观锁为什么用独立版本号而不是业务字段？**
   <details><summary>答案</summary>

   业务字段可能"改回原值"（10→9→10），用业务字段判断会误判"没被改过"。独立版本号单调递增，任何一次更新都会 +1，不会误判。
   </details>
