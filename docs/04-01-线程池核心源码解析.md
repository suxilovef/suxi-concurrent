## 1. 为什么需要线程池

```
不用线程池的问题：
  每个任务 new Thread() → 创建/销毁线程开销巨大
  线程数无上限 → 资源耗尽（OOM / 线程爆炸）

线程池的意义：
  ✅ 复用线程（减少创建/销毁开销）
  ✅ 控制并发数（防止线程爆炸）
  ✅ 队列缓冲（削峰填谷）
  ✅ 统一管理（监控/拒绝/优雅停机）
```

## 2. 7 大核心参数（🛠️ 必背）

```java
public ThreadPoolExecutor(
    int corePoolSize,          // ① 核心线程数
    int maximumPoolSize,       // ② 最大线程数
    long keepAliveTime,        // ③ 空闲存活时间
    TimeUnit unit,             // ④ 时间单位
    BlockingQueue<Runnable> workQueue,  // ⑤ 任务队列
    ThreadFactory threadFactory,        // ⑥ 线程工厂
    RejectedExecutionHandler handler)   // ⑦ 拒绝策略
```

| 参数 | 含义 | 关键点 |
|---|---|---|
| corePoolSize | 核心线程数 | 核心线程**不回收**（默认） |
| maximumPoolSize | 最大线程数 | 线程数上限 = 核心 + 临时 |
| keepAliveTime | 临时线程空闲存活时间 | 超过时间回收临时线程 |
| unit | 时间单位 | — |
| workQueue | 任务队列 | **核心线程满后任务先排队** |
| threadFactory | 线程工厂 | 生产规范：必须自定义命名 |
| handler | 拒绝策略 | 队列满 + 线程满时触发 |

### 2.1 关键理解：线程数的两档

```
线程数分两档：
  第一档：corePoolSize —— 常驻线程（不回收）
  第二档：maximumPoolSize —— 最多线程（超出的叫"临时线程"，空闲会被回收）

任务提交流程（先核心 → 再队列 → 再临时 → 最后拒绝）：

  提交任务
    ├─ 线程数 < corePoolSize     → 新建核心线程执行
    ├─ 核心线程忙，队列未满       → 任务入队（等待）
    ├─ 队列满，线程数 < maxPool   → 新建临时线程执行
    └─ 队列满，线程数 = maxPool   → 执行拒绝策略
```

> ⚠️ **最常见的误解**：以为"线程不够就创建新线程"。**实际是先入队！** 核心线程满了，任务先进队列，队列满了才创建临时线程。

## 3. ctl 变量（一个 int 存储两种信息）

```java
public class ThreadPoolExecutor {
    // ★ 核心：一个 int 同时存储"运行状态"和"工作线程数"
    private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0));

    // 高 3 位：运行状态（runState）
    // 低 29 位：工作线程数（workerCount）
    private static final int COUNT_BITS = Integer.SIZE - 3;   // 29
    private static final int CAPACITY   = (1 << COUNT_BITS) - 1;  // 最大线程数 2^29-1

    // 5 种运行状态（数值依次增大）
    private static final int RUNNING    = -1 << COUNT_BITS;   // 111... 接收新任务+处理队列
    private static final int SHUTDOWN   =  0 << COUNT_BITS;   // 000... 不接收新任务，处理队列
    private static final int STOP       =  1 << COUNT_BITS;   // 001... 不接收新任务，中断所有
    private static final int TIDYING    =  2 << COUNT_BITS;   // 010... 所有任务结束，待终止
    private static final int TERMINATED =  3 << COUNT_BITS;   // 011... 已终止

    // 位运算：提取状态 / 提取线程数 / 合并
    private static int runStateOf(int c)     { return c & ~CAPACITY; }
    private static int workerCountOf(int c)  { return c & CAPACITY; }
    private static int ctlOf(int rs, int wc) { return rs | wc; }
}
```

### 3.1 为什么状态值这样设计？

```
状态大小关系（核心设计）：

  RUNNING(-1) < SHUTDOWN(0) < STOP(1) < TIDYING(2) < TERMINATED(3)

好处：比较状态只需比较 ctl 数值！

  c >= SHUTDOWN  → 线程池已关闭（不再接收新任务）
  c < SHUTDOWN   → 还在运行（RUNNING，唯一小于 SHUTDOWN 的状态）

→ 用 ctl.compareAndSet 同时保证状态+线程数的原子更新
→ 一个变量搞定两个信息，避免了状态和线程数不一致的问题
```

### 3.2 5 种状态流转

```
            ┌─────────────────────┐
            │      RUNNING        │  接收新任务，处理队列任务
            └──────────┬──────────┘
        shutdown()     │     shutdownNow()
            ▼          │          ▼
     ┌────────────┐    │    ┌────────────┐
     │  SHUTDOWN  │    │    │    STOP    │
     │ 不接收新任务 │    │    │ 不接收+中断 │
     │ 处理队列任务 │    │    │ 清空队列    │
     └──────┬─────┘    │    └──────┬─────┘
            │          │           │
            └────┬─────┴────┬──────┘
                 ▼          ▼
            ┌─────────────────────┐
            │      TIDYING        │  队列清空 + 线程归零
            └──────────┬──────────┘
                       ▼
            ┌─────────────────────┐
            │    TERMINATED       │  终止完成
            └─────────────────────┘
```

## 4. execute() 完整流程（⭐ 核心）

```java
public void execute(Runnable command) {
    if (command == null) throw new NullPointerException();

    int c = ctl.get();
    // ① 线程数 < 核心线程数 → 新建核心线程
    if (workerCountOf(c) < corePoolSize) {
        if (addWorker(command, true))
            return;
        c = ctl.get();        // addWorker 失败 → 重新读取状态
    }

    // ② 线程数 >= 核心 → 尝试入队
    if (isRunning(c) && workQueue.offer(command)) {
        int recheck = ctl.get();
        // 双重检查：入队后线程池可能被关闭
        if (!isRunning(recheck) && remove(command))
            reject(command);          // 池被关闭 → 移除任务 + 拒绝
        else if (workerCountOf(recheck) == 0)
            addWorker(null, false);   // 没有线程了 → 补一个空线程去队列取任务
    }
    // ③ 队列满 → 尝试创建临时线程
    else if (!addWorker(command, false))
        reject(command);              // 线程也满 → 拒绝策略
}
```

### 4.1 execute 流程图（务必能画）

```
execute(task)
    │
    ├─ ① workerCount < corePoolSize?
    │    是 → addWorker(task, true)  新建核心线程 ✅
    │    否 ↓
    ├─ ② 池是 RUNNING 且队列能入队?
    │    是 → 入队，双重检查：
    │         ├─ 池已关闭 → remove + reject
    │         └─ 无线程 → addWorker(null, false) 补线程
    │    否 ↓
    ├─ ③ addWorker(task, false) 新建临时线程?
    │    是 → ✅
    │    否 ↓
    └─ ④ reject(task) 执行拒绝策略
```

### 4.2 三个分支的关键细节

```
分支 ② 的"入队后补线程"：
  为什么入队成功还要补线程？
  场景：corePoolSize=0，任务入队后一个线程都没有
  → 补一个"空任务"线程，让线程从队列里取任务执行

分支 ② 的双重检查：
  为什么入队后要 recheck？
  场景：任务入队瞬间线程池被 shutdown
  → 队列里的任务永远不会执行 → 必须移除 + 拒绝

分支 ③ 的 addWorker 失败：
  可能原因：线程数已达上限 / 池已关闭
  → 走拒绝策略
```

## 5. addWorker() —— 创建 Worker

```java
private boolean addWorker(Runnable firstTask, boolean core) {
    retry:
    for (;;) {
        int c = ctl.get();
        int rs = runStateOf(c);

        // ① 状态检查：关闭后不再接收新任务
        if (rs >= SHUTDOWN &&
            !(rs == SHUTDOWN && firstTask == null && !workQueue.isEmpty()))
            return false;

        for (;;) {
            int wc = workerCountOf(c);
            // ② 线程数检查（核心用 corePoolSize，临时用 maximumPoolSize）
            if (wc >= CAPACITY ||
                wc >= (core ? corePoolSize : maximumPoolSize))
                return false;
            // ③ CAS 增加线程数（成功后跳出双重循环）
            if (compareAndIncrementWorkerCount(c))
                break retry;
            c = ctl.get();       // CAS 失败 → 重读
            if (runStateOf(c) != rs)
                continue retry;  // 状态变了 → 重新检查
        }
    }

    // ④ 创建 Worker 并启动
    boolean workerStarted = false;
    boolean workerAdded = false;
    Worker w = null;
    try {
        w = new Worker(firstTask);       // 创建 Worker（内部 new Thread）
        final Thread t = w.thread;
        if (t != null) {
            final ReentrantLock mainLock = this.mainLock;
            mainLock.lock();             // 加主锁（保护 workers 集合）
            try {
                int c = ctl.get();
                // ⑤ 双重检查状态（持锁后用最新状态重新验证）
                if (runStateOf(c) < SHUTDOWN ||
                    (runStateOf(c) == SHUTDOWN && firstTask == null)) {
                    workers.add(w);      // 加入工作线程集合
                    workerAdded = true;
                }
            } finally {
                mainLock.unlock();
            }
            if (workerAdded) {
                t.start();               // ⑥ 启动线程
                workerStarted = true;
            }
        }
    } finally {
        if (!workerStarted)
            addWorkerFailed(w);          // 失败回滚（减线程数 + 移除 Worker）
    }
    return workerStarted;
}
```

```
addWorker 关键点：
  ① 外层循环：状态检查（shutdown 后不能加）
  ② 内层循环：线程数检查（核心/最大上限）
  ③ CAS 递增 workerCount（无锁竞争）
  ④ 加主锁保护 workers 集合
  ⑤ 持锁后二次检查（防止加进去时池已关闭）
  ⑥ 启动线程
```

## 6. Worker 内部类（线程复用的核心）

### 6.1 Worker 的结构

```java
private final class Worker extends AbstractQueuedSynchronizer
        implements Runnable {
    final Thread thread;        // 包装的线程
    Runnable firstTask;         // 第一个任务（可能为 null）
    volatile long completedTasks;   // 完成任务数

    Worker(Runnable firstTask) {
        setState(-1);           // ★ 初始 state = -1（禁止中断）
        this.firstTask = firstTask;
        this.thread = getThreadFactory().newThread(this);
    }

    public void run() {
        runWorker(this);        // 线程启动后执行 runWorker
    }

    // AQS 实现：只支持独占 + 不可重入
    protected boolean tryAcquire(int unused) {
        if (compareAndSetState(0, 1)) return true;
        return false;
    }
    protected boolean tryRelease(int unused) {
        setState(0);
        return true;
    }
}
```

### 6.2 为什么 Worker 继承 AQS？

```
Worker 继承 AQS 的原因：实现"不可重入的互斥锁"，用于精确控制中断

核心场景（shutdown 时）——interruptIdleWorkers：
  for (Worker w : workers) {
      if (!t.isInterrupted() && w.tryLock()) {   // tryLock 成功 = 空闲（未持锁）
          t.interrupt();                         // 只中断空闲线程！
      }
  }

  → w.tryLock() 成功 = 该 Worker 没有在执行任务（空闲）
  → 空闲的 Worker 才允许被中断（让它从队列取任务的阻塞中醒来退出）
  → 正在执行任务的 Worker（持锁）不会被中断 → 任务能完整执行完

为什么初始 state = -1？
  刚创建的 Worker 还没执行任务（处于"未启动"状态）→ 禁止中断
  runWorker 开始执行时 → w.unlock() → state 变为 0 → 之后 tryLock 才可能成功

补充：shutdownNow（STOP 状态）用 interruptWorkers，此时所有线程都会被中断
```

### 6.3 runWorker() —— 线程复用的核心（⭐）

```java
final void runWorker(Worker w) {
    Thread wt = Thread.currentThread();
    Runnable task = w.firstTask;    // 第一个任务（可能为 null）
    w.firstTask = null;
    w.unlock();                     // state 0 → 允许中断
    boolean completedAbruptly = true;

    try {
        // ★ 核心循环：取任务 → 执行 → 再取 → 再执行...
        while (task != null || (task = getTask()) != null) {
            w.lock();               // 加锁（执行期间禁止中断）
            // ① 线程池 STOP 状态 → 中断当前线程
            if ((runStateAtLeast(ctl.get(), STOP) ||
                 (Thread.interrupted() && runStateAtLeast(ctl.get(), STOP))) &&
                !wt.isInterrupted())
                wt.interrupt();

            try {
                beforeExecute(wt, task);   // ② 钩子：执行前（可扩展）
                try {
                    task.run();            // ③ ★ 执行任务（不是 start！）
                } finally {
                    afterExecute(task, null);  // ④ 钩子：执行后
                }
            } finally {
                w.unlock();                // 释放锁（允许中断）
                task = null;
                w.completedTasks++;        // 完成任务计数
            }
        }
        completedAbruptly = false;
    } finally {
        processWorkerExit(w, completedAbruptly);  // ⑤ 线程退出处理
    }
}
```

```
runWorker 核心：
  while (task != null || (task = getTask()) != null)
    task.run();   // ← 直接调用 run，不是 new Thread！

→ 这就是"线程复用"的本质：
  同一个线程（Worker.thread），循环执行多个任务
  线程从队列 getTask() 拿任务 → run() → 再拿 → 再 run...
  而不是"一个任务一个线程"
```

## 7. getTask() —— 取任务与线程回收

```java
private Runnable getTask() {
    boolean timedOut = false;   // 上次取任务是否超时

    for (;;) {
        int c = ctl.get();
        int rs = runStateOf(c);

        // ① 池已关闭且队列空 → 不取任务，返回 null（线程退出）
        if (rs >= SHUTDOWN && (rs >= STOP || workQueue.isEmpty())) {
            decrementWorkerCount();   // 减少线程数
            return null;
        }

        int wc = workerCountOf(c);
        // ② 是否启用超时回收：
        //    timed = 允许核心超时 || 线程数 > 核心数
        boolean timed = allowCoreThreadTimeOut || wc > corePoolSize;

        if ((wc > maximumPoolSize || (timed && timedOut)) &&
            (wc > 1 || workQueue.isEmpty())) {
            if (compareAndDecrementWorkerCount(c))
                return null;        // ③ 超时且没任务 → 退出（线程回收）
            continue;
        }

        try {
            // ④ 阻塞取任务：
            //    timed → poll(keepAliveTime)（超时返回 null → 回收）
            //    非 timed → take()（一直等）
            Runnable r = timed ?
                workQueue.poll(keepAliveTime, TimeUnit.NANOSECONDS) :
                workQueue.take();
            if (r != null)
                return r;
            timedOut = true;        // 超时了 → 下一轮退出
        } catch (InterruptedException retry) {
            timedOut = false;
        }
    }
}
```

### 7.1 线程回收的完整链路

```
线程回收（临时线程）：

  线程执行完当前任务
    → 回到 runWorker 循环
    → getTask() 取任务
    → poll(keepAliveTime) 阻塞等待
    → 超过 keepAliveTime 没任务 → 返回 null
    → runWorker 循环结束
    → processWorkerExit() 清理
    → 线程自然结束（回收）

触发回收的条件：
  timed = allowCoreThreadTimeOut || wc > corePoolSize
  → 线程数超过核心数 → 多余的线程超时回收
  → 或开启 allowCoreThreadTimeOut → 核心线程也能回收
```

### 7.2 核心线程为什么不回收（默认）

```
核心线程用 take() —— 无限阻塞等待：
  take() 永远不返回 null → getTask 不会退出 → 线程永不结束

临时线程用 poll(keepAliveTime) —— 超时返回 null：
  超时 → 线程退出 → 回收

→ 这是 keepAliveTime 只对"超过核心数的线程"生效的原因
```

## 8. processWorkerExit —— 线程退出处理

```java
private void processWorkerExit(Worker w, boolean completedAbruptly) {
    // ① 异常退出 → 减少线程数（正常退出时 getTask 已减过）
    if (completedAbruptly)
        decrementWorkerCount();

    final ReentrantLock mainLock = this.mainLock;
    mainLock.lock();
    try {
        completedTaskCount += w.completedTasks;   // 汇总完成任务数
        workers.remove(w);                        // 移除 Worker
    } finally {
        mainLock.unlock();
    }

    // ② 尝试终止线程池（如果满足终止条件）
    tryTerminate();

    // ③ 线程数不足 → 补充
    int c = ctl.get();
    if (runStateLessThan(c, STOP)) {          // 还没到 STOP
        if (!completedAbruptly) {
            int min = allowCoreThreadTimeOut ? 0 : corePoolSize;
            if (min == 0 && !workQueue.isEmpty())
                min = 1;                      // 队列还有任务 → 至少留 1 个线程
            if (workerCountOf(c) >= min)
                return;
        }
        addWorker(null, false);               // 补充线程（保持线程数）
    }
}
```

```
为什么异常退出后要补充线程？
  线程因异常退出 → 线程数减少 → 可能低于 corePoolSize
  → 补一个线程保证线程池有足够处理能力
```

## 9. 生产注意事项 & 常见坑点

### 🕳️ 坑 1：任务提交顺序误解

```java
// ❌ 以为"线程不够就新建线程"
// 实际：核心线程满 → 先入队！队列满才建临时线程

// 现象：核心 2 最大 10 队列 100
// 提交 3 个任务 → 前 2 个占核心线程，第 3 个进队列（不是新建线程！）
```

### 🕳️ 坑 2：Executors 工厂的陷阱

```java
// ❌ newFixedThreadPool：无界队列 → 任务堆积 → OOM
Executors.newFixedThreadPool(10);

// ❌ newCachedThreadPool：最大线程数 MAX_VALUE → 线程爆炸
Executors.newCachedThreadPool();

// ✅ 生产规范：new ThreadPoolExecutor(...) 显式传参 + 有界队列
```

### 🕳️ 坑 3：自定义 ThreadFactory 的重要性

```java
// ❌ 默认线程名 "pool-1-thread-1" → 线上排查看不出是哪个池
// ✅ 自定义命名：
ThreadFactory factory = new ThreadFactory() {
    private final AtomicInteger seq = new AtomicInteger();
    @Override
    public Thread newThread(Runnable r) {
        Thread t = new Thread(r);
        t.setName("order-async-" + seq.incrementAndGet());  // 可识别！
        t.setDaemon(false);   // 默认非守护（确保任务执行完）
        return t;
    }
};
```

### 🕳️ 坑 4：任务里抛异常，线程不会死但任务丢了

```java
// ⚠️ 任务 run() 抛 RuntimeException → 线程退出（completedAbruptly）
// → 线程池会补充线程（processWorkerExit）
// → 但异常本身被吞掉（除非自定义 afterExecute / UncaughtExceptionHandler）

// ✅ 生产规范：任务内自行 try-catch，或实现 Thread.UncaughtExceptionHandler
```

### 🕳️ 坑 5：核心线程为 0 的注意

```java
// corePoolSize = 0 的场景（如 CachedThreadPool）：
// 任务提交 → 入队 → 如果队列里一直有任务但没线程 → 任务永远不执行！
// execute 里有兜底：入队后 workerCount == 0 → addWorker(null, false) 补线程
// → 但注意：CachedThreadPool 的 SynchronousQueue 不存储 → 所以总是新建线程
```

## 10. 面试高频考点

1. **线程池 7 大参数分别是什么？**
   → corePoolSize / maximumPoolSize / keepAliveTime / unit / workQueue / threadFactory / handler。

2. **任务提交的执行顺序？**
   → 核心线程 → 队列 → 临时线程 → 拒绝策略。**注意队列在临时线程之前！**

3. **ctl 变量怎么一个 int 存两种信息？**
   → 高 3 位运行状态 + 低 29 位工作线程数。状态值大小设计（RUNNING<SHUTDOWN<STOP<TIDYING<TERMINATED）使得比较状态只需比较数值。

4. **线程是怎么复用的？**
   → Worker.thread 循环调用 runWorker → getTask() 从队列取任务 → task.run() 直接执行（不是 new Thread）。一个线程执行多个任务。

5. **临时线程什么时候回收？核心线程为什么默认不回收？**
   → 临时线程用 poll(keepAliveTime) 超时返回 null → 退出；核心线程用 take() 无限阻塞 → 永不退出。

### 练习 1：验证任务执行顺序（45 分钟）★必做

```java
package com.sw.yang.concurrent.pool;

import org.junit.jupiter.api.Test;

import java.util.concurrent.*;

/**
 * 练习 1：验证线程池任务执行顺序（核心 → 队列 → 临时 → 拒绝）
 *
 * 配置：核心 2，最大 4，队列容量 2
 * 提交 7 个任务 → 观察各任务由哪个线程执行
 */
public class ExecuteOrderTest {

    @Test
    public void testExecuteOrder() throws InterruptedException {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                2,                     // 核心 2
                4,                     // 最大 4
                60, TimeUnit.SECONDS,
                new ArrayBlockingQueue<>(2),   // 队列 2
                new ThreadFactory() {
                    private final java.util.concurrent.atomic.AtomicInteger seq =
                            new java.util.concurrent.atomic.AtomicInteger();
                    @Override
                    public Thread newThread(Runnable r) {
                        Thread t = new Thread(r);
                        t.setName("pool-worker-" + seq.incrementAndGet());
                        return t;
                    }
                },
                new ThreadPoolExecutor.AbortPolicy());

        // 提交 7 个任务
        for (int i = 1; i <= 7; i++) {
            final int id = i;
            try {
                pool.execute(() -> {
                    System.out.println("任务 " + id + " 由线程 [" +
                            Thread.currentThread().getName() + "] 执行");
                    try { Thread.sleep(50); } catch (InterruptedException e) { }
                });
            } catch (RejectedExecutionException e) {
                System.out.println("任务 " + id + " 被拒绝！");
            }
        }

        // 观察输出：
        // 任务 1、2 → worker-1、worker-2（核心线程）
        // 任务 3、4 → 入队（等待）
        // 任务 5、6 → worker-3、worker-4（临时线程！队列满了）
        // 任务 7 → 被拒绝（队列满 + 线程满）

        pool.shutdown();
        pool.awaitTermination(5, TimeUnit.SECONDS);
        System.out.println("✅ 观察：核心(2) → 队列(2) → 临时(2) → 拒绝(1)");
    }
}
```

import org.junit.jupiter.api.Test;

                System.out.println("第二个任务执行（线程: " + Thread.currentThread().getName() + "）"));

        pool.awaitTermination(5, TimeUnit.SECONDS);

## 12. 自测题

1. **execute() 的三条路径分别是什么？为什么队列在临时线程之前？**
   <details><summary>答案</summary>

   ① 核心未满 → 新建核心线程；② 队列未满 → 入队；③ 队列满 → 新建临时线程；④ 都满 → 拒绝。
   队列优先于临时线程的原因：临时线程有创建/销毁开销，且 keepAliveTime 后才回收。任务短暂排队比新建线程更划算。
   </details>

2. **ctl 高 3 位低 29 位的设计有什么好处？**
   <details><summary>答案</summary>

   ① 一个 AtomicInteger 原子更新状态+线程数（避免不一致）；② 状态数值大小设计使比较只需 `c >= SHUTDOWN` 一次位运算；③ 节省内存。
   </details>

3. **线程复用是怎么实现的？**
   <details><summary>答案</summary>

   Worker 包装一个 Thread；runWorker 中 while 循环调用 getTask() 从队列取任务，然后直接 task.run()。同一个线程反复执行队列中的任务，而不是每个任务 new Thread。
   </details>

4. **临时线程为什么用 poll(keepAliveTime) 而核心线程用 take()？**
   <details><summary>答案</summary>

   poll(keepAliveTime) 超时返回 null → getTask 返回 null → 线程退出（回收临时线程）；take() 无限阻塞 → 永不返回 null → 核心线程永不退出。
   </details>

5. **任务抛异常后线程池会发生什么？**
   <details><summary>答案</summary>

   该线程退出（completedAbruptly=true）→ processWorkerExit 减少线程数并补充新线程 → 线程池继续工作。但异常默认被吞掉（除非自定义 UncaughtExceptionHandler 或 afterExecute）。
   </details>
