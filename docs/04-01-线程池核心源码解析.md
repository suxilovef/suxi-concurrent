## 1. 为什么需要线程池（设计原理）

> 先摆一把尺子（docs/00 第一性原理节）：**它在压缩哪个代价、守住哪个正确性？**
> 答：压缩「线程创建/销毁的内核开销 + 栈内存」；守住「线程数有界 + 队列有界」。
> 下面四个手段，全部从「一个任务一个线程」这个原始做法错在哪推出来。

### 1.1 原始做法的三个代价

```
task → new Thread(task).start()      // 每个任务来一次
```

| 代价 | 具体是什么 |
|---|---|
| **创建/销毁开销** | 内核 syscall + 栈分配（默认 1MB 虚拟内存）+ 调度器注册 → µs~百µs 级 |
| **并发度不可控** | 任务来多少就开多少线程 → 线程爆炸、上下文切换雪崩、OOM |
| **无边界、无管理** | 没有上限、没有排队、没有拒绝、没有监控、没有优雅停机 |

### 1.2 四个手段，逐一拆掉

**手段① 复用 —— 拆掉"创建开销"**

```
关键洞察：线程不是任务的一部分，它是"执行任务的载体"
         载体可以脱离具体任务存在

  一个任务一个线程：  线程生命周期 == 任务生命周期     （绑定）
  线程池：           线程生命周期 ⊃ 多个任务生命周期   （解耦）

实现：把"跑一个任务"换成"循环取任务"
  while ((task = getTask()) != null) task.run();     // runWorker（§6.3）

★ 这是整个设计的地基，后面三个手段都是围绕它加的调节阀
代价：载体常驻就要占内存（栈），闲置线程是纯浪费 → 引出 ②③
```

**手段② 缓冲 —— 拆掉"突发击穿"**

```
任务来得比处理快时，不立刻扩线程（扩线程有代价）→ 先入队

  队列 = 用内存换时间（削峰填谷）
★ 代价 = 内存占用 + 任务不能立刻执行（延迟）
  → 所以队列必须有界，否则 ② 只是把"线程爆炸"换成了"OOM"
```

**手段③ 分档 —— 拆掉"并发度不可控"**

```
  core 档：常驻线程，保证基础吞吐，不反复创建销毁（默认不回收）
  max  档：弹性线程，应对突发（空闲 keepAliveTime 后回收）

  决策顺序：核心满 → 入队 → 队列满 → 扩临时线程 → 都满 → 拒绝
```

> ★ **为什么队列优先于扩容**（设计里最反直觉的一处，也是坑 1 那个误解的根源）：
>
> ```
> 入队    = 内存写 + 一次 unpark       ns~µs 级，无内核态切换
> 建线程  = syscall + 栈分配 + 注册     µs~百µs 级
> → 差 1~2 个数量级
>
> 本质是"先缓冲、后扩资源"：临时线程是消化积压的最后手段，
> 队列没满就说明积压还没到需要动它的程度
>
> 代价：无界队列下 maximumPoolSize 形同虚设（队列永远不满）
> ```

**手段④ 边界与生命周期 —— 拆掉"无管理"**

```
  有界线 + 拒绝策略 → 压力击穿时"显式失败"，而不是静默堆积到 OOM
  ctl 一个 int 存状态+线程数 → 状态与计数永不不一致（§3）
  shutdown / shutdownNow 两级关停 → 有序排空 vs 立即中断（04-02）
  监控计数 + before/afterExecute 钩子 → 可观测、可扩展
```

### 1.3 汇总

```
线程池 = 复用（去创建开销）
       + 缓冲（削峰）
       + 两档弹性（自适应并发）
       + 有界拒绝（守可用性）
       + 统一生命周期（可管理）
```

```
只记三句：
  ① 把「一个任务一个线程」换成「一个线程循环取任务」 —— 决定它是什么（地基）
  ② 建线程比入队贵 1~2 个数量级                    —— 决定四条分支的顺序
  ③ 有界 + 拒绝                                   —— 决定它不会把自己压垮
```

## 2. 7 大核心参数（🛠️ 必背）

```java
public ThreadPoolExecutor(
    int corePoolSize,          // ① 核心线程数
    int maximumPoolSize,       // ② 最大线程数
    long keepAliveTime,        // ③ 空闲存活时间
    TimeUnit unit,             // ④ 时间单位
    BlockingQueue<Runnable> workQueue,  // ⑤ 任务队列
    ThreadFactory threadFactory,        // ⑥ 线程工厂
    RejectedExecutionHandler handler)   // ⑦ 拒绝策略
```

| 参数 | 含义 | 关键点 |
|---|---|---|
| corePoolSize | 核心线程数 | 核心线程**不回收**（默认） |
| maximumPoolSize | 最大线程数 | 线程数上限 = 核心 + 临时 |
| keepAliveTime | 临时线程空闲存活时间 | 超过时间回收临时线程 |
| unit | 时间单位 | — |
| workQueue | 任务队列 | **核心线程满后任务先排队** |
| threadFactory | 线程工厂 | 生产规范：必须自定义命名 |
| handler | 拒绝策略 | 队列满 + 线程满时触发 |

### 2.1 关键理解：线程数的两档

```
线程数分两档：
  第一档：corePoolSize —— 常驻线程（不回收）
  第二档：maximumPoolSize —— 最多线程（超出的叫"临时线程"，空闲会被回收）

任务提交流程（先核心 → 再队列 → 再临时 → 最后拒绝）：

  提交任务
    ├─ 线程数 < corePoolSize     → 新建核心线程执行
    ├─ 核心线程忙，队列未满       → 任务入队（等待）
    ├─ 队列满，线程数 < maxPool   → 新建临时线程执行
    └─ 队列满，线程数 = maxPool   → 执行拒绝策略
```

> ⚠️ **最常见的误解**：以为"线程不够就创建新线程"。**实际是先入队！** 核心线程满了，任务先进队列，队列满了才创建临时线程。

## 3. ctl 变量（一个 int 存储两种信息）

```java
public class ThreadPoolExecutor {
    // ★ 核心：一个 int 同时存储"运行状态"和"工作线程数"
    private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0));

    // 高 3 位：运行状态（runState）
    // 低 29 位：工作线程数（workerCount）
    private static final int COUNT_BITS = Integer.SIZE - 3;   // 29
    private static final int CAPACITY   = (1 << COUNT_BITS) - 1;  // 最大线程数 2^29-1

    // 5 种运行状态（数值依次增大）
    private static final int RUNNING    = -1 << COUNT_BITS;   // 111... 接收新任务+处理队列
    private static final int SHUTDOWN   =  0 << COUNT_BITS;   // 000... 不接收新任务，处理队列
    private static final int STOP       =  1 << COUNT_BITS;   // 001... 不接收新任务，中断所有
    private static final int TIDYING    =  2 << COUNT_BITS;   // 010... 所有任务结束，待终止
    private static final int TERMINATED =  3 << COUNT_BITS;   // 011... 已终止

    // 位运算：提取状态 / 提取线程数 / 合并
    private static int runStateOf(int c)     { return c & ~CAPACITY; }
    private static int workerCountOf(int c)  { return c & CAPACITY; }
    private static int ctlOf(int rs, int wc) { return rs | wc; }
}
```

### 3.1 为什么状态值这样设计？

```
状态大小关系（核心设计）：

  RUNNING(-1) < SHUTDOWN(0) < STOP(1) < TIDYING(2) < TERMINATED(3)

好处：比较状态只需比较 ctl 数值！

  c >= SHUTDOWN  → 线程池已关闭（不再接收新任务）
  c < SHUTDOWN   → 还在运行（RUNNING，唯一小于 SHUTDOWN 的状态）

→ 用 ctl.compareAndSet 同时保证状态+线程数的原子更新
→ 一个变量搞定两个信息，避免了状态和线程数不一致的问题
```

### 3.2 5 种状态流转

```
            ┌─────────────────────┐
            │      RUNNING        │  接收新任务，处理队列任务
            └──────────┬──────────┘
        shutdown()     │     shutdownNow()
            ▼          │          ▼
     ┌────────────┐    │    ┌────────────┐
     │  SHUTDOWN  │    │    │    STOP    │
     │ 不接收新任务 │    │    │ 不接收+中断 │
     │ 处理队列任务 │    │    │ 清空队列    │
     └──────┬─────┘    │    └──────┬─────┘
            │          │           │
            └────┬─────┴────┬──────┘
                 ▼          ▼
            ┌─────────────────────┐
            │      TIDYING        │  队列清空 + 线程归零
            └──────────┬──────────┘
                       ▼
            ┌─────────────────────┐
            │    TERMINATED       │  终止完成
            └─────────────────────┘
```

## 4. execute() 完整流程（⭐ 核心）

```java
public void execute(Runnable command) {
    if (command == null) throw new NullPointerException();

    int c = ctl.get();
    // ① 线程数 < 核心线程数 → 新建核心线程
    if (workerCountOf(c) < corePoolSize) {
        if (addWorker(command, true))
            return;
        c = ctl.get();        // addWorker 失败 → 重新读取状态
    }

    // ② 线程数 >= 核心 → 尝试入队
    if (isRunning(c) && workQueue.offer(command)) {
        int recheck = ctl.get();
        // 双重检查：入队后线程池可能被关闭
        if (!isRunning(recheck) && remove(command))
            reject(command);          // 池被关闭 → 移除任务 + 拒绝
        else if (workerCountOf(recheck) == 0)
            addWorker(null, false);   // 没有线程了 → 补一个空线程去队列取任务
    }
    // ③ 队列满 → 尝试创建临时线程
    else if (!addWorker(command, false))
        reject(command);              // 线程也满 → 拒绝策略
}
```

### 4.1 execute 流程图（务必能画）

```
execute(task)
    │
    ├─ ① workerCount < corePoolSize?
    │    是 → addWorker(task, true)  新建核心线程 ✅
    │    否 ↓
    ├─ ② 池是 RUNNING 且队列能入队?
    │    是 → 入队，双重检查：
    │         ├─ 池已关闭 → remove + reject
    │         └─ 无线程 → addWorker(null, false) 补线程（活性兜底，见 4.3）
    │    否 ↓
    ├─ ③ addWorker(task, false) 新建临时线程?
    │    是 → ✅
    │    否 ↓
    └─ ④ reject(task) 执行拒绝策略
```

### 4.2 分支 ② 的"事后裁决"：入队后为什么要 recheck？

```
分支 ② 的 recheck 一次裁决两件事（对应代码里的 if / else if 两条臂）：

  臂 1：池被关闭了？   → !isRunning(recheck) && remove(command) → reject
  臂 2：池里没线程了？ → workerCountOf(recheck) == 0 → addWorker(null, false) → 见 4.3

为什么一次读能管两件事？因为根因是同一个：
  execute 的 isRunning(c) 读发生在 offer() 之前，"两次读 + offer"之间没有任何原子性
  → offer 无法与递交那一刻的状态原子绑定 → 入队后必须"事后裁决"一次
  → 官方注释第 2 步原话（JDK 8 / 21 逐字一致）：
     「we still need to double-check whether we should have added a thread
       (because existing ones died since last checking) or that the pool shut down
       since entry into this method.」
  作者把"线程死光了"和"池关闭了"并排写进同一次 recheck，正是因为二者同源

臂 1 展开（池已关闭 → remove + reject）：
  · STOP（shutdownNow）：队列会被清空 → 任务留下只会静默丢失 → 显式拒绝
  · SHUTDOWN（shutdown）：队列本会被排空（SHUTDOWN 继续执行队列任务！），
    但任务是在"关闭窗口"内提交的 → 拒绝，守住"关闭后不接受新任务"的确定语义
    ⚠️ 不能理解成"队列里的任务永远不会执行"——SHUTDOWN 下它们会执行
  · remove 失败（任务已被某个 worker 取走）→ 不 reject，落到臂 2
    （此时必然 wc ≥ 1，臂 2 自然不触发，无害）
```

### 4.3 分支 ② 的"入队后补线程"：补一个消费者

先精确化：不是"入队后总要补线程"，是 `wc == 0` 才补。

```java
if (isRunning(c) && workQueue.offer(command)) {
    int recheck = ctl.get();
    if (!isRunning(recheck) && remove(command)) reject(command);
    else if (workerCountOf(recheck) == 0)      // ← 只有 wc == 0 才走到这
        addWorker(null, false);
}
```

**主干：入队不会创建线程**

```
任务不会自己跑，最终都得靠某条线程从队列 take() 出来 run()：

  ① addWorker(command, true)   → new 一条线程，它自己就把任务跑了  ✅ 有人跑
  ② workQueue.offer(command)   → 只把任务塞进队列，没创建任何线程  ❓ 谁跑？
  ③ addWorker(command, false)  → new 一条线程，它自己就把任务跑了  ✅ 有人跑

② 是在赌"池里已经有线程，它们会来队列取" —— 但这不是必然的：
  corePoolSize = 0 时，线程空闲一会儿全退光，池里真的可能是 0 条线程
  → 塞进队列的任务永远躺着没人取（不报错、不拒绝，就是不执行）
  → 所以 recheck 一下：真的一条线程都没有，就补一条

补的是"空线程"（firstTask = null），因为它没活干，启动后直接去 getTask()：
  runWorker(w) → firstTask 为 null → 进循环 → getTask() → 拿到刚入队那条 → run()
  → 所以准确说法不是"补空线程"，是"补一个消费者"
```

**wc 为什么会是 0：**

```
常态：corePoolSize = 0
  分支 ① 的条件 workerCountOf(c) < corePoolSize，core=0 时 "0 < 0" 恒 false
  → 分支 ① 被定义性地跳过，任务直奔入队，而此刻池里可能一条线程都没有
  （CachedThreadPool 日常不触发：它用 SynchronousQueue，offer 直接失败 → 走分支 ③）

缝隙：最后一个线程刚好正在退出
  ctl.get() 是普通读，两次读之间隔着 isRunning 读 + offer，没有原子性
    T_worker : 查到队列为空 → 决定退出（还没真正减计数）
    T_submit : offer 成功  → 队列非空了
    T_worker : 减计数      → wc 1→0，线程死亡
    T_submit : recheck 读到 wc == 0 → 入队成功，却一个消费者都没有
  官方注释把这条写在 execute() 头上："because existing ones died since last checking"
```

**两个细节：**

```
为什么传 null 而不是 command？
  command 已经在队列里了。当 firstTask 再传一次 → 跑一遍，队列那份又被取出来跑一遍
  → 任务执行两次。传 null = 无首发任务，直接进 getTask() 取。

为什么 core = false？
  core 只影响 addWorker 内部的上界检查（core ? corePoolSize : maximumPoolSize），
  不影响回收 —— timed 按当前 wc 动态算（§7.2）。
  false 把补位放宽到 max 上界，避免 addWorker 重读 ctl 时 wc 已涨到 core~max 之间而补位落空。
```

> 📎 **主干之外**：不变量"队列非空 ⟹ 至少一个线程"其实由四处共同守着 —— `getTask()` 的 `wc > 1 || workQueue.isEmpty()`（源头：非最后一个且队列空才准退出）、本节的 recheck（窗口前侧）、`processWorkerExit()` 的 `min == 0 && !workQueue.isEmpty() → min = 1`（窗口后侧，与本节的 recheck 方向互补）、`tryTerminate()` 的 SHUTDOWN 不终止（关闭路径）。正因为源头那道挡着，core > 0 时本节这条基本走不到。

🧪 **验证**：`pool/CoreZeroFallbackTest`

## 5. addWorker() —— 创建 Worker

```java
private boolean addWorker(Runnable firstTask, boolean core) {
    retry:
    for (;;) {
        int c = ctl.get();
        int rs = runStateOf(c);

        // ① 状态检查：关闭后不再接收新任务
        if (rs >= SHUTDOWN &&
            !(rs == SHUTDOWN && firstTask == null && !workQueue.isEmpty()))
            return false;

        for (;;) {
            int wc = workerCountOf(c);
            // ② 线程数检查（核心用 corePoolSize，临时用 maximumPoolSize）
            if (wc >= CAPACITY ||
                wc >= (core ? corePoolSize : maximumPoolSize))
                return false;
            // ③ CAS 增加线程数（成功后跳出双重循环）
            if (compareAndIncrementWorkerCount(c))
                break retry;
            c = ctl.get();       // CAS 失败 → 重读
            if (runStateOf(c) != rs)
                continue retry;  // 状态变了 → 重新检查
        }
    }

    // ④ 创建 Worker 并启动
    boolean workerStarted = false;
    boolean workerAdded = false;
    Worker w = null;
    try {
        w = new Worker(firstTask);       // 创建 Worker（内部 new Thread）
        final Thread t = w.thread;
        if (t != null) {
            final ReentrantLock mainLock = this.mainLock;
            mainLock.lock();             // 加主锁（保护 workers 集合）
            try {
                int c = ctl.get();
                // ⑤ 双重检查状态（持锁后用最新状态重新验证）
                if (runStateOf(c) < SHUTDOWN ||
                    (runStateOf(c) == SHUTDOWN && firstTask == null)) {
                    workers.add(w);      // 加入工作线程集合
                    workerAdded = true;
                }
            } finally {
                mainLock.unlock();
            }
            if (workerAdded) {
                t.start();               // ⑥ 启动线程
                workerStarted = true;
            }
        }
    } finally {
        if (!workerStarted)
            addWorkerFailed(w);          // 失败回滚（减线程数 + 移除 Worker）
    }
    return workerStarted;
}
```

```
addWorker 关键点：
  ① 外层循环：状态检查（shutdown 后不能加）
  ② 内层循环：线程数检查（核心/最大上限）
  ③ CAS 递增 workerCount（无锁竞争）
  ④ 加主锁保护 workers 集合
  ⑤ 持锁后二次检查（防止加进去时池已关闭）
  ⑥ 启动线程
```

## 6. Worker 内部类（线程复用的核心）

### 6.1 Worker 的结构

```java
private final class Worker extends AbstractQueuedSynchronizer
        implements Runnable {
    final Thread thread;        // 包装的线程
    Runnable firstTask;         // 第一个任务（可能为 null）
    volatile long completedTasks;   // 完成任务数

    Worker(Runnable firstTask) {
        setState(-1);           // ★ 初始 state = -1（禁止中断）
        this.firstTask = firstTask;
        this.thread = getThreadFactory().newThread(this);
    }

    public void run() {
        runWorker(this);        // 线程启动后执行 runWorker
    }

    // AQS 实现：只支持独占 + 不可重入
    protected boolean tryAcquire(int unused) {
        if (compareAndSetState(0, 1)) return true;
        return false;
    }
    protected boolean tryRelease(int unused) {
        setState(0);
        return true;
    }
}
```

### 6.2 为什么 Worker 继承 AQS？

```
Worker 继承 AQS 的原因：实现"不可重入的互斥锁"，用于精确控制中断

核心场景（shutdown 时）——interruptIdleWorkers：
  for (Worker w : workers) {
      if (!t.isInterrupted() && w.tryLock()) {   // tryLock 成功 = 空闲（未持锁）
          t.interrupt();                         // 只中断空闲线程！
      }
  }

  → w.tryLock() 成功 = 已启动（state = 0）且未在执行任务（空闲）
    注意：state = -1 的未启动 Worker，tryLock 同样失败（tryAcquire 是 CAS 0→1）
    → state = -1 一箭双雕：interruptIfStarted 显式跳过 + tryLock 天然拿不到
  → 空闲的 Worker 才允许被中断（让它从队列取任务的阻塞中醒来退出）
  → 正在执行任务的 Worker（持锁）不会被中断 → 任务能完整执行完
    （仅对 shutdown()；shutdownNow 会中断执行中的任务）

为什么初始 state = -1？
  刚创建的 Worker 还没执行任务（处于"未启动"状态）→ 禁止中断
  runWorker 开始执行时 → w.unlock() → state 变为 0 → 之后 tryLock 才可能成功

补充：shutdownNow（STOP 状态）用 interruptWorkers —— 但不是"所有线程都会被中断"：
  实际调用 w.interruptIfStarted()，只中断 getState() >= 0（已启动 runWorker）的 Worker
  未启动的 Worker（state = -1）被跳过 —— 与上文"未启动禁止中断"的设计一致
  🧪 版本差异：早期 JDK 8 直接 w.thread.interrupt() 全部中断；后续 8u 更新与 JDK 17/21
    修复为 interruptIfStarted（本仓库 jdk8-lab 的 1.8.0_441 与主工程都是后者）
  语义补充：即使 STOP 下，已分配给未启动 Worker 的 firstTask 依然会被执行（带着中断位），
    shutdownNow 只是"尽力中断"，不保证任务不执行（除非任务自己检查中断）
```

### 6.3 runWorker() —— 线程复用的核心（⭐）

```java
final void runWorker(Worker w) {
    Thread wt = Thread.currentThread();
    Runnable task = w.firstTask;    // 第一个任务（可能为 null）
    w.firstTask = null;
    w.unlock();                     // state 0 → 允许中断
    boolean completedAbruptly = true;

    try {
        // ★ 核心循环：取任务 → 执行 → 再取 → 再执行...
        while (task != null || (task = getTask()) != null) {
            w.lock();               // 加锁（执行期间禁止中断）
            // ① 线程池 STOP 状态 → 中断当前线程
            if ((runStateAtLeast(ctl.get(), STOP) ||
                 (Thread.interrupted() && runStateAtLeast(ctl.get(), STOP))) &&
                !wt.isInterrupted())
                wt.interrupt();

            try {
                beforeExecute(wt, task);   // ② 钩子：执行前（可扩展）
                try {
                    task.run();            // ③ ★ 执行任务（不是 start！）
                    afterExecute(task, null);
                } catch (Throwable ex) {   // ④ ★ 任务抛异常时钩子能拿到异常
                    afterExecute(task, ex);
                    throw ex;              // 异常外泄 → 线程死亡 → 池补线程（见坑 4）
                }
            } finally {
                w.unlock();                // 释放锁（允许中断）
                task = null;
                w.completedTasks++;        // 完成任务计数
            }
        }
        completedAbruptly = false;
    } finally {
        processWorkerExit(w, completedAbruptly);  // ⑤ 线程退出处理
    }
}
```

```
runWorker 核心：
  while (task != null || (task = getTask()) != null)
    task.run();   // ← 直接调用 run，不是 new Thread！

→ 这就是"线程复用"的本质：
  同一个线程（Worker.thread），循环执行多个任务
  线程从队列 getTask() 拿任务 → run() → 再拿 → 再 run...
  而不是"一个任务一个线程"
```

## 7. getTask() —— 取任务与线程回收

```java
private Runnable getTask() {
    boolean timedOut = false;   // 上次取任务是否超时

    for (;;) {
        int c = ctl.get();
        int rs = runStateOf(c);

        // ① 池已关闭且队列空 → 不取任务，返回 null（线程退出）
        if (rs >= SHUTDOWN && (rs >= STOP || workQueue.isEmpty())) {
            decrementWorkerCount();   // 减少线程数
            return null;
        }

        int wc = workerCountOf(c);
        // ② 是否启用超时回收：
        //    timed = 允许核心超时 || 线程数 > 核心数
        boolean timed = allowCoreThreadTimeOut || wc > corePoolSize;

        if ((wc > maximumPoolSize || (timed && timedOut)) &&
            (wc > 1 || workQueue.isEmpty())) {
            if (compareAndDecrementWorkerCount(c))
                return null;        // ③ 超时且没任务 → 退出（线程回收）
            continue;
        }

        try {
            // ④ 阻塞取任务：
            //    timed → poll(keepAliveTime)（超时返回 null → 回收）
            //    非 timed → take()（一直等）
            Runnable r = timed ?
                workQueue.poll(keepAliveTime, TimeUnit.NANOSECONDS) :
                workQueue.take();
            if (r != null)
                return r;
            timedOut = true;        // 超时了 → 下一轮退出
        } catch (InterruptedException retry) {
            timedOut = false;
        }
    }
}
```

### 7.1 线程回收的完整链路

```
线程回收（临时线程）：

  线程执行完当前任务
    → 回到 runWorker 循环
    → getTask() 取任务
    → poll(keepAliveTime) 阻塞等待
    → 超过 keepAliveTime 没任务 → 返回 null
    → runWorker 循环结束
    → processWorkerExit() 清理
    → 线程自然结束（回收）

触发回收的条件：
  timed = allowCoreThreadTimeOut || wc > corePoolSize
  → 线程数超过核心数 → 多余的线程超时回收
  → 或开启 allowCoreThreadTimeOut → 核心线程也能回收
```

### 7.2 核心线程为什么不回收（默认）

```
核心线程用 take() —— 无限阻塞等待：
  take() 永远不返回 null → getTask 不会退出 → 线程永不结束

临时线程用 poll(keepAliveTime) —— 超时返回 null：
  超时 → 线程退出 → 回收

→ 这是 keepAliveTime 只对"超过核心数的线程"生效的原因

⚠️ 精确化：线程没有"核心/临时"的身份标签！
  timed 由 getTask 每次迭代按当前线程数动态计算：timed = allowCoreThreadTimeOut || wc > corePoolSize
  → wc > core 期间，连"核心线程"也用 poll(keepAliveTime)，同样会超时退出
  → 退出后 processWorkerExit 把总数补回 core

所以"核心线程不回收"的准确含义 =
  "线程总数不会降到 core 以下"，而不是"某条特定线程永远活着"
  （也解释了为什么无法预测"回收哪条线程"——由谁先空闲决定）
```

## 8. processWorkerExit —— 线程退出处理

```java
private void processWorkerExit(Worker w, boolean completedAbruptly) {
    // ① 异常退出 → 减少线程数（正常退出时 getTask 已减过）
    if (completedAbruptly)
        decrementWorkerCount();

    final ReentrantLock mainLock = this.mainLock;
    mainLock.lock();
    try {
        completedTaskCount += w.completedTasks;   // 汇总完成任务数
        workers.remove(w);                        // 移除 Worker
    } finally {
        mainLock.unlock();
    }

    // ② 尝试终止线程池（如果满足终止条件）
    tryTerminate();

    // ③ 线程数不足 → 补充
    int c = ctl.get();
    if (runStateLessThan(c, STOP)) {          // 还没到 STOP
        if (!completedAbruptly) {
            int min = allowCoreThreadTimeOut ? 0 : corePoolSize;
            if (min == 0 && !workQueue.isEmpty())
                min = 1;                      // 队列还有任务 → 至少留 1 个线程
            if (workerCountOf(c) >= min)
                return;
        }
        addWorker(null, false);               // 补充线程（保持线程数）
    }
}
```

```
为什么异常退出后要补充线程？
  线程因异常退出 → 线程数减少 → 可能低于 corePoolSize
  → 补一个线程保证线程池有足够处理能力
```

### 🕳️ 坑 1：任务提交顺序误解

### 🕳️ 坑 3：自定义 ThreadFactory 的重要性

```java

ThreadFactory factory = new ThreadFactory() {
    private final AtomicInteger seq = new AtomicInteger();
    @Override
    public Thread newThread(Runnable r) {
        Thread t = new Thread(r);
        t.setName("order-async-" + seq.incrementAndGet());  // 可识别！

```

### 🕳️ 坑 4：任务里抛异常，线程会死但池会自动补

```java
// ⚠️ 任务 run() 抛异常 → 异常经 runWorker 的 catch (Throwable ex) 外泄
// → 该线程死亡（completedAbruptly=true）→ 池自动补一条新线程（processWorkerExit）
// → 池"看起来没死"，但异常默认经 Thread 的 uncaughtExceptionHandler 打印到 stderr（不是无声吞掉）
// → afterExecute 能拿到异常，靠的正是 runWorker 里那个 catch 块（§6.3 ④）

// ✅ 生产规范：任务内自行 try-catch，或实现 Thread.UncaughtExceptionHandler / 自定义 afterExecute
```

### 🕳️ 坑 5：核心线程为 0 的注意

```java
// corePoolSize = 0 的场景（如 CachedThreadPool）：
// 真实队列：任务提交 → 入队 → execute 兜底：workerCount == 0 → addWorker(null, false) 补线程
//   → 不会出现"队列积压但无线程"（兜底失败 = 池已关闭/到上限，本来就该拒绝）
//   → 完整因果链见 §4.3（不变量 + 四层防线）；本仓库验证测试：pool/CoreZeroFallbackTest
// SynchronousQueue（CachedThreadPool）：不存储 → offer 直接失败 → 走 addWorker 新建线程
// 真正的坑：空闲期无线程，突发时第一个任务必须等新建线程（延迟）；
//   且队列一旦非空，线程数不会自动缩回 0（除非开 allowCoreThreadTimeOut）
```

## 10. 面试高频考点

1. **线程池 7 大参数分别是什么？**
   → corePoolSize / maximumPoolSize / keepAliveTime / unit / workQueue / threadFactory / handler。

2. **任务提交的执行顺序？**
   → 核心线程 → 队列 → 临时线程 → 拒绝策略。**注意队列在临时线程之前！**

3. **ctl 变量怎么一个 int 存两种信息？**
   → 高 3 位运行状态 + 低 29 位工作线程数。状态值大小设计（RUNNING<SHUTDOWN<STOP<TIDYING<TERMINATED）使得比较状态只需比较数值。

4. **线程是怎么复用的？**
   → Worker.thread 循环调用 runWorker → getTask() 从队列取任务 → task.run() 直接执行（不是 new Thread）。一个线程执行多个任务。

5. **临时线程什么时候回收？核心线程为什么默认不回收？**
   → 临时线程用 poll(keepAliveTime) 超时返回 null → 退出；核心线程用 take() 无限阻塞 → 永不退出。

## 12. 自测题

1. **execute() 的三条路径分别是什么？为什么队列在临时线程之前？**
   <details><summary>答案</summary>

   ① 核心未满 → 新建核心线程；② 队列未满 → 入队；③ 队列满 → 新建临时线程；④ 都满 → 拒绝。

   队列优先于临时线程：建线程（syscall + 栈分配 + 注册，µs~百µs）比入队（内存写 + 一次 unpark，ns~µs）
   贵 1~2 个数量级 → "先缓冲、后扩资源"。
   完整因果链见 §1.2 手段③；"压缩哪个代价、守住哪个正确性"见 §1 开头那把尺子。
   </details>

2. **ctl 高 3 位低 29 位的设计有什么好处？**
   <details><summary>答案</summary>

   ① 一个 AtomicInteger 原子更新状态+线程数（避免不一致）；② 状态数值大小设计使比较只需 `c >= SHUTDOWN` 一次位运算；③ 节省内存。
   </details>

3. **线程复用是怎么实现的？**
   <details><summary>答案</summary>

   Worker 包装一个 Thread；runWorker 中 while 循环调用 getTask() 从队列取任务，然后直接 task.run()。同一个线程反复执行队列中的任务，而不是每个任务 new Thread。
   </details>

4. **临时线程为什么用 poll(keepAliveTime) 而核心线程用 take()？**
   <details><summary>答案</summary>

   poll(keepAliveTime) 超时返回 null → getTask 返回 null → 线程退出（回收临时线程）；take() 无限阻塞 → 永不返回 null → 核心线程永不退出。
   </details>

5. **任务抛异常后线程池会发生什么？**
   <details><summary>答案</summary>

   该线程退出（completedAbruptly=true）→ processWorkerExit 减少线程数并补充新线程 → 线程池继续工作。但异常默认只经 uncaughtExceptionHandler 打印到 stderr，不会进日志体系（除非自定义 Handler 或 afterExecute，见坑 4）。
   </details>

6. **入队已经成功了，为什么还要 `addWorker(null, false)`？为什么传 null、为什么 core=false？**
   <details><summary>答案</summary>

   **因为入队不会创建线程。** 三条分支里 ① 和 ③ 都 new 了一条线程（它自己就把任务跑了），只有 ② 是纯 `queue.offer()`，没创建任何线程。万一池里一条线程都没有（`corePoolSize = 0` 时空闲线程全退光了），塞进队列的任务就永远没人取。

   所以 recheck 一下：`workerCountOf(recheck) == 0` 就补一条。补的这条 `firstTask = null`，因为它没活干，启动后直接 `getTask()` 从队列拿——正好把刚入队那条取走。

   传 `null`：command 已在队列里，当 firstTask 传会被执行两次。
   传 `false`：`core` 只影响 addWorker 内部的上界检查（不影响回收），false 把补位放宽到 `maximumPoolSize`。

   wc 为 0 的另一条来源是竞态缝隙（最后一个 worker 查到队列为空决定退出，与我们的 offer 之间没有原子性），官方注释写作 "because existing ones died since last checking"。详见 §4.3。
   </details>
